---
title: A pipeline is not a property of a recording
group: Substrate
position: 11
status: settled
decided: 2026-08-28
---

The recording, the analysis run on it, and the values that apply one to the
other are separate documents. A project document sits beside the recording and
carries its identity. A pipeline document is a file the user owns, kept wherever
they keep their work, declaring structure and ports and knowing nothing about
any footage. A parameter document holds values a port can be satisfied from. A
take names one pipeline, the version it was bound against, and where each of its
ports gets its value. None of the four contains another, and the references run
one way — a take names a pipeline and a parameter document, and neither of those
ever names a recording.

What this refuses is the self-contained project: one file holding the footage
reference, the chain, and its tuning together. The argument against it is not
tidiness but revision. A pipeline is corrected *after* the recordings it was
applied to have been analysed — tune a chain on one recording, apply it to
forty, then find the mistake in step three — and under embedding that fix is
forty edits with nothing able to say which of the forty are now on the corrected
version. Embedding gives the chain no identity of its own, so it cannot be
versioned, and the operation the tool exists to support is the one that becomes
untrackable.

The null option is the bundle. ilastik's `.ilp` carries workflow, labels and
cached features in one document, and the consequence is that applying somebody
else's classifier to your data is an awkward operation on a file that is mostly
their pixels. CellProfiler splits the same content the way this decision does —
`.cppipe` is the analysis definition and travels, `.cpproj` adds the image list
— and the artifact people cite in a methods section is the definition, which is
the tell for which half carries the science.

The opposite error is the definition that names its recording's surroundings.
DeepLabCut's `config.yaml` holds an absolute `project_path`, hand-edited on
every move, which is a machine-local fact written into the document meant to
travel — the durable-instruction failure in a file instead of a comment. So a
pipeline declares what it needs and never where to find it: requirement in the
document that travels, resolution in the one that does not.

Values live apart from both for a reason neither of those covers. A port's value
may be proposed by an optimiser, generated by a sweep, or computed by a script
from a calibration frame, and each of those has to write it down somewhere. A
value held inside a document SIEVE also authors makes every such generator parse
and rewrite that document, which is two writers on one file; a value in its own
document is owned outright by whatever produced it. A port therefore names a
document and a key within it, since one crop document holds several named
regions. The arrangement also absorbs geometry that is sometimes shared and
sometimes not — two recordings shot on one undisturbed rig point at the same
crop document, a third shot after the table was bumped points at its own —
without a batch or session concept existing anywhere.

The project document holds identity and no analysis at all. Its job is to fail
loudly rather than to remember: without it a renamed recording leaves
`.sieve/<stem>/` orphaned with nothing saying what it was about, and a recording
re-exported at a different size under the same name leaves every take beside it
silently describing footage that no longer exists. Which take was last open is
deliberately not here — that is where a person was rather than what is true of
the recording, so it belongs to the per-user library beside the settings, where
two people opening one recording off a shared drive do not inherit each other's
cursor.

Identity is a fingerprint over the recording's bytes — its size with a checksum
of its first and last block, the shape OpenSubtitles' hash has long used to name
video files quickly — together with the filename it was last seen under. Hashing
the whole file is not available at any price that fits: an hour of 4K is tens of
gigabytes, which is tens of seconds per recording, and it would be paid both on
every open and on every candidate when searching a folder. The sparse
fingerprint costs two seeks and a stat, so verifying on open is free and testing
every video in a folder stays under a second, which is what makes the same field
answer the second question: a recording renamed in place is found by hashing the
candidates beside it. That repair is offered and never performed — `video.mp4`
sitting beside `video_backup.mp4` is an ordinary folder, and byte-identical
copies make the match genuinely ambiguous in a way only the user settles.

What this buys is byte identity rather than content identity, and the direction
it errs is deliberate. A lossless remux decodes to identical frames and
fingerprints completely differently, so SIEVE calls it a different recording
where a person would not; the honest fingerprint is over decoded pixels and is
not available, since it needs a decoder this tree carries as an experiments
dependency rather than a runtime one, and `src/sieve/project/footage.py` already
refuses a frame table for the adjacent reason. A false alarm asks a question,
where the alternative silently accepts the wrong file. The field names the
algorithm that produced it rather than implying it — the instinct
[ADR-0010](ADR-0010-a-key-carries-a-version.md) has about keys — so that a
content-level fingerprint, the day a decoder is a runtime dependency, coexists
with this one instead of orphaning every project written under it.

The fingerprint repairs a rename and not a move: `.sieve/` sits beside the
recording, so a file renamed in place still has its project next to it, while a
recording moved to another drive leaves the directory behind with nothing to
search from. Carrying the same fingerprint on the library row would close that,
letting a recording added from its new home be recognised as one an orphaned
project is about. That is a consequence of the field existing, not a further
decision here.

Location follows from the split. The project document is
`<folder>/.sieve/<stem>.json`, with takes and derived work under
`<folder>/.sieve/<stem>/`, so a folder holding a season's footage holds many
projects without the folder meaning anything. A pipeline has no home beside any
recording — one used on forty in different folders would need forty — so it
lives where the user puts it, in a repo or beside their data or in an email, and
a per-user index records the ones SIEVE has seen. Parameter documents have the
same homelessness for the same reason and take the same answer. That is the
arrangement `src/sieve/project/library.py` already holds for recordings: the
document belongs to the user, and the index is a fact about this person on this
machine.

A pipeline carries a UUID minted at creation, a display name, and a monotonic
version, because those are three jobs. The UUID survives a rename and a move,
which is what a reference needs and what a path cannot give — the same
distinction between location and identity `library.py` records about its own
key. The name is what a human picks out of a list. The version is what makes
"v2 dropped a parameter" sayable, so a take that recorded the version it bound
against is checkable when it is opened rather than discovered wrong on a cluster
node an hour into a queue. Content hashing is refused for the reason
[ADR-0010](ADR-0010-a-key-carries-a-version.md) refuses it in a key: every edit
would mint a new identity, and *the same pipeline, corrected* is precisely what
must stay expressible.

Nothing is written beside the recording until there is authored content to
write. Pointing at a file adds a row to the per-user library and touches its
folder not at all; the project document appears with the first take. Lab footage
sits on read-only archives and shared mounts, and a tool that writes into
somebody's data directory because they looked at a file is one they learn to
work around. The accepted cost is that a recording added and never worked on has
no identity beside it, so renaming it strands the library row — which is a row,
not work.

Every one of these documents carries a schema version from its first byte, per
the lead in `docs/architecture-leads.md`, and a document written by a later
version is left alone rather than reinterpreted or overwritten, which is what
`library.py` already does. Within `.sieve/<stem>/` the authored and the reported
stay apart: takes are authored, while run records and derived artifacts —
proxies, chunks, stored step output — are written by the run and never by hand,
and one directory holding both is one nothing can safely walk.

The accepted cost is felt at the small end. One box drawn on one video now
touches four documents where a bundle would have touched one, and that is only
tolerable because SIEVE writes the parameter document itself at a default
location — the person sees a crop they drew, not four files, unless they go
looking for them. The arrangement is built for the case where the same chain
meets forty recordings, and it charges the single-video case a little to get
there.

What is deliberately not decided here is how a port names its value and what a
binding looks like, which wait on the parameter and fan-out leads, and sidecar
import — existing annotations, ground truth, calibration authored by other tools
entirely. That is a further writer and gets its own place under `.sieve/<stem>/`
when something first reads one. The layout leaves room for it; this decision
claims nothing about it.
