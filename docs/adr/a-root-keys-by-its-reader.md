title: A root keys by its reader
adr: 24
position: "04.05"
status: settled
decided: 2026-08-09
---

A root's key flavour follows the reader: a file read through the shared decode
stack folds `source_key`; only a tool reading with its own code folds
`picked_key`.

Why: the decoder's identity and the decoded plane move the pixels a
decoder-read root is handed, so omitting them keys a colour graph and a luma
graph over one file alike — the symptomless stale hit `cache_key.py`'s opening
paragraph is written against. For an own-code reader, `version` already stands
proxy for the reading, and folding a decoder that never touched the file would
move its keys on every seek-strategy change; `picked_key`'s docstring argues
that half and it holds exactly there. The first source tool keyed every source
root bare, which broke the equality
[a-users-file-wires-in-like-any-other-input](a-users-file-wires-in-like-any-other-input.md)
states in its key paragraph; under this rule an artifact standing where footage
stood — a written crop, a checkpoint, a folder of pre-cropped videos — is
decoder-read, so that paragraph's "free by construction" holds again as a rule
rather than as a coincidence of one function. The obvious alternative —
accepting both halves as key-moving and re-stating the Phase 5 gate — dies at
the settled end state: VISION's "every input including this one is a tool" and
the mockup's source card make source tools the eventual root of all footage,
so a bare key would become the primary path's key the day that card lands. The
measurement, v2's one-flavour precedent, and the full argument are
[findings/2026.08.09-a-source-tool-root-keys-in-a-different-flavour-than-the-footage-it-replaces.md](../findings/2026.08.09-a-source-tool-root-keys-in-a-different-flavour-than-the-footage-it-replaces.md).
