# DAG validation

The item asked for construction, cycle detection, topological sort, and the
static edge rejection the declared I/O types exist to enable, plus the walk
`cache_key.py` deliberately does not carry. All five are in
`src/sieve/pipeline/dag.py`, and the two things worth recording are why the
order is not free and why the key walk is allowed to return a partial answer.

## The topological order is not free

A topological order is not unique, and the obvious implementation lets which
one comes out depend on when a node was freed by Kahn's algorithm — which is a
property of the traversal, not of the document. `_topological` re-sorts the
ready set by each node's position in `pipeline.nodes` on every step instead, so
the order is the document's.

This looked like a readability nicety and is not. The executor will schedule in
this order and VISION step 7's processing report will key against it, so an
order that varied with the shape of the traversal would make two runs of one
unchanged project produce reports that are not comparable, with nothing having
changed to explain it.

## A partial key map is the right answer

`node_keys` returns keys for the cacheable nodes and simply omits the rest.
`cache_key.py` already establishes that non-cacheability propagates for free —
a downstream with no upstream hash has nothing to fold in — and the walk is
where that becomes visible: `NotCacheableError` is swallowed at exactly the
node that raises it, and every descendant then fails the "are all my parents
keyed" test on its own.

The alternative, raising out of the walk, would mean one non-deterministic
filter in a twelve-node graph costs the other eleven their cache entries. The
other alternative — inventing a key for a node whose ancestry cannot be
reproduced — is the silent failure the whole cache-key module is written
against. Absence is the only honest third option, and it reads correctly at the
call site: a node not in the map is a node that must be computed.

## What was checked by mutation

Three deliberate breakages, each caught by exactly one test:

| Mutation | Caught by |
| --- | --- |
| append newly-freed nodes instead of re-sorting the ready set | `test_the_order_follows_the_document_and_not_when_a_node_was_freed` |
| key a root against `[]` rather than `[source_key(...)]` | `test_the_walk_is_the_hand_walk` |
| report a missing filter once per node rather than once per `(id, version)` | `test_a_missing_filter_is_named_by_id_and_version_all_at_once` |

The first is the one worth keeping. Appending is what an implementation
naturally does, it produces a perfectly valid topological order, and every
other test in the file passes with it in place — the graph is still correctly
ordered, it is just ordered by an accident of the traversal rather than by the
document.

`test_the_walk_is_the_hand_walk` is written as a hand-walk rather than as a
digest comparison on purpose. It asserts that the traversal reaches the same
answer `tests/unit/test_cache_key.py` reaches by hand over the same shape, so
a traversal that grew its own idea of what a key is made of would make the two
files disagree rather than leave each internally consistent.
