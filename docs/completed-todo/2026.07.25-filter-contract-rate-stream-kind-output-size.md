summary: >
  The three things VISION asks of filters that `FilterSpec` could not express
  are now declarable: a filter can say its output stops being indexed like its
  input, an edge can carry rows instead of frames, and a checkpoint's on-disk
  size can be predicted before it is written.

decisions:
  - what: 'rate and output size are methods on `ParamsBase`, not fields on `FilterSpec`'
    why: 'the quantity *is* a parameter — a decimator''s stride, a downsampler''s scale — so a constant on the spec cannot express the one case the declaration exists for, and two nodes sharing a spec must be able to disagree'
  - what: '`output_rate` returns `Fraction`, not `float`'
    why: 'it is the divisor in `ceil(need / rate)`, and a binary rounding one short of an integer costs a whole warmup frame at exactly the boundary the arithmetic is about'
  - what: '`rate_changing` on the spec is cross-checked against whether `params_model` overrides `output_rate`'
    why: 'the override computes the conversion; the flag is what makes forgetting to write one raise at registration instead of rendering an under-warmed preview that looks entirely plausible'
  - what: 'the same cross-check is deliberately *not* applied to `frame_bytes_ratio`'
    why: 'storage is a HUD prediction and never a correctness decision, so an undeclared override is a wrong number rather than a wrong result — the asymmetry is the point'
  - what: '`source_warmup_frames` walks sink to root, converting at each node, rather than summing'
    why: 'ARCHITECTURE''s sum is right in the wrong unit; summing is only valid when one index space runs the length of the path'
  - what: 'the path arithmetic lives in `core/filter_base.py`, not in `pipeline/executor.py`'
    why: 'it needs no graph, only an order someone else established, so it is testable with no executor — and the conversion belongs beside the declaration that defines its unit'
  - what: '`TableSpec` is a sibling of `ArraySpec` under a `StreamSpec` union, not a field on it'
    why: 'a table has no dtype and an array has no columns, so one type carrying both field sets is half-empty whichever kind it describes'
  - what: 'columns are conjunctive where dtype sets are disjunctive'
    why: 'a filter listing two dtypes accepts either; a filter listing two columns needs both, because an absent column cannot be substituted by a present one'
  - what: 'kind narrowing goes through `isinstance`, with `StreamKind` kept for naming a rejection'
    why: 'pyright strict does not narrow a union on a `ClassVar` discriminator, and a suppression to keep the prettier spelling would buy nothing'

rejected:
  - what: 'moving frame decimation into `decode/` as a source setting rather than a filter'
    why: 'VISION 3C lists it among temporal filters and step 4 puts it *into* the graph, where order shifts the outcome — a decode-time setting could not sit downstream of an optical-flow node. Its only advantage was that the index-space conversion already happens in `decode/`, and `output_rate` removes that advantage'
  - what: 'a `rate_param: str` naming the integer field that divides'
    why: 'checkable like `primary_params`, but it can only express integer decimation — not interpolation, not a windowed filter emitting one frame per overlapping span'
  - what: 'named ports on `Edge` so a detector could emit a frame and a table at once'
    why: 'a real case, but it changes the saved artifact and every edge ever written; worth making when a filter needs it and not before'
  - what: 'a `Callable[[ParamsBase], Fraction]` field on the spec'
    why: 'unserializable, awkward to type, and strictly worse than a method on the class that already knows the stride'
  - what: 'a third `Mode` member for rate-changing filters'
    why: '`Mode` answers whether a filter can emit as soon as it consumes; a decimator is streaming by that test and rate-changing by another, and folding two orthogonal axes into one enum makes both unaskable'
