# Filter contract: rate, stream kind, output size

Closes `docs/findings/2026.07.25-the-filter-contract-cannot-type-vision.md`,
which is now `status: closed`. The finding's own summary of the three gaps —
"one gap wearing three hats, because output frames per input frame is most of
output bytes per input byte" — turned out to be the design: `output_rate` is
consumed twice, once by the warmup conversion and once by the storage
prediction, and `frame_bytes_ratio` supplies the half it does not cover.

## The two open questions, answered

**Where stream kind belongs.** Beside `ArraySpec`, not on it. The finding
raised the awkward case — a filter emitting both a frame and a detection table
— and that case is genuinely unsolved here: one stream per node still. It is
unsolved deliberately, because solving it means named ports on `Edge`, and that
is a change to the artifact rather than to the contract.

**What shape the rate declaration takes.** A method on the params model, for
the reason the finding predicted would decide it: a decimator's factor is a
parameter, so a constant on the spec is not merely inelegant but unable to
express the case. The cost is that the spec stops being purely data. That cost
is paid down by `rate_changing`, which *is* data, and which cannot disagree
with the method because `__post_init__` compares the two.

## Why the cross-check compares function objects

`self.params_model.output_rate is not ParamsBase.output_rate` rather than
calling it. A params model with required fields cannot be instantiated during
spec construction, and the question being asked is whether an override exists
at all, not what it returns. The check proves an override was written, not that
it is correct — but the failure it closes is the one the finding named, which
was forgetting to write one entirely.

test states what the wrong answer was, since 50 alone does not show that
anything was ever at risk of being 5.

## What changed outside the item's scope

`FilterSpec.accepts` and `emits` widened from `ArraySpec` to `StreamSpec`, and
`register_filter` widened with them. No existing caller passes a table, so this
is source-compatible; it is noted because the diff shows two signature changes
in a file the item's title does not mention.

The three specs the new tests chain (`DECIMATOR`, `DOWNSAMPLER`, `IIR`) are
module-scope constants rather than locals. Constructing them is what several
tests do *before* the thing they are about, and repeating the construction was
also the only thing in the file `ruff format` disagreed with.
