# Per-node backend

Promoted out of `docs/LATER.md`'s GPU entry rather than done as part of it. The
GPU work proper — `namespace.py`, frame residency, cache locality — stays
deferred and correctly so; this is the one piece of it that is cheap, is
testable with no GPU, and would otherwise force a signature change on the CLI
after the CLI was written against the old one.

## The rule this restores

`dispatch.py`: "a filter with a CPU kernel and no GPU kernel is complete, not
deficient." A single `backend` on the plan contradicted that — a GPU plan over
a chain containing one CPU-only filter raised `NoKernelError` and the whole run
died, though every node had *a* kernel. Selection is now a plan-time decision
per node, and the key is derived from what was selected. The executor's
no-fallback rule is unchanged and is now trivially true: by the time it runs
there is nothing left to choose.

## A docstring that was wrong

`dag.py` described a mixed-backend graph as "two walks, which is what the
per-node shape of `node_key` already allows". That cannot work. A downstream
key folds in its upstreams' keys, so two independent walks can only ever
describe two *disconnected* subgraphs — a chain whose backend changes partway
is one walk in which the backend varies. The sentence is corrected in place and
the old claim kept visible, since a reader who remembers it should see it
withdrawn rather than silently absent.

The consequence is load-bearing and is what the new test's last two assertions
pin: a node running on CPU in both plans still keys differently between them
when something upstream of it moved to GPU. A per-node backend that stopped at
the node itself would let that downstream share entries across two runs that
computed different bytes.

## What was checked by mutation

| breakage | caught by |
| --- | --- |
| a mapping missing a node defaults to CPU | the missing-node test |
| keys derived from one backend rather than the mapping | mixed-backend test's key inequality |

## What is still not here

Nothing chooses the mapping. A caller states it, and no code walks the kernel
shelf against `DEFAULT_PREFERENCE` to build one, because that resolution needs
a policy — fastest available per node, or fewest host/device transfers across
the graph — and the second is only the right answer once frames can stay
resident. Recorded in `docs/LATER.md` under GPU execution.
