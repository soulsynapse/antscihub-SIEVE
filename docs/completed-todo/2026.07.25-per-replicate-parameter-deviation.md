# Per-replicate parameter deviation

`core/pipeline_model.py` had said replicates are processed with identical
parameters and called that deliberate. It is now `Replicate.overrides` plus
`resolved_params`, and the docstring records the reversal rather than deleting
the sentence.

## The two writes

`Project.with_param_edit(node_id, replicate_id, params)` pins what changed on
the replicate *and* overwrites `Node.params` with everything submitted. The
second write is the whole mechanism: an unconfigured replicate resolves to
`Node.params`, which therefore always holds the most recent settings, so the
next arena the user clicks into opens showing the last one's values. The cost
was accepted knowingly in the TODO item and is unchanged — editing replicate 2
silently changes the ten nobody was looking at.

`with_param_reset` is the way back, and it moves nothing: resetting is not an
edit, so the default stays where the last real edit left it. Without it a
parameter set once could only be re-pinned, never returned to inheriting, and
the replicate could never rejoin the equivalence group it started in.

## Why sparsity is per key

The TODO item required sparsity but did not say at which level. Per node — an
override is present or absent — cannot express the case the whole feature is
for: a dim arena that needs its own threshold and should still follow later
changes to every parameter nobody varied. Per key it is a dict merge,
`{**node.params, **override}`, and both halves of the workflow hold at once.

The consequence is that the pinned set has to be a *diff*, taken against what
this replicate resolved to immediately before the edit. That makes submitting a
value equal to the one on screen pin nothing — which is precisely the ambiguity
requirement 3 of the item already accepted ("cannot tell 'the user set this to
the same value' from 'the user never touched it'"), now paid at write time
instead of read time. It buys the GUI being allowed to submit a whole form.

## What was checked by mutation

- Replacing `updated_node` with `node` — dropping the second write — fails
  `test_untouched_replicates_follow_the_newest_edit` and two others. This is the
  mutation that produces a system where all twelve arenas must be configured by
  hand, and nothing else in the suite notices it.
- Storing the whole submitted set rather than the diff fails only
  `test_a_pinned_parameter_does_not_freeze_its_siblings`, which is the intended
  one-to-one: that test exists for exactly this mistake.
- Returning the live dict from `Replicate.override_for` fails only
  `test_an_override_read_out_cannot_be_written_back_in`. `frozen=True` stops the
  field being reassigned and says nothing about the dict inside it.

## What changed outside the item's scope

`test_replacing_the_graph_catches_stale_checkpoints_and_sinks` had to grow a
step. The shared fixture now carries an override, so swapping the pipeline out
raises on the *override* before it reaches the checkpoint — the test now asserts
both, in order, which is a stronger claim than the one it made before.

`Replicate.overrides` is declared `hash=False`. A frozen dataclass generates
`__hash__` from its compared fields, and a dict field would have made every
`Replicate` unhashable at the first `set()` — a failure with no relation to
whatever code triggered it. Excluding it is also the honest semantics: identity
is `replicate_id`, so two replicates differing only in overrides hash alike and
compare unequal.

`default_factory=_no_overrides` rather than `dict`, because pyright strict
infers `dict[Unknown, Unknown]` from the bare builtin.
