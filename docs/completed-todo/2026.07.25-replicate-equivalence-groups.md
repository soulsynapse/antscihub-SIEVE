# Replicate equivalence groups

`equivalence_groups(pipeline, replicates)` walks replicates in order, builds a
canonical JSON key from `resolved_params` over the graph's nodes, and assigns
the next unused integer on first sight of a new key. `Project.equivalence_groups`
is a lookup around it, `ReplicateDocument.equivalence_groups` is the GUI's, and
neither computes anything itself — the same rule `resolved_params` is under, for
the same reason.

## The TODO asked for topological order; declaration order is what landed

The item said to hash over "the graph's nodes in topological order". That buys
nothing here and was not implemented. The grouping is invariant under node
order: every replicate is fingerprinted under the *same* order within one call,
so permuting the nodes changes every fingerprint string and changes no
equivalence class. What topological order would have cost is real — a
`pipeline/dag.py` dependency underneath a function in `core/` that is otherwise
pure arithmetic over `resolved_params`, and `dag.py` does not exist yet.

Declaration order is stable for a given document: `Pipeline.nodes` is a tuple,
`_replacing` substitutes positionally, and YAML round-trips preserve it. That is
all the stability the numbering claims, and it is the same stability
`Project.replicates` already documented.

## Why the GUI document grew a graph

The replicate table's model reads `ReplicateDocument`, which held a
`ReplicateSet` and nothing else. A group number is not derivable from a
replicate alone — `overrides` is a mapping whose keys name nodes — so the
document now holds a `Pipeline`, empty until `set_pipeline` is called.

Nothing calls `set_pipeline` yet. There is no GUI that edits nodes and no
project loader (that is the "Open and save a project" item), so in the running
application every replicate currently reads group 1, which is the correct answer
to "which of these run the same thing" when the answer is "nothing yet". The
column becomes informative the moment either of those lands, with no further
change here.

`set_pipeline` is deliberately not a `QUndoCommand`. It is how a loaded document
hands the document its graph, not a user edit; when a graph editor exists, its
edits go through the undo stack and land here, so the setter stays the one write
either way.

## What was checked by mutation

- Fingerprinting `replicate.overrides` instead of `resolved_params` — the
  plausible shortcut, since an override is what a user just clicked — fails
  `test_a_deviating_replicate_renumbers_every_group_below_it` and the GUI's
  `test_the_number_is_derived_rather_than_stored`. It splits a replicate that
  pinned a parameter to the value its siblings inherit, and merges nothing.
- Walking only `nodes[:1]` fails exactly
  `test_a_deviation_anywhere_in_the_graph_splits_a_group` and nothing else,
  which is the one-to-one that test was written for.
- Letting the replicate itself into the fingerprint (geometry, name, id) fails
  four tests across both files. Every arena has its own ROI, so this is the
  mutation that silently turns the column into a row counter.

## What changed outside the item's scope

`Column.AREA` and `Column.GROUP` are now a `_DERIVED` frozenset rather than two
`is Column.AREA` checks in `setData` and `flags`. Both columns are read-only for
the same reason — they are computed from something else in the document, and
there is nothing coherent to write backwards through the derivation. "Make this
replicate group 2" names no parameter change.

`replicate_tab._build_table_panel` listed the resize-to-contents columns by
name, so adding one silently left it stretch-sized. It now takes every column
that is not `NAME`, which is what the line meant.

Group numbers are right-aligned by the existing `TextAlignmentRole` branch,
which covers every column but `NAME` — no new case was needed.
