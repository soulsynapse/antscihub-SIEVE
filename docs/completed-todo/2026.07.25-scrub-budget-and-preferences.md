# Scrub budget and Preferences

Read `docs/findings/2026.07.25-the-seek-is-irreducible.md` for the probes and
what each one predicted. The short version: the seek is 46.7 ms of a 67.8 ms
round trip and there is no knob for it, so the budget was going to be missed
until either the number changed or the software started asking for less.

Both happened, in that order and for stated reasons. The ceiling moved to
100 ms — the classic threshold for a response reading as instantaneous — and
`gui/scrub_policy.py` now watches the median of the last 5 scrub round trips
and, above budget, snaps drag targets to a 1 s grid that `gui/frame_cache.py`
serves for free. A cache hit does not seek, which is the entire mechanism.

Also landed: `gui/preferences.py` (QSettings, three settings, all of them
consumed by something), `gui/preferences_dialog.py` behind Edit →
Preferences… applying on change, and `gui/toast.py` — the bottom-right notice
that tells the user once, and only once, when coarse mode engages.

## The bug the tests caught

Request coalescing originally dropped whatever was pending in favour of
whatever arrived last. That is correct for drag positions and wrong for a
released slider: a scrub landing on a cached frame is served instantly and was
taking the pending exact request down with it, stranding the user on a grid
point they never asked for. Requests now carry their kind, and a pending
`EXACT` is never discarded for a later `SCRUB`.

`test_a_pending_exact_request_survives_a_later_cached_scrub` is the pin. It
only reproduces with the cache warm and the policy degraded, which is why the
degradation tests inject a policy with a budget of 0 ms — the reference machine
meets the real budget on this clip, so waiting for a genuine miss would mean
the path is only exercised on machines where it is least likely to be checked.
