# Stale frame on reopen

The TODO called this a flash: the old frame paints, the next decode corrects
it. That was the visible half. The unrecorded half is that `_on_frame_ready`
also put the stale frame into `FrameCache`, and `_reset_source_state` had
already cleared the cache — so the first thing in the new video's cache was a
frame of the old one, filed under an index the new video also has. That is not
self-correcting; a later scrub to that index is served from cache and shows the
wrong video with no decode to overwrite it. The generation check runs before
the `put`, which is what closes it.

**What was checked by mutation.** Both new tests were run against the
unmodified `player.py` and both fail there:
`test_a_frame_decoded_before_a_close_is_not_shown` records a display on a
player with no source, and `test_a_frame_decoded_before_a_reopen_is_not_shown`
records `[0, 30]` where `[0, 0]` is correct — frame 30 of the closed source in
the reopened one's viewport.

Both tests change the source in the same turn of the event loop that starts the
decode. That is what makes them deterministic rather than a race: the queued
`frame_ready` cannot be delivered until control returns to the event loop, so
the reset is always first, whatever the decode thread's timing.

**Outside the item's scope.** The `request is not None` guard on the
degradation sample in `_on_frame_ready` is gone, along with the `request is
None` display branch above it. Both existed only to describe the state the
cleared `_in_flight` slot could produce; with the early return, `request` is
non-`None` for the rest of the method by construction.
