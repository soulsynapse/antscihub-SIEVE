# Window state and layout

Three edits that share one question — what the user sees before they have done
anything — and one consequence that was not in the item.

## Remembering a path made the tests write the real store

`MainWindow` built its own `Preferences()`, which is `QSettings()` with the
organisation and application names `app.main` sets. Nothing wrote to it, so
nobody noticed. Recording the opened video changes that: every GUI test that
opens the synthetic video would have written a `tmp_path` mp4 into the
developer's actual registry, and the next real launch would have tried to
reopen a file pytest deleted.

So `MainWindow.__init__` now takes an optional store, and both window fixtures
inject one over a temporary INI file. That is the same argument `Preferences`
itself already made for accepting an injected `QSettings` — it just did not
reach the window until the window had something to write.

The same reasoning is why the restore is `restore_last_video()` called by
`app.main` rather than something the constructor does. A constructor that
decodes a file is one that cannot be used by a test, a benchmark, or a future
CLI-side preview without arranging for a video first.

## The existence check belongs to the caller

`Preferences.last_video` returns whatever was stored, without asking the
filesystem whether it is still there. The alternative — return `None` for a
missing file — collapses two states the window needs to distinguish: "nothing
remembered" and "remembered, but gone". Today both produce the same empty
window, but only one of them is a candidate for the eventual "could not find
*Arena3.mp4*; locate it?" prompt, and an accessor that has already thrown the
distinction away cannot support that.

What the window must not do is put a modal warning in front of a user who has
not clicked anything, which is what `open_video` on a missing path produces via
`_on_failed`. `restore_last_video` returns `False` instead, leaving the window
in exactly the state it would have had with nothing remembered — status-bar
hint included, which is what the test asserts.

## What was checked by mutation

| Mutation | Caught by |
| --- | --- |
| drop `not path.is_file()` from the restore guard | `test_a_remembered_video_that_is_gone_leaves_the_window_empty` |
| never write `last_video` in `_on_opened` | `test_opening_a_video_records_it` |
| drop `setStretchFactor(1, 1)` on the top splitter | `test_the_player_and_the_tool_pane_get_equal_widths` |

The third is the one worth keeping. `setSizes([500, 500])` alone makes the
split look right at construction and wrong at every subsequent resize, with all
the extra width going to the player — a failure that only appears once the
window is maximized, which is to say on every launch after this change.

The maximize itself is not unit-tested, deliberately: a test asserting the
window-state flag restates the line that sets it. It was verified against the
real desktop instead — the window comes up `isMaximized: True` at 1920x1009
with the top splitter at `[955, 954]`.

## What changed outside the item's scope

`Preferences._store` gained a `notify` parameter so session state can be
written without emitting `changed`. The existing dedupe bug in that method
(TODO: "Three small GUI fixes" #2, where a raw stored value is compared against
a typed one) is untouched and does not affect this key: `last_video` stores a
`str` and compares against a `str`, so the guard is correct for it and wrong
only for the bool and float keys it was already wrong for.

`open_video_dialog` now starts in the remembered video's directory when that
directory still exists. It was not in the item, but a file dialog that opens on
the last-used folder is the second half of "remember the last video" and costs
four lines.
