decisions:
  - what: state is created by KernelBinding.start, once per execute
    why: two replicates previewing one node are two runs and must be two states; a kernel closing over its own would mix them and every frame would look fine
  - what: a stateless kernel comes back from start unwrapped
    why: existing kernels keep their identity, so a benchmark or equivalence test that names downsample_cpu gets the function it named
  - what: StatefulKernel is a separate protocol, not an optional third argument
    why: the two have different arity, and one union-typed decorator would let a two-argument kernel be registered with a factory and fail at the first frame
  - what: FilterSpec.stateful, and cacheable excludes it
    why: not unreproducibility — see the finding; the exclusion is on the category because nothing that derives a key can check the warmup declaration the invariance rests on
  - what: register refuses a state factory for a spec that does not declare stateful
    why: the factory and the declaration say the same thing to different readers, and disagreeing means span-dependent output written under a key that does not carry the span
  - what: background_ema declares warmup_frames=90
    why: ceil(ln 0.01 / ln 0.95), the worst case over the legal alpha range, because a static declaration cannot read a parameter
  - what: the kernel is written as in-place out= writes over three reused buffers
    why: 20.6 ms/frame against the readable form's 40.6 at 1080p — 145 frames inside full_preview_render rather than 74
  - what: ParamsBase.spec() added
    why: the __filter_spec__ narrowing dance was being written by hand in the decorators, the registry, and every test, each with its own message

  - what: warmup_frames > 0 implying stateful, enforced in __post_init__
    why: warmup means "my first N outputs are untrustworthy", and a WINDOWED filter has those without keeping kernel state
  - what: caching a stateful node on the strength of its declared warmup
    why: correct for background_ema and unverifiable in general — see the finding
  - what: cv2.accumulateWeighted for the model update

# A kernel that can remember

## What was checked by mutation

Two deliberate breakages, both caught:

`settle_frames(1.0)` raised `ValueError: math domain error` — `log(1 - alpha)`
is `log(0)` at the legal upper bound. Found by
`test_the_declared_warmup_is_the_worst_case_over_the_legal_alpha_range`, which
was written to pin the relationship between the `Field` bound and
`warmup_frames` and caught an unrelated real bug on the way. Fixed by answering
1, which is the true settle time rather than a special case.

The `_narrow` float path was originally `astype(dtype, copy=False)`. On float32
input with `emit=background` that returns `state.model` itself, so the next
frame rewrites the frame already handed to the caller.
`test_an_emitted_frame_is_not_a_view_of_the_state` fails on it; nothing else
would, because every other dtype copies as a side effect of converting.

## Where the reasoning changed mid-item

The cache exclusion was written first with the wrong justification: that a
stateful filter's output at a frame depends on where the run began, so two spans
sharing a frame disagree. The test written to demonstrate that disagreement
found bit-identical output, and the reason is `warmup_frames` — a correctly
declared warmup is exactly the guarantee that the dependence has decayed below
the filter's epsilon before anything is yielded, and the clamp at frame 0 covers
the remaining case.

So the rule stands and its reason does not. It is now on the *category*: a
filter declaring `warmup_frames=0` over a running sum is indistinguishable to
`Dag.node_keys` from one declaring 90 over a settled EMA, and both are in
`test_stateful_execution.py` making that concrete from opposite sides. The full
argument is
`docs/findings/2026.07.26-stateful-output-is-not-keyed-by-what-it-is.md`, and
the docstrings in `filter_base.py`, `executor.py`, `background_ema.py`, and
`background_ema.md` were corrected to match it rather than left carrying the
first version.

## What this filter costs, said plainly

10 ms per megapixel is the most expensive thing per pixel in this repo — 30x
`downsample`, and 20.6 ms a frame at 1080p. A ten-second clip at 30 fps is six
seconds of compute, twice `full_preview_render`, before anything downstream
runs. It does not cache, so a re-run pays it again.

That is not a defect to fix later; it is what a background model costs, and the
answer is already written down in `downsample.md` — put a downsample in front
and the cost falls with the square of the factor. What it does change is
`docs/LATER.md`'s GPU entry, whose arithmetic previously said a PCIe round trip
costs more than any kernel we have. Against this one it is 5% of the work. The
entry was not promoted — its trigger is a *measured* budget miss and no
in-pipeline budget can be missed until the preview exists — but the answer to
"would GPU pay?" has flipped from "provably not" to "probably, go measure".

## What changed outside the item's scope

`ParamsBase.spec()` replaces the `__filter_spec__ is None` narrowing that
`kernel`, `stateful_kernel`, `KernelRegistry`, and four test modules were each
doing by hand with their own message.

`KernelRegistry` now stores a `KernelBinding` per triple rather than a bare
callable, so the state factory travels with the kernel it belongs to instead of
in a parallel dict keyed the same way.

## What was deliberately not done

`warmup_frames > 0` does not imply `stateful`, and there is no check for it. It
is tempting — this item exists because the lead-in was being decoded on behalf
of state the protocol could not hold — but the declaration means "my first N
outputs are untrustworthy", and a `WINDOWED` filter will have exactly that
property without keeping any kernel state. Adding the implication now would have
to be removed the day the second shape lands.
