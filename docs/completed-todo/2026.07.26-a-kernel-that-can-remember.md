# ---- the load-bearing part ------------------------------------------------
decisions:
  - what: state is created by KernelBinding.start, once per execute
    why: two replicates previewing one node are two runs and must be two states; a kernel closing over its own would mix them and every frame would look fine
  - what: a stateless kernel comes back from start unwrapped
    why: existing kernels keep their identity, so a benchmark or equivalence test that names downsample_cpu gets the function it named
  - what: StatefulKernel is a separate protocol, not an optional third argument
    why: the two have different arity, and one union-typed decorator would let a two-argument kernel be registered with a factory and fail at the first frame
  - what: FilterSpec.stateful, and cacheable excludes it
    why: not unreproducibility — see the finding; the exclusion is on the category because nothing that derives a key can check the warmup declaration the invariance rests on
  - what: register refuses a state factory for a spec that does not declare stateful
    why: the factory and the declaration say the same thing to different readers, and disagreeing means span-dependent output written under a key that does not carry the span
  - what: background_ema declares warmup_frames=90
    why: ceil(ln 0.01 / ln 0.95), the worst case over the legal alpha range, because a static declaration cannot read a parameter
  - what: the kernel is written as in-place out= writes over three reused buffers
    why: 20.6 ms/frame against the readable form's 40.6 at 1080p — 145 frames inside full_preview_render rather than 74
  - what: ParamsBase.spec() added
    why: the __filter_spec__ narrowing dance was being written by hand in the decorators, the registry, and every test, each with its own message

rejected:
  - what: warmup_frames > 0 implying stateful, enforced in __post_init__
    why: warmup means "my first N outputs are untrustworthy", and a WINDOWED filter has those without keeping kernel state
  - what: caching a stateful node on the strength of its declared warmup
    why: correct for background_ema and unverifiable in general — see the finding
  - what: cv2.accumulateWeighted for the model update
    why: 19.4 ms/frame against the numpy in-place 20.6, and it is dtype-restricted where this handles all four declared dtypes in one path

measurements:
  source: 1080p BGR uint8 synthetic, in-process; downsample measured alongside for scale
  results:
    - background_ema foreground, 1080p: 20.6 ms/frame (9.9 ms/MP)
    - background_ema background, 1080p: 17.9 ms/frame (8.7 ms/MP)
    - the allocating formulation of the same arithmetic: 40.6 ms/frame
    - downsample anti-aliased, same frames: 0.32 ms/MP (declared 0.35)
