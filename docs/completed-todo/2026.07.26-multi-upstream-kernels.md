# ---- the load-bearing part ------------------------------------------------
decisions:
  - what: "`Edge.port` defaults to `\"in\"`, and `SCHEMA_VERSION` went to 2"
    why: >
      the default is the migration — every pre-port edge fed the one input a
      single-input filter has, so version-1 documents load unchanged; the bump
      exists because every save now writes `port` on every edge, and a v1
      build's `extra="forbid"` would report that as a stray field where the
      version check gives the designed message
  - what: "`HASH_VERSION` went to 2: the upstream fold is sorted `[port, key]` pairs"
    why: >
      a sorted list of bare keys cannot tell `a - b` from `b - a` — same two
      upstream keys, different computation — and that conflation is the silent
      direction of the asymmetry rule; sorting the pairs keeps edge-declaration
      order out of the key exactly as before
  - what: "`FilterSpec.accepts` may be a mapping of port name to `StreamSpec`; bare spec means `{\"in\": spec}`"
    why: >
      every existing filter keeps its declaration unchanged; `input_ports` does
      the normalization once and the executor picks the calling convention by
      its length, never by inspecting the callable
  - what: which shape a kernel is is enforced at import, not at the first frame
    why: >
      "@kernel on a multi-port spec" and "@merging_kernel on a single-port
      spec" both raise in the decorator, mirroring how `stateful_kernel` and
      `stateful=True` already police each other
  - what: a merging filter cannot be a root, and one port takes exactly one edge
    why: >
      the source is one stream, so which port would receive it is a guess
      `dag.py` is not entitled to make; one-producer-per-port is structural on
      `Pipeline` (it subsumes the old duplicate-edge check), while
      unknown/unfilled ports are `dag.py`'s `PortWiringError`, since only the
      resolved spec knows the port set
  - what: the executor gained no alignment machinery
    why: >
      the per-index loop computes every node for a source index before moving
      to the next, so a merge's upstream outputs for that index are already in
      `outputs` by topological order, whatever the branches' warmups; the merge
      fixture asserts equal indices on every call and a branch-of-unequal-warmup
      test pins it
  - what: "`plan.py` needed no change"
    why: >
      the TODO item priced "lead-in becoming a backward max over all upstreams"
      — `_lead_in` already was one, via the `downstreams` walk; the property
      test now generates multi-upstream graphs (arity-matched specs, ports
      `p0..pk`), so the walk-equals-paths claim finally covers merges

rejected:
  - what: positional ports (first edge is first input)
    why: edge-declaration order in YAML would become semantic, and reordering a list would silently swap a subtraction
  - what: a stateful merging kernel protocol
    why: nothing needs one; the decorator refuses the pairing with a message saying the filter that needs it brings its signature
  - what: suppressing the default `port` on save so v1 builds could read v2 documents
    why: only port-free documents would survive the trip anyway, and a multi-port one would then fail on a v1 build with a stray-field parse error instead of the version message

# Multi-upstream kernels

The item G of REFINED-VISION's temporal section gated on: every kind-amplifier
worth building is a combination of channels, and the executor refused any node
with two upstreams. What it turned out to cost: one field on `Edge`, a union on
`FilterSpec.accepts`, one new protocol, two wiring checks, and a two-line change
to the key fold. What it deliberately did not touch: `emits` stays one stream
per node — output ports wait for the filter that needs them — and `WINDOWED` /
`rate_changing` stay refused at run time.

**What was checked by mutation.** Reverting the key fold to
`sorted(upstream.values())` — the exact pre-port derivation modulo the version
seed — fails three tests, each at its own layer:
`test_which_port_a_stream_arrives_on_is_part_of_the_computation` (the digest),
`test_swapping_a_merges_ports_moves_its_key_and_only_its_key` (the walk), and
`test_a_merging_node_gets_a_frame_per_port_and_the_ports_mean_something` (plan
keys end to end).

**A degenerate case worth remembering.** The first draft of the swap test wired
`b` and `c` as *identical* blurs of one upstream, and the swapped wiring keyed
the same — correctly. Two byte-identical computations share a key by design, so
swapping the ports of two equal keys genuinely is the same computation. Port
identity separates computations, not node ids. The test now gives the branches
different radii and says so in a comment, because the next person to write a
port test will reach for the same degenerate fixture.

**Outside the item's scope.** `_run_node`'s index check now compares against
the loop's index rather than `incoming.index` (a merge has no single incoming
frame), which quietly strengthens it: for a merging node it is also the
assertion that its inputs were aligned. `register_filter`'s `accepts` parameter
type widened to match the spec's. `tests/property/test_warmup.py`'s generator
registers one filter per `(warmup, rate, arity)` triple and speaks a uniform
`p<i>` port vocabulary — arity 1 included — so that a single-parent node's edge
never has to guess whether its filter's port is named `in`.
