# ---- the load-bearing part ------------------------------------------------
decisions:
  - what: N whole `VideoReader.read` calls in parallel, not a parallel convert
    why: OpenCV's `retrieve()` converts on the calling thread and exposes no way to reach the conversion alone
  - what: every frame stays byte-identical, so `decoder_identity()` is untouched
    why: it is the criterion the route was chosen on — the three faster routes all need a cache generation
  - what: interleaved claims from a sliding window, not contiguous chunks
    why: the consumer reads in order, so chunking would hold the span in memory instead of a window
  - what: an epoch counter, and a jump drops what was in flight
    why: hygiene, not correctness — a stale frame for index i is byte-identical to a fresh one, so this bounds lingering entries and stale failures and nothing more
  - what: opt-in rather than what `VideoReader` became
    why: a scrubbing GUI jumps constantly and would pay the abandoned-read cost on every drag
  - what: INFERRED_WORKER_CAP is 4
    why: measured, not guessed — throughput peaks there and is worse than sequential at 12 on a 32-core machine
  - what: '`--workers` on both commands, one `WORKERS_OPTION`, nothing on `Project`'
    why: VISION step 6 puts machine capability on the command line; a `threads:` field would make one machine's allocation part of another machine's document
  - what: '`frame_source()` returns a `PrefetchFrameSource` even at one worker'
    why: '`--workers 1` costs 3%, so it can be the same code path with an empty window rather than a second reader class'

rejected:
  - what: reading SLURM_CPUS_PER_TASK and a SIEVE_DECODE_WORKERS override
    why: built, then cut — see the body. `available_cpus` already covers the usual SLURM case, a SLURM-only variable reads as scheduler coverage while ignoring PBS/LSF/SGE, and an override duplicates `--workers`
  - what: a byte-budget knob deriving `lookahead` from frame size
    why: the same over-building impulse the env vars were; the memory arithmetic is documented and one knob is enough until something measures a problem
  - what: chasing the remaining 6x here
    why: it needs the frame to get smaller, which changes what a pixel is — a contract decision, not a performance one

# Read frames faster than one at a time

## The HPC exposure was asked for, built, and then mostly cut

The item asked for the worker count to be "exposable for the HPC down the line",
and the first version of `resolve_workers` consulted `SIEVE_DECODE_WORKERS` and
`SLURM_CPUS_PER_TASK` with a documented precedence and four tests pinning it.
Three of those four tests existed only to check rules that existed only to be
checked, which is the smell that prompted the reassessment.

What survives is the part that is not a guess: the count is a **parameter** rather
than a constant, **one** function decides it when nobody said, and it arrives as a
**command-line option** and appears nowhere in the artifact. What went is the
environment layer, for three reasons that are not line count:

- `available_cpus` asks `sched_getaffinity`, which under the usual affinity and
  cgroup plugins already *is* a job step's allocation — so the SLURM variable is
  largely redundant with the answer that gets computed anyway.
- A SLURM-only special case reads as scheduler coverage while doing nothing for
  PBS (`PBS_NP`), LSF (`LSB_DJOB_NUMPROC`), or SGE (`NSLOTS`). Dead code that
  looks alive is worse than absent code.
- `SIEVE_DECODE_WORKERS` is a second way to say what `--workers` says. A batch
  script writing `--workers $SLURM_CPUS_PER_TASK` puts the number in the file
  someone debugging a slow job will open, which is also what VISION step 6 asks
  for.

`pipeline_model.py` had already decided this — "machine capability reaches the run
as command-line options" — so the argument is from what the repo committed to
rather than from taste.

## The estimate was 9x and the measurement is 1.61x

The finding this item came from concluded that roughly 9x was available without
changing a pixel, on the strength of ffmpeg doing the identical decode and convert
at 2.95 ms/frame against `VideoReader`'s 24.5. That was an estimate and it was
wrong, and the way it was wrong is worth keeping: it assumed the only wall was the
single-threaded conversion, so N conversions would be N times the throughput.

The curve says otherwise — 15.25 ms/frame at four workers, 20.45 at eight, 28.49
at twelve, which is worse than one thread on a machine with thirty-two cores. The
optimum leaves twenty-eight cores idle, so the limit is not the CPU. It is a
47.6 MB BGR array allocated and freed for every frame, and adding workers adds
concurrent large allocations whose page faults serialise. ffmpeg's `AVFrame` pool
recycles buffers and never pays it.

So the module ships at 1.61x and the finding says plainly that the remaining gap
belongs to routes where the frame gets smaller. That is a worse result than the
item was written expecting and a better-understood one.

## What was checked by mutation, including the two checks that failed

Three mutations were planned and only one behaved as claimed. The other two are
the useful part of this section, because in both cases the defect was in the test
or in the claim rather than in the code.

**A worker reading `index + 1` instead of `index`** fails three tests, led by
`test_every_frame_is_byte_identical_to_the_sequential_reader`. That is the one
that matters: an off-by-one reader writes a wrong frame under a right key and
every store keeps it forever.

**Deleting the epoch comparison in `_publish` fails nothing, and no test can be
written that it would fail.** This was claimed as a correctness mechanism, in the
module docstring and in a test name, on the analogy of `gui/coalescer.py`'s
`generation` stamp. The analogy is wrong: the coalescer's stamp prevents a frame
decoded against a closed video being painted into the next one, whereas here a
frame for index `i` is byte-identical whichever position asked for it — same
reader, same index, same bytes. So a stale frame cannot be a wrong frame. The
epoch counter earns its place as hygiene (up to `workers` abandoned frames do not
linger, a stale failure is not raised at a caller who has moved on) and the two
docstrings now say that instead. The test was renamed to claim what it does pin,
which is that a jump answers with the frame requested rather than with a
neighbour.

**The window-bound test took three attempts, and the first two were wrong in
opposite directions.**

1. It read one frame, spun until `_done` reached the bound, and counted. It passed
   with the bound deleted, because it stopped looking at exactly the moment the
   window reached its limit.
2. Rewritten as an invariant asserted after every read, plus a non-vacuity check
   that the window was observed exactly full. That check is a race — with two
   workers, `claim - want` touches 3 only between one worker finishing and the
   consumer taking that frame — so it failed against *correct* code.
3. What works: let the producer outrun the consumer, then wait for quiescence.
   The pool advances its claim once per completed read, so a consumer reading as
   fast as the workers produce keeps the window shallow whether a bound exists or
   not — which is why attempt 1 saw nothing. The real consumer runs filters per
   frame and does outrun nothing. Reading one frame, then polling until the claim
   stops moving, makes the assertion exact rather than probabilistic: at
   quiescence `claim - want` is `lookahead` precisely. Verified stable over five
   consecutive runs, and it now fails both an unbounded window and a window that
   never reads ahead.

## What changed outside the item's scope

`decode/reader.py`'s module docstring described the reference footage as H.264. It
is mpeg4 Simple Profile at 183 Mbps, which is why hardware acceleration never
engaged, and the docstring now says so and cites the finding.

`tests/integration/test_cli_run.py::test_a_dry_run_never_opens_the_video`
monkeypatched `sieve.cli.run_cmd.VideoReader`, which that module no longer imports.
It now patches both doors into the container — `run_cmd.frame_source` and
`common.VideoReader` — because `span_for` moving to `cli/common.py` created the
second one, and patching only the first would have left the dry-run path able to
open a video with the test still green.
