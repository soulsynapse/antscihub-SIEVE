# The representative-clip preview

## The item asked for coalescing in this module, and it belongs one layer up

`docs/TODO.md` said `gui/coalescer.py` was extracted Qt-free "so preview
inherits the two slots, the rank rule, and the source stamp rather than
reimplementing them". It cannot inherit them by importing them: the coalescer
lives in `sieve.gui`, which the `.importlinter` layers contract puts *above*
`sieve.pipeline`. That is not an accident of where the file was put — it is the
right place. Coalescing exists because a human is dragging something, and
`sieve preview` renders once and has nothing to discard.

So the extraction is still load-bearing and the beneficiary is the GUI's preview
panel rather than this module: it will coalesce *renders* the way `player.py`
coalesces *frame requests*, against the same two slots and the same rank rule,
and `RequestCoalescer` is Qt-free so that panel can be tested by feeding it
calls. What `pipeline/preview.py` owes that arrangement is to be a plain
synchronous call holding no state of its own beyond the store, which it is:
`render_window` and `render_frame` can be run on a worker thread, and the answer
to a render nobody would have seen can be dropped without the session knowing.

The one thing not carried over is the source stamp. A `generation` counter here
would be guarding against a frame arriving for footage that has been closed,
and the session holds the reader and the source identity for its whole life —
a new asset is a new session.

## What was checked by mutation

Three deliberate breakages, each killed by exactly the test written for it:

- **Clearing the store in `set_window`** — the obvious implementation, and
  invisible in the output — fails only
  `test_moving_the_window_keeps_the_frames_the_two_spans_share`.
- **A `MemoryFrameStore` per render**, which is what a GUI loop rebuilding its
  cache when the graph changes would amount to, fails
  `test_an_edit_below_the_root_recomputes_the_suffix_and_decodes_nothing`, the
  window test, and both CLI reuse tests — four tests, which is the right blast
  radius for the claim the module exists for.
- **A one-frame render publishing `full_preview_render` too** fails only
  `test_the_first_frame_is_timed_inside_the_whole_render`.

## What changed outside the item's scope

`cli/run_cmd.py` lost `_load`, `_parse_span`, `_span`, and `_refuse` to
`cli/common.py`, unchanged apart from losing their underscores. Its tests pass
untouched, including `test_a_dry_run_never_opens_the_video`, which monkeypatches
`sieve.cli.run_cmd.VideoReader` — still the name the run path uses, and the span
fallback that moved refuses before it reaches a container on a dry run.

The timings report was going to print `Budget.label`, and did, until running the
command in a real Windows terminal raised `UnicodeEncodeError` on the arrow in
"Scrub/seek → frame repaint". The CliRunner-based tests could not have caught it
— click captures to a UTF-8 buffer — so `test_a_repeated_render_reuses_the_store`
now asserts `result.output.isascii()`, which is the property that actually
travels.

## What the measurement changed about the item

The item claimed the budgets "are what say whether it works". They say something
more specific than expected: `full_preview_render`'s 3 s ceiling is met by the
store and not by the filters, and on the reference footage a *cold* 5–10 s window
cannot meet it at any filter cost — 3 s buys about 137 decoded frames and a
10-second window is 600. The finding is `open` rather than `closed` because the
consequence, decoding at the ROI or reading a materialized crop, is
`materialize.py`'s and `reader.py`'s rather than this module's. Nothing in
`budgets.py` was moved on the strength of one probe on one machine.
