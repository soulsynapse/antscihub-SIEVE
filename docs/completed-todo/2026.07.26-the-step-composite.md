# ---- the load-bearing part ------------------------------------------------
decisions:
  - what: the three modes collapsed to one composite with a selected step
    why: raw video is the first step's composite at full opacity, full state is
      the tail selected; only "contribution of this step" carries information
      the scalar plots cannot (argued in the TODO item, which was the design)
  - what: the target is the deepest node-backed ok step at or before the selection
    why: tab-side steps (morlet, windowed count) have no rendered frame; the
      caption says "(deepest rendered)" so the fallback is visible, not silent
  - what: the composite pair rides window renders and otherwise uses request_frame,
      suppressed while a window render is outstanding
    why: the runner holds one pending slot; a playhead refresh stream would
      displace the graphs' render from it and the series would never arrive
  - what: composite refreshes neither clear the HUD nor feed it costs
    why: a store-warm single frame is near-zero cost — begin() per playhead move
      would empty the window series and add_cost would overwrite real render
      costs with cache-hit times
  - what: block-grid overlays colorize with the heat panel's warm stop, scaled by
      the window series' 99.5th percentile, painted nearest-neighbour
    why: same colour = same quantity across panels; fixed scale keeps cell
      visibility meaning one thing at every playhead; smoothing would invent
      gradients between blocks the data does not contain
  - what: the first step's input is the player frame cropped to the replicate ROI
    why: the graph runs over the crop when a replicate exists, and an overlay on
      footage the graph never saw would misalign by construction

rejected:
  - what: napari (and any N-layer viewer) for the overlay
    why: the collapsed requirement is two layers and one slider — QPainter;
      closes the deferred napari question for good (Deferred decisions)
  - what: retaining per-frame node outputs over the window for playhead scrubs
    why: two full-resolution nodes over a 300-frame window is on the order of a
      gigabyte; a store-warm request_frame is milliseconds
