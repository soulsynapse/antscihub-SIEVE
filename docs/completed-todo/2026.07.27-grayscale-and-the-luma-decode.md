summary: >
  A graph that declares no chroma-reading filter is now decoded from the Y plane
  rather than a BGR conversion of it — 19.4 to 8.0 ms per frame, and the render
  of a working window is 1.88x faster.

decisions:
  - what: the decode format is derived from the graph, never chosen by a user
    why: >
      `Dag.needs_chroma` asks whether any filter excludes GRAY from `accepts`.
      A flag would let someone pick a format the cache key says was not used; a
      hard-coded "always luma" would make a colour filter unwritable, because
      the frame would already be single-channel before any node saw it. Derived,
      it is luma for every graph on today's shelf and flips back on its own the
      day one reads hue.
  - what: three version constants moved, and they are not redundant
    why: >
      DECODE_POLICY_VERSION 1 to 2 says this build decodes differently;
      `source_key`'s new format field says which format a given run used, so a
      future colour graph cannot collide with a luma one; HASH_VERSION 2 to 3 is
      the case that constant's own docstring names, a field added to a key. They
      invalidate the same entries once and each records a distinct fact.
  - what: over-include on the chroma question — any node, not just the roots
    why: >
      Only roots touch the source frame, but channel layout propagates and a
      downstream demand for colour is evidence the chain was meant to carry it.
      `cache_key.py`'s asymmetry rule decides it — an input wrongly included is a
      slower correct answer, an input wrongly omitted is a wrong one served from
      cache and never noticed.
  - what: an entry point installs the stderr filter, never `VideoReader`
    why: >
      Redirecting fd 2 is process-global. A reader doing it on construction
      would do it inside pytest, where fd 2 belongs to the capture fixture —
      which is not hypothetical: putting it in the Typer callback broke
      `test_cli_preview` on the first run, because `CliRunner` drives the app
      in-process.

rejected:
  - what: a `grayscale` filter in spatial prep with the 2x shown on its card
    why: >
      The first shape of this item, and it survived until the equivalence was
      measured. At 0.004 sd on the block series there is no tradeoff to put in
      front of anyone, and an option whose two settings are indistinguishable in
      the answer is a decision handed to a user with no basis to make it.
  - what: cv2.utils.logging.setLogLevel, OPENCV_LOG_LEVEL, another backend
    why: >
      All three measured, all three fail on this build — the log level does not
      reach the FFmpeg backend, the environment variable does not reach the
      plugin from inside the process (Python's putenv writes a different block,
      and SetEnvironmentVariableW does not help either), and MSMF and DSHOW do
      not open files at all. Filtering the stream by line was what was left, and
      it drops one line rather than muting stderr.
  - what: reusing a preallocated BGR buffer for the reads
    why: >
      Measured 16.9 ms against 22.0 on the colour path, so it works — but 14.0 ms
      on the luma path, worse than the 11.0 ms of allocating fresh. Two
      mechanisms for one problem, where the cheaper one is also the simpler.
