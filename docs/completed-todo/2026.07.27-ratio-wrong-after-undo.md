# ---- the load-bearing part ------------------------------------------------
decisions:
  - what: the filter tab subscribes to replicate_changed, index-filtered to
      the selected row
    why: it is the only signal a ROI write emits — `apply_replace` emits
      nothing else, and neither `selection_changed` nor `tuning_changed` fires
      — so a tab that renders the selected arena and does not listen for it
      renders a geometry the document no longer holds; the index test is what
      keeps `set_all_to_size`, which rewrites every row, from throwing one
      full window render per replicate
  - what: a replicate edit invalidates exactly as a selection change does —
      `_refresh_from_document` then `resubmit`
    why: "`Replicate` carries the pinned overrides as well as the ROI, so the
      handler cannot assume only geometry moved; re-resolving first is the
      same ordering `_on_selection_changed` documents, and it keeps the render
      on the runner's latest-wins window path rather than a single frame"
  - what: the `select` early-return on the current row is kept, unchanged
    why: re-emitting would turn `select` into a refresh primitive that every
      caller inherits, against its own docstring; the guard was only
      load-bearing while the missing subscription existed, because the gesture
      that papered over the bug was clicking the row already selected

  - what: loosening the guard so a no-op select re-renders

      leaves the actual hole open for every other path into the tab — a typed
      crop, a drag, a future selected-crop view; the item named this and it

# Ratio wrong after undo

Two defects were named in the item; only one turned out to need a change. The
missing `replicate_changed` subscription was real and is now wired. The
`select` guard is not a defect — it is the first one's symptom seen from the
gesture side, and once the tab hears about the edit itself, clicking the
already-selected row has nothing left to refresh. Its docstring now says so,
so the next reader does not re-argue it.

**What was checked by mutation.** Removing the `replicate_changed.connect`
line fails two tests for distinct reasons:
`test_undoing_a_crop_edit_resubmits_the_selected_arena` (the tab resubmits
`SECOND_BOX` after the undo restored `FIRST_BOX`) and
`test_selecting_the_already_selected_row_leaves_the_tab_consistent` (what was
last rendered does not match the document at the moment of the re-select).
Dropping the index test in `_on_replicate_changed` fails
`test_an_edit_to_an_unselected_arena_does_not_resubmit`.

**Still unlistened-for.** `replicate_changed` now has four subscribers; the
other three (`crop_tools.py`, `replicate_tab.py`, `replicate_table.py`) are
all on the replicate tab. Nothing yet consumes `replicate_added` or
`structure_changed` on the filter side, which is correct while the tab renders
exactly one arena — a selected-crop view or a multi-arena composite would
change that, and the **Stamp as the default gesture** item is where it lands.
