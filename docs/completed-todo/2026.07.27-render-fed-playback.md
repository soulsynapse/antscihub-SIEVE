# Render-fed playback, and the frontier it loops at

The defect this answers is rule 6's mirror clause: a pane that froze solid
while a window render filled read as a crashed application, when the system
was working perfectly. The mechanism is the decode-bandwidth finding
(`docs/findings/2026.07.27-decode-is-a-bandwidth-wall-shared-by-two-consumers.md`):
two readers over one file contend on the one scarce resource, speeding either
up only starves the other, and removing a consumer is the only thing that
works. The render's frames were discarded, not unavailable — `execute`
decoded into a local and dropped it — so the fix is to keep them and play
them.

## How it landed, where that differs from the item as written

- The item's Shape had `FrameResult` carry the *cropped* `source` local. What
  landed carries the frame **before** the crop, under the same field name:
  the replicate crop is what the graph consumes, but the sharer is a
  full-frame viewport, and a crop cannot be undone. The cost argument is
  unchanged.
- The item fixed the ring bound as "a named constant beside
  `ProxyFrameCache`'s bound with a comment saying the resource ledger owns
  the real answer". The ledger landed first, so the bound went straight in as
  a `MemoryShare` row (`RENDER_RING_SHARE`, 256 MB floor) — the stated
  successor arrived before the placeholder was ever written.
- The "follow the render" labelled mode the item suggested building first was
  not built. The luma finding had already inverted the premise — the render
  (~88 fps) outruns playback (59.94 fps) — so the ring path *is* the simple
  version, and the frontier fold (`timeline_model.feed_bounds`) is the edge
  behaviour at render start and after a backward seek, exactly as the item's
  final section predicted.
- The player's ring consult is gated on the viewport being gray, which also
  scopes the feed to the filter tab (the only place the pane goes gray, as of
  the gray-toggle item's tab scoping). The replicate tab's colour pane is
  untouched by construction rather than by a second mechanism.

The render's frontier is not the settled frontier: "the last frame that
exists" (`RenderFrameRing.frontier`) against "the last frame whose value will
not change" (`DetectorResult.settled`). The player folds at the first only,
and only while a window render is filling.
