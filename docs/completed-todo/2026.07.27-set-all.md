# Set all

## Why this item existed at all

It was not on `TODO.md`. `TODO.md` claimed REFINED-VISION's **Replicates**
section was "built as far as it can be", with only the status table's two
columns outstanding and correctly deferred. An audit of the section against the
code, sentence by sentence, found that claim was wrong in two places: the "set
all" in line 39 was implemented nowhere and deferred nowhere, and so was line
41's click-through navigation on the filter tab.

That is worth recording as a failure mode rather than as a one-off. Both gaps
are in sentences whose *other* clauses had landed — "set all" sits in a sentence
mostly about accepting a replicate, which works, and line 41 sits inside the
Replicates section while describing the filter tab. A section gets marked
complete by checking its headline claims, and a subordinate clause is where an
unbuilt requirement hides. The fix that generalizes is the audit itself: read
the vision section against the code by sentence, not by feature.

## Why a rack of unequal boxes is a defect and not an untidiness

The operation looks like a convenience — twelve boxes, make them match — and the
argument for building it properly rather than approximately is that it is not.

REFINED-VISION **D** is the reason. At a fixed per-block threshold, the expected
number of false positives scales with blocks times frames, so two replicates
whose boxes differ in size run the *same* settings at different false-positive
rates. The fractional count band (`core/detection.count_band_to_counts`) already
protects against the naive version of this — a fraction of the region's blocks
means the same thing at any grid size — but it does not and cannot protect
against the number of tests changing. A rack cut by hand, where the arenas are
physically identical and the boxes are not, therefore produces a per-replicate
difference in detection rate that has no biological referent and reads exactly
like one.

So the thing being built is not "tidy up the table". It is the operation that
makes one threshold mean one thing across a rack.

## The frame edge is the whole correctness question

Everything else here is bookkeeping. The one place this operation can be
silently wrong is a box near the edge of the frame.

`ROI` already had `clamped_to`, which *trims*, and `VideoView._placed`, which
*slides*. Reaching for the first from a batch resize compiles, passes anything
that does not test an edge case, and returns a rack that is uniform except for
the one box against the right edge — which came back narrower, looks identical
on screen, and is now the replicate with a different block count. That is the
exact failure the user pressed the button to prevent, produced by the button.

`_placed` already carried the argument for sliding in its docstring, which is
why the fix was to move the rule rather than to write a second one: it is now
`ROI.placed_in`, in typed numbers, with `_placed` a one-line delegation and
`ROI.resized_in` — centre-preserving — layered on top for this operation. Two
callers, one rule.

There is a residual asymmetry worth naming rather than hiding: a box slid off
the edge no longer sits where the user put it. That is correct — the extent is
what the button was asked to make uniform and the position is what it was not —
but it means a rack whose arenas genuinely run to the frame edge will have its
edge boxes moved inward. The alternative is refusing the operation for such a
rack, which is worse: the user's remedy is then to re-cut by hand, which is the
non-uniformity they started with.

## What was checked by mutation

Four deliberate breakages, applied and run rather than reasoned about. Two of
them behaved differently from the prediction written before running them, which
is the reason this section is worth the minutes it costs.

- **`resized_in` trimming (`clamped_to`) instead of sliding (`placed_in`)** —
  three failures, not the one predicted:
  `test_a_box_at_the_frame_edge_slides_instead_of_shrinking` (as designed),
  `test_every_replicate_takes_the_stamp_size` (the edge box is 160 wide, so the
  rack is not uniform), and `test_a_rack_already_at_that_size_records_no_history`.
  The third is the informative one. A trimmed box is never *at* the requested
  size, so every press moves it again and the operation has no fixed point — the
  no-op guard can never engage. That is a second, independent symptom of the
  same defect, and it says something the edge test does not: trimming makes this
  button non-idempotent.
- **`resized_in` keeping `x`/`y` instead of recentring** — exactly one failure,
  `test_each_box_is_resized_about_its_own_centre`, as predicted. The size and
  undo tests pass, which is precisely why that test has to exist separately.
- **`set_all_to_size` looping `set_roi` per row instead of pushing one
  `SetReplicateROIs`** — exactly one failure,
  `test_the_whole_rack_is_one_undo_step`, as predicted. Every other assertion in
  the class passes, sizes included, which is what makes the loop such a
  plausible implementation to write.
- **`set_all_requested` left unconnected in `replicate_tab._connect`** — three
  failures, and the two that *pass* are the point. Nothing happens at all, so
  the centres are trivially unchanged and no history is trivially recorded:
  `test_each_box_is_resized_about_its_own_centre` and
  `test_a_rack_already_at_that_size_records_no_history` both pass vacuously
  against a button that does nothing. A test suite of only those two would
  certify a dead button. This is also why the tests press the button rather than
  calling `document.set_all_to_size` — an unwired signal is entirely invisible
  to a document-level test.

## What changed outside the item's scope

`VideoView._placed` lost its body to `ROI.placed_in`. The behaviour is
unchanged — `tests/gui/test_video_view.py`'s stamp-placement tests pass
untouched — but the docstring that carried the slide-versus-trim argument moved
with the code, so a reader looking for it in `video_view.py` now finds a pointer
instead of the argument.

`docs/LATER.md` gained **Click-through navigation on the filter tab**, the other
half of what the audit found. It is deferred rather than built, and the entry
argues that binding those two clicks to the *chain* — which is expressible today
— is the wrong thing rather than a partial thing, because it would spend a
gesture that has an output-axis meaning on the replicate tab already.
