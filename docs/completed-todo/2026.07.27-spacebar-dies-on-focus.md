summary: >
  Typing controls now claim the keyboard by name and release it at a commit, so
  clicking a crop-tools field no longer disables playback for the rest of the
  session and a half-typed number no longer reaches the document one digit at a
  time.

decisions:
  - what: >
      The guard is a set of named sources (`gui/editing_sources.py`), not a
      counter and not a boolean. Cell editors are named by the delegate that
      opened them, crop fields by their object name.
    why: >
      A counter and a boolean both fail on the same input — an unbalanced
      close, which is exactly what a widget hidden mid-edit produces. A set
      makes both directions idempotent, so a source that disappears is dropped
      by identity without anyone tracking how many opens it owned. The stuck
      state stops being reachable rather than being recovered from.
  - what: >
      Focus stops being a suppression source; the number fields suppress from
      their first keystroke to their commit instead.
    why: >
      Decided in the item on 2026-07-27. A spin box holding the keyboard is not
      an edit, and treating it as one is what made "click around, lose the
      spacebar" reachable. An edit bounded by a commit has a defined exit —
      Enter, Esc, or leaving the field — so the item's demand for a known-good
      recovery point is met by construction rather than by a rescue hook.
  - what: >
      `setKeyboardTracking(False)` on the number fields, so the value applies at
      the same boundary the keyboard claim ends at.
    why: >
      Qt's own name for the rule, and it makes the two halves one edge instead
      of two that could drift. Typing `15` into a field showing `100` no longer
      writes a 1-pixel region, no longer renders one, and no longer leaves a
      step on the undo stack the user never took.
  - what: >
      The drop-menu half of the same rule was split out as
      `docs/todo/menus-apply-on-selection.md` rather than built here.
    why: >
      It is not the same change wearing a different widget. `QComboBox` emits
      `activated` for keyboard navigation of a *closed* combo, so the obvious
      signal swap fixes the popup case and leaves the arrow-key case untouched;
      the real options are an event filter, a debounce, or a pending-value
      state, and choosing between them wants a measurement this item did not
      need. The item states all three with a recommendation.

rejected:
  - what: A reference count instead of a set of sources.
    why: >
      It is the item's own first suggestion and it is one bug smaller than the
      boolean, not zero. Two closes for one open sits it at -1, where it then
      swallows the next real open — and the hidden-mid-edit case produces
      exactly that. `tests/gui/test_editing_guard.py` pins the interleaving.
  - what: >
      Keeping focus-based suppression and only making the latch robust.
    why: >
      Named and rejected in the item. It preserves a behaviour nobody wants
      once it is stated out loud: a control that is merely selected is not a
      control that is being used.
  - what: >
      A rescue hook — clearing the guard on window deactivation or tab change.
    why: >
      It treats the stranded state as something to recover from rather than
      something to make unreachable, and it would have masked the real defect
      in testing while leaving it live in any session that never changed tab.
      `hideEvent` ending the edit is the same insurance scoped to the widget
      that actually knows it is going away.
