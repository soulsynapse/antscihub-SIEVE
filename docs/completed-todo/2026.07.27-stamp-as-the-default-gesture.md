# ---- the load-bearing part ------------------------------------------------
decisions:
  - what: "`VideoView` owns the crop mode; `CropToolsPanel` emits
      `mode_requested` and repaints from `set_mode`"
    why: the item offered two shapes and preferred one owner over a second
      signal, and the view is the owner because it is both the widget that
      *acts* on the mode and the only widget with cause to change it on its
      own — the panel has no way to know a drag just completed; the tab
      carries both directions of the binding so neither widget imports the
      other, which is the same shape the stamp size and the zoom readout
      already used
  - what: the round trip is stopped by making `set_mode` idempotent rather
      than by a `_refreshing` guard on the panel
    why: checking a radio button emits a request that arrives back as the mode
      it already is, so the early return ends it in one lap; a guard would add
      a second piece of state whose only job is to hide that the first one
      already works, and the numeric fields' `_refreshing` flag exists for a
      genuinely different reason (a user edit and a refresh are
      indistinguishable at `valueChanged`, which is not true of a mode)
  - what: the selection *writes* the stamp size rather than being read at
      placement time
    why: rule 6's mirror direction — the panel shows the stamp size in a field
      beside the "Set all" button that applies it to the whole rack, so a
      placement that silently preferred the selection would leave that field
      reading one number while clicks produced another; writing keeps exactly
      one stamp size, on screen, and lets a typed one stand until the
      selection actually moves
  - what: the write is hooked to `set_replicates` as well as `set_selected`
    why: the highlighted replicate changes size without the highlight
      moving, which is exactly what a handle drag is — and tuning one arena
      before stamping the other eleven is the gesture between cutting the
      first box and cutting the rack

rejected:
  - what: a third object owning the mode, with both widgets as views over it
    why: the item likened the fix to `ReplicateDocument` being the one store
      for tuning, but the analogy stops at the undo stack — a crop mode is not
      saved, not undoable, and not read by anything outside these two widgets,
      so a store for it would be a class whose entire content is one enum and
      whose only subscriber list has one entry
  - what: preferring the selection at placement time and leaving `_stamp_size`
      as the typed-or-drawn value
    why: fewer lines, and it fails rule 6 — see the third decision above
  - what: flipping to `STAMP` only when the draw was the *first* one
    why: it makes the mode depend on the replicate count, which is a rule the
      user has to be told rather than one they can see; the flip costs nothing
      to reverse because a drag draws in either mode, so there is no case
      where "always" is worse than "the first time"

# Stamp as the default gesture

Three claims from one line of the vision, in three different states, and the
item's reading of each held up against the code.

**The click-versus-drag half already worked, and now says so.** The mode is
consulted only in `_release_click` — a release that travelled is a draw
regardless — so the flip to `STAMP` changes what a *click* means and nothing
else. `test_a_drag_in_stamp_mode_still_draws` is that confirmation, and it is
what makes the flip cheap: there is no gesture the user loses and has to go
back to the radio buttons for.

**What was checked by mutation.** Four lines, four distinct failures:

- dropping `set_mode(CropMode.STAMP)` from the draw branch fails three tests,
  the mode assertion and both tests that depend on being in stamp mode;
- dropping `_take_stamp_from_selection()` from `set_selected` fails
  `test_a_click_stamps_the_highlighted_replicate_not_the_last_drawn`;
- dropping it from `set_replicates` fails
  `test_the_stamp_follows_the_selected_box_being_resized`;
- dropping `mode_changed.connect(set_mode)` in the tab fails
  `test_a_completed_draw_puts_both_widgets_in_stamp_mode` on the panel half
  alone — which is the whole point of the ownership change, since the view
  half passes.

That second mutation initially passed, and the reason is worth keeping.
`apply_insert` sets the document's selection *before* emitting
`structure_changed`, so the tab rebuilds the overlay while the *view* still
holds the previous selection — which meant the stamp briefly took the old
box's size and, in that fixture, the old box was the 200x200 one the test was
asserting. The test now pins the intermediate state (the freshly drawn box is
selected, so the stamp is 137x91) before selecting back, and fails as it
should. A test that passes for the wrong reason is worse than one that fails.

**What this does not touch.** Placement is still `ROI.placed_in` and unchanged:
a stamp at the frame edge slides rather than shrinks, which is the property
`test_a_stamp_at_the_edge_slides_rather_than_shrinks` has held since the stamp
was written and the reason "Set all" cannot reach for `clamped_to`.
