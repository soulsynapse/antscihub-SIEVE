# The graphs fill as the window renders

## What was actually wrong

`SeriesCollector` assembled the working window on the render thread and
`FilterTab._on_render_finished` turned the whole of it into a `DetectorUpdate`
in one call. Nothing was incorrect about it; it simply meant the feedback for a
long window arrived only once, at the end. The tab's entire value is the speed
of the tuning loop, and a loop whose feedback lands once per render is not one.

## Why the transform makes this harder than it looks

The obvious implementation — recompute on the growing prefix, repaint — is
wrong for a reason specific to this signal chain. The Morlet transform is not
causal. It zero-pads past the end of whatever record it is handed, so the
newest values are contaminated by padding rather than by data, and they
*change* when the next frames arrive. Recomputing naively gives a leading edge
that writhes and then settles, and worse, a detection gate that flickers on and
off as the values under the threshold move.

So the design is two frontiers rather than one. The curve is published to the
decode frontier and drawn faded past the settled one, because a provisional
value that looks provisional is honest and worth watching arrive. The gate stops
at the settled frontier, because a detection is navigation: the seeker's ticks
and the prev/next jumps consume it, and an interval that appears and then
vanishes is a worse failure than a graph that has not got there yet.

`core.wavelet.settled_frames` is the transform's frontier and
`core.detection.settled_frames` is the detection window's — a centered D window
near the cut averages frames that have not arrived. The smaller wins, and a
`final` pass overrides both, because a render that is over has no moving
frontier and its edges mean what the clip's edges mean.

## The frontier is charged against the band, not the bank

Contamination at the cut comes from the daughters actually summed, so a
detector tuned to a high band settles close to the frontier where one reaching
down to 0.5 Hz needs seconds of it. Denominating on the whole bank would have
withheld graph the transform had already finished with, every time, for every
user — and the wide-open default band is the only case that pays the worst
number.

There is an honest consequence recorded in
`tests/gui/test_filter_tab_partial.py`: a working window *shorter* than the
settling distance settles nothing at all while it fills, so its detections
appear only when the render finishes. On the 40-frame fixture at 20 fps against
a 0.5 Hz floor that is every partial pass. That is the design working. Anyone
tempted to make short windows "feel more responsive" by settling them early
would be reintroducing the retracting detections the frontier exists to prevent.

## What the padding measurement cost, and why it was worth stopping for

The no-retraction property failed its first test, at the *leading* edge — frames
0 to 26 gated on one pass and ungated on the next, which is the opposite end of
the record from anything a trailing frontier governs.

The cause was a pre-existing defect in `morlet_power`, not in this work.
`PAD_EFOLDINGS` was implicitly one, `next_fast_len` was leaving a ~56-frame zero
gap, and a 0.5 Hz wavelet needs over twice that — so a burst against one end of
the record wrapped circularly onto the other at 2.4% of full band-power scale.
The whole-clip path had it too and it was merely less visible, because it needs
strong signal near a boundary and a working window the user has positioned *on*
an event is exactly that.

The numbers are in
`docs/findings/2026.07.27-the-morlet-pad-was-one-e-folding-short.md`. The reason
it had to be fixed before `COI_SETTLE_EFOLDINGS` could be chosen at all is that
the wraparound term dominated the trailing measurement and made the error look
flat with respect to the frontier. Only once the padding was sufficient did the
real shape appear.

## Dividing the machine, and the rule that had to grow

`PREVIEW_WORKERS = 2` was justified in a comment against exactly one other
consumer, the player's decode thread. That reasoning holds for two things and
stops holding at three, and this change is the third — running `scipy.fft`,
whose default is *every core*.

Non-negotiable #5 read "don't improve pre-pipeline at cost to in-pipeline or
vice versa", which is a two-body rule with no slot for the case that actually
bites: a third consumer starving both the others. It now reads over consumers,
and the arithmetic is declared in `gui/concurrency.py` and asserted in
`tests/unit/test_concurrency.py` rather than argued in three comments. A fourth
consumer, or a raised constant, fails a test.

`core/` deliberately holds none of it and still defaults to every core. The cap
is an optional parameter, so the GUI leaves room and a cluster node does not —
capping in `core/` would have throttled precisely the runs that should saturate
a machine.

The cost is real and worth stating: fewer, slower partial passes than an
uncapped detector would manage. Since the loop is self-pacing, that shows up as
a coarser fill rather than a stall, which is the right way to pay for a scrub
that stays smooth.

## The pass counts were measured twice, and the first set was wrong

Worth recording because the failure mode is easy to repeat. `prefetch.py` had an
uncommitted edit in the working tree — `_claim < _want + 1` where the committed
code says `_want + _lookahead` — which makes `_want` the only claimable index
and so collapses N decode workers to one frame in flight, removing read-ahead
entirely. Every render taken during this work was therefore slower than the
committed code produces, and the first pass-count measurement (17 partials at
~2-frame strides) was taken against that.

Restored, the same probe gives 13-14 partials at ~3-frame strides. The loop
paces itself against the render, so the numbers moving in that direction is the
design confirming itself rather than a result changing — but the *specific*
counts are a property of the machine, the fixture and the decode path, and are
only comparable to a later measurement if that is stated.

The general lesson is the one `docs/findings/` exists for: a timing number taken
with an uncommitted change in the tree is a number about a tree nobody else has.
`git status` before measuring, not only before committing.

## What changed outside the item's scope

Four GUI test fixtures gained a `shutdown()`. `FilterTab` now owns a `QThread`
and therefore carries the same obligation `VideoPlayer` and `PreviewRunner`
already did; without it every tab built in a test leaked a thread and the suite
wedged a few modules later. That failure mode — passing alone, hanging in a
full run — is worth recognising quickly the next time a widget acquires a
thread.
