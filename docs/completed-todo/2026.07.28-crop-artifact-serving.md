  - what: >
      `plan.py`, `dag.py`, and `executor.py` were touched after all, gaining
      `ExecutionPlan.pre_cropped` and `ExecutionPlan.source_start` — two
      defaulted fields and a `plan.roi` property.
    why: >
      The item asserted those three modules were untouched, on the reading that
      an artifact run is planned with `roi=None`. It cannot be: the ROI reaches
      both the root key and the executor's crop *through* `plan.replicate`, and
      the only way to say "no region" without a new field is to pass
      `replicate=None` — which silently reverts every per-arena parameter
      override to the node's baseline. That is a wrong answer with no symptom:
      the run completes, reports the same frame count, and computes the wrong
      numbers. The child-source model split one fact into two — which arena's
      *parameters* resolve, and which *pixels* the reader hands over — and
      `pre_cropped` is that split written down. `plan.roi` is then the one place
      the two ways of having no crop (no fan-out, already cropped) are answered
      together, and `dag.node_keys` and `execute` both read it rather than
      reaching for `replicate.roi`.
  - what: >
      `source_start` clamps `decode_start`, so lead-in reaching before the
      artifact begins is reported as a shortfall rather than requested.
    why: >
      The item's match rule says the clip must lie inside the record's span —
      but `sieve materialize` cuts *exactly* the clip, and a graph's lead-in is
      before the clip by construction. Demanding full lead-in coverage would
      mean no artifact ever backs any graph with warmup, which is every graph
      that matters. The frames are not available from any file, which is
      precisely the situation `decode_start`'s existing clamp at frame 0 already
      handles: clamp, run under-warmed, and report it in `lead_in_shortfall`.
      This is the same clamp with a different floor, and it is why the floor is
      a field rather than a literal.
  - what: >
      A crop-served render feeds the render ring nothing. The player decodes for
      itself, as it did before render-fed playback existed.
    why: >
      The item asked for the ring and viewport to "render the crop as a crop".
      They cannot usefully: the pane those frames are painted in draws replicate
      boxes over them in *source* coordinates, so a crop there is not a smaller
      picture but the wrong one, and there is no second surface to put it in.
      And the condition the ring was built for is gone — render-fed playback
      exists to stop the render and the player contending on the parent's
      decode bandwidth, and a crop-served render never touches the parent. So
      the player gets that bandwidth entirely to itself, which is the outcome
      the ring was an approximation of. `FrameResult.source_cropped` is what
      carries the refusal, and it is the same shape as the ring's existing
      refusal of chroma: decline, never convert.
  - what: >
      Resolution is asked against the *request's window*, not the project's
      clip.
    why: >
      It is what is about to be decoded. A single-frame render — a wizard hover,
      a paused-playhead repaint — can name a frame outside what was cut, and
      matching on the clip would hand the artifact an index it does not hold.
      Asking about the window makes that case fall back to the parent, which is
      the same direction every other clause fails in.
  - what: >
      `sieve run --dry-run` and `sieve preview`'s header name the artifact when
      one is serving; nothing prints anything when the fallback is taken.
    why: >
      The fallback must be silent at run time — it is the status quo, not an
      event — but silent *everywhere* would make a stale record
      indistinguishable from a live one until somebody timed the run. A user who
      cut an artifact and then nudged the box gets no error and no slowdown they
      would notice on a short clip. `--dry-run` is the honest place for the
      answer, and the preview header is where it belongs because that command's
      whole output is timings that differ by two orders of magnitude between
      the two cases.

# Serving the crop artifact

Built as specified except where the decisions above say otherwise. Three things
the diff does not say on its own.

**The item's `RunOutputs` is `FrameResult`.** No `RunOutputs` exists anywhere in
the repo; the field the item describes — "the frame *before* the replicate crop"
— is `FrameResult.source` in `pipeline/executor.py`, and the flag landed there as
`source_cropped`. Nothing else in the item depended on the name.

**The stale paragraph in `cache_key.py` was corrected rather than deleted.**
`source_key` carried a paragraph saying a materialized crop "does not appear and
must not: it is a faster route to the same pixels, and letting its presence move
a key would make a storage decision into a semantic one." Under the child-source
model an artifact *does* move the key, knowingly. The function is still correct
and still never asked whether a crop exists — it is handed a different `source`
— so what was wrong was the reasoning, and the paragraph now says which of the
two claims survived. The pattern is the same one `Dag.node_keys`' backend
argument already follows: the superseded sentence is corrected in place with the
correction visible, because a deleted wrong reason is a reason somebody re-argues.

**The verification that the tests are not vacuous is itself asserted.** Both
integration claims would pass most convincingly in the case that means nothing —
a resolution that quietly fell back to the parent produces identical pixels, and
a render that never happened leaves an empty ring. So the frame-for-frame test
asserts `pre_cropped` before comparing, and the GUI test asserts
`PreviewRender.plan.pre_cropped` before asserting the ring is empty. Deleting
either line leaves a test that passes for the wrong reason.

## What is still open behind this

The GUI has no gesture that *writes* a record — that is
`docs/todo/crop-boundary-gesture.md`, the last of the three crop items and the
one that surfaces staleness to the user. Until it lands, `project.crops` is
non-empty only for a project `sieve materialize` has been run on, which the
runner now serves from correctly the moment such a project is opened.
