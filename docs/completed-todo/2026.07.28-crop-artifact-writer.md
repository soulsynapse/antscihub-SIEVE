  SIEVE now writes something that outlives the process: `sieve materialize`
  cuts one replicate's crop over the clip span to an FFV1/Matroska file beside
  the project, verifies it by reading its own output back through the unchanged
  `VideoReader`, and records it on `Project.crops` as a child source with its
  own identity — which is the commit that returns "filesystem is truth at rest"
  to the rules table as rule 8.

decisions:
  - what: >
      The read-back tolerance is a *gross* two-grey-level bound on mean and
      standard deviation, applied only to frames whose digest already missed.
    why: >
      The item asked for "cheap statistics" without naming them, and the choice
      is between holding the fed frames (a whole clip resident, which this pass
      exists not to do) and holding a summary. What the tolerance guards is the
      qp0-gray failure class — a valid file serving pixels that match no fed
      frame — and garbage does not land within two grey levels of the frame it
      impersonates. FFV1 passes on the digest and always will, so the tolerance
      is never reached today; it is there so a later declared-lossy format does
      not force this check to be deleted rather than loosened.
  - what: >
      `CropArtifact.backs` matches on parentage, geometry, format, and file
      existence — and deliberately not on span.
    why: >
      The item stated the first three. Span is the one condition whose answer
      is not a yes or a no: a record covering [10, 20) asked for [12, 30) backs
      part of the request, and what to do about a partial cover depends on which
      frames the caller wants. A predicate that folded it in would answer "no"
      to a record that is perfectly usable, and the serving item would have to
      re-derive the real question anyway.
  - what: >
      `storage/crop_writer.py` declares two local `Protocol`s for PyAV's
      encoding surface and casts to them, rather than a file-level pyright
      suppression.
    why: >
      PyAV ships type information, but `add_stream` is overloaded on a literal
      set of codec names that does not include `ffv1`, and its packets are
      generic in a parameter the stubs leave open — so under `strict` every call
      through it is partially unknown. The repo's no-suppression rule leaves
      writing down the surface actually used, which is eight lines and is
      checked: a PyAV that renamed `pix_fmt` fails to type here instead of
      failing on the first artifact somebody writes.
  - what: >
      `sieve materialize` takes one replicate per invocation and has no
      `--format` flag.
    why: >
      Format is `not Dag.needs_chroma` for the graph that will read the file; a
      flag would let a user write a colour artifact for a luma session, which is
      the exact combination the codec finding proved reads back as plausible
      wrong pixels. And a crop is minutes of decode — a command that quietly
      started twelve of them is a command whose cost nobody estimated, so "all
      of them" is a shell loop, which prints per-artifact progress for free.

rejected:
  - what: >
      Decoding the write pass through `PrefetchFrameSource` to shorten the 46 s
      luma / 124 s BGR cut.
    why: >
      The pass is a strictly sequential walk, which is the access pattern the
      prefetcher buys the least on, and taking decode workers is a rule 5
      declaration rather than a local optimisation. The write is also priced at
      one render's decode — the thing it replaces costs 107x more per frame
      forever after.
  - what: >
      Recording the frame-clamped ROI on the artifact instead of the
      replicate's own.
    why: >
      Clamping is a function of the decoded frame and the executor applies the
      identical `ROI.clamped_to(...).crop(...)`, so the pixels agree either way
      — but a replicate whose box overhangs the frame edge would then never
      match its own artifact, because `backs` compares against the box the
      document holds.
