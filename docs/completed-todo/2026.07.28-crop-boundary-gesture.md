summary: >
  The GUI can now write a crop artifact and live with one: a card above the
  chain stack says which of the four states a replicate's source boundary is
  in, offers the cut with its price on the affordance, runs the write off the
  GUI thread with progress and cancel while the preview is paused, and — once a
  record backs the replicate — fades and refuses the box and the clip that
  would orphan it, with an explicit discard as the only way back.

decisions:
  - what: >
      The document owns the crop records and the source home, the way it
      already owns `visited` — edited by the GUI, saved with the project, off
      the undo stack — and `ReplicateDocument.crop_backing` is the single place
      the four-state reading is asked for.
    why: >
      Three surfaces need the answer (the card, the replicate box, the timeline
      fence) and `gui/crop_binding.py` needs four inputs to give it: the
      records, the replicates, the parent's identity, and the format the graph
      decodes. Only the document holds all four. The alternative — the window
      owning the set and handing pieces to each surface — is three callers each
      assembling the arguments, which is three chances to ask a slightly
      different question, and rule 6's absent-versus-stale distinction is
      exactly what a slightly different question loses. `Project.with_crops`
      was already written for this owner and says so in its docstring.
  - what: >
      Registering a record is not undoable, and discarding deletes the file
      behind one confirmation.
    why: >
      `mark_visited`'s argument, one notch stronger: a Ctrl+Z that dropped the
      record would leave a verified artifact on disk that the session can no
      longer find while the folder still holds it. Deletion on discard follows
      from the same asymmetry — a record is the *only* thing that associates a
      crop file with a replicate, since nothing rediscovers an unrecorded file,
      so keeping the bytes leaves the user a folder SIEVE can neither serve nor
      explain. The confirmation names the file and says both halves.
  - what: >
      Pausing the preview is a new `PreviewRunner.set_paused`, not a new row in
      `gui/concurrency.py`.
    why: >
      Rule 5 is about consumers that *take* a share. The write pass borrows the
      preview's for the length of one cut and gives it back on every exit —
      success, failure, and cancel — so the declared sum does not move and there
      is no fourth consumer to declare. A row would have to describe something
      that is never live at the same time as the thing beside it.
  - what: >
      `MainWindow._write_project` now assembles the project *first* and
      relocates the assembled value, reversing the order it ran in.
    why: >
      The document is the live crop set, so `apply_to` overwrites whatever the
      base carried — which meant a Save As was rebasing records that were then
      thrown away and storing ones that were not. One relocation over the
      assembled project rebases source, sinks, and crops together, from the one
      directory they are all actually relative to (`source_home.project_dir`).
  - what: >
      `apply_to` calls `with_crops` last, after `with_pipeline`.
    why: >
      `with_crops` validates the whole project, and before the graph is written
      the intermediate value still carries pins naming nodes the *old* graph
      does not have. This is the same ordering constraint `with_pipeline`
      already documents, arriving at a second validating setter — and it is a
      test failure, not a theory: `test_settings_memory` caught it.
  - what: >
      The source card sits outside the stack's scrolling column.
    why: >
      `ChainStackView.rebuild` tears that column down on every structural edit,
      and the card is the one thing on the tab that can be mid-write. A card
      rebuilt underneath a running write pass loses its progress and its cancel
      button while the write continues.
  - what: >
      The timeline clamps a window drag inside the frozen span mid-gesture,
      rather than letting it travel and refusing on release.
    why: >
      Rule 6's mirror direction: a handle that went where the user pointed and
      then snapped back looked live for the length of the drag. The document's
      refusal stays as the backstop for the paths that are not drags — a typed
      number, an undo, a loaded clip.

rejected:
  - what: Guarding the frozen box in the viewport only.
    why: >
      Geometry moves three ways — a drag, a typed number, and set-all — and a
      guard on the gesture guards one of them. The refusal lives in
      `set_roi`, which all three pass through, and the viewport's fade is what
      keeps the refusal from being the first the user hears of it.
  - what: Refusing `set_all_to_size` outright when any row is frozen.
    why: >
      A rack of twelve with one materialized arena should still square up the
      other eleven. Taking the whole gesture down would make one artifact a
      reason to discard it, which is the opposite of what the freeze is for.
      The skipped rows are named in the refusal message.
  - what: >
      A `crops_changed` emit from `load_project`.
    why: >
      Adoption sets the home *after* the load, so a listener that re-read the
      records at that moment would resolve them against the previous project's
      directory. The home and the set are declared together by
      `MainWindow._adopt_project`, which is the one caller that has both.
