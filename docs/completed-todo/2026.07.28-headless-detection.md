summary: >
  Detection composes into an answer without Qt: `src/sieve/detect/` holds
  `detect`, `settled_for`, and `gate_to` over a resolved `DetectorSettings`,
  `sieve detect` runs a whole clip from the command line, and
  `gui/chain_model.recompute` and `gui/detector_worker.settled_for` are
  two-line adapters that convert live state at the boundary.

decisions:
  - what: the series a detection runs over is the sink's output, and a graph
      with two sinks is refused with `--node` named rather than one picked
    why: which series a detection was taken over is part of what the answer
      means; picking silently would return a number describing a different
      measurement than the caller believes
  - what: "a project whose `detector` is None reports that it has no detector
      and so claims nothing — it is not resolved to
      `DetectorSettings.default_for(fps)` and not printed as zero intervals"
    why: rule 6 — never tuned and tuned-but-disarmed are two distinct absences
      and neither of them is "found nothing"; resolving the default into the
      field would make an untuned project's output look founded
  - what: "`DetectorState.to_settings()` was written here"
    why: the item asserted it already existed; only `as_settings_changes()` did,
      which returns a dict for partial submits and is not the same object

rejected:
  - what: leaving `recompute` in `gui/` and having the CLI import upward
    why: "`sieve.gui` and `sieve.cli` are siblings in the layers contract, so the
      import is forbidden and the alternative is a second implementation of the
      composition — rule 1 with the detection chain substituted for the executor"
