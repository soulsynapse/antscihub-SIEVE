# The prefetch worker optimum on the luma path

The measurement is `docs/findings/2026.07.28-the-luma-path-has-almost-nothing-left-to-thread.md`
and is not restated here. What this entry adds is the shape of the change: the
sweep script was a throwaway against the two reader classes, deleted after it
produced the curve, because the protocol it implements is one paragraph of the
finding's `source.probe` and a reader who needs to re-run it has the footage,
the frame range, and the repeat count from there.

The defect this closed was invisible by construction. Every frame the luma pool
produces is correct at any worker count, so nothing in the suite, nothing in the
budgets, and nothing a user sees would have reported that the preview's reader
was inferring a count 21% past its own optimum. The only thing that could report
it was a curve, and the constant's comment said so — "inherited, not established"
— which is why the flag was worth honouring rather than quietly leaving.

The wiring test is the one that earns its place. `resolve_workers(workers)`
without the keyword type-checks, passes every other test in the prefetch suite,
and reintroduces exactly the regression this item removed; the unit test on the
function cannot see that, because the function is fine. It skips rather than
asserts on an allocation under four cores, where both caps resolve to the same
number and the test would pass with the keyword deleted.

Nothing outside the item's scope changed. `gui/concurrency.py`'s
`PREVIEW_WORKERS` kept its value and gained the reason it now has one: two was
a concession to the player's decode thread and is, on the luma path the preview
actually takes, also the optimum.
