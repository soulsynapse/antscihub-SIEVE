title: A drop menu applies on selection, not on highlight
date: 2026-07-28
commit: 7d90b36
tags: [gui, input, combo, wheel]
settled: none

summary: >
  A mode menu can be arrowed through or scrolled past without the values on the
  way becoming renders: navigation keys on a closed combo open the popup, where
  highlighting and choosing are different acts, and `textActivated` is the one
  signal either call site wires.

files:
  added:
    - src/sieve/gui/commit_combo.py
    - tests/gui/test_commit_combo.py
  changed:
    - docs/SCAFFOLD.md
    - src/sieve/gui/filter_tab.py
    - src/sieve/gui/param_form.py
  removed: []

decisions:
  - what: >
      The behaviour is a `QComboBox` subclass (`gui/commit_combo.py`) that both
      call sites instantiate, not an application-level event filter beside
      `wheel_steps.py`.
    why: >
      `wheel_steps.py` is a filter because its rule needs an answer the widget
      does not have — whether something scrollable encloses it, which only the
      parent chain knows — and because it must cover knobs `param_form`
      generates for filters nobody has written yet. This rule needs neither. It
      is unconditional, it is decided entirely from the combo's own state
      (popup open or closed), and `param_form` already funnels every generated
      enum through one constructor, so a subclass reaches the same set with
      nothing to install and nothing to opt out of. A filter would also have to
      re-derive "is this combo's popup open" from outside the widget that owns
      it.
  - what: >
      A wheel over a closed combo is declined outright, with no focus escape
      hatch — unlike a spin box, which still steps once it is focused.
    why: >
      The asymmetry `wheel_steps.py` documents turns on a knob having a step
      that is not a commit: a focused spin box has to answer the wheel, because
      cranking it is the gesture. A combo has no such step. Every notch is a
      value the document records and the pipeline re-plans, so "yield only when
      unfocused and enclosed by something scrollable" would buy nothing and
      leave the defect live for exactly the user who clicked the menu first.
      This also closes a gap rather than opening one: the wheel filter watches
      `QAbstractSlider` and `QAbstractSpinBox` only, so combos in the card
      column were never covered by the panel fix.
  - what: >
      Type-to-search on a closed combo is left exactly as Qt has it, while
      Up/Down/PageUp/PageDown/Home/End are redirected to the popup.
    why: >
      The rule being enforced is that a value the user *passed over* is not a
      value they chose. A keystroke that names an entry does not pass over
      anything — it is a statement of which entry — so it is a selection under
      this rule, not a violation of it. Redirecting it would cost the fastest
      way to work a menu for no defect removed.

rejected:
  - what: The plain signal swap, `currentTextChanged` → `textActivated`.
    why: >
      Named and rejected in the item, and the mutation check confirms the
      premise rather than taking it on trust: with the key redirect disabled,
      a single Down on a closed combo emits `textActivated("zscore")`. Qt
      counts arrowing a closed combo as an act of selection, so the swap fixes
      the popup and leaves the arrow keys untouched.
  - what: A debounce — the value that survives ~200 ms is the chosen one.
    why: >
      Decided against in the item on 2026-07-27. It makes "chosen" a function
      of how fast the user moves, which is the per-keystroke defect the number
      fields shed in `spacebar-dies-on-focus` wearing a different widget.
  - what: A pending value the combo shows until Enter, a click, or focus-out.
    why: >
      The most literal reading of the number fields' shape and the most work,
      and it incurs a cost option (1) does not: the pending state has to be
      *visibly* distinct or a menu reading `zscore` over a pipeline running
      `off` looks more live than it is, which is rule 6's mirror clause.
  - what: >
      Measuring first whether a passed-over value is fully cache-served on the
      way back — the item's fourth possibility.
    why: >
      Worth taking as a finding about cache behaviour, but it was never this
      item's gate and the item says so. A fully cache-served pass-through is
      still a wasted render queued in front of the one the user wants, and the
      fix does not change shape depending on the answer.
