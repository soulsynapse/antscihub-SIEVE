    why: >
      A retention policy has two inputs and a trace of queries alone cannot be
      replayed — a rule has to be told what it was offered before it can be
      scored on what it kept. One line-buffered file rather than two per-thread
      ones because the interleaving *is* the eviction arithmetic: a put that
      lands after a get evicts against a different playhead than one that lands
      before it.
  - what: >
      The instrument lives in `bench/` and the policies are index-only
      simulations, not a `RenderFrameRing` subclass.
    why: >
      The experiment's question — which frames a rule keeps — has no Qt in it,
      and running the candidates through the real ring would need a QImage per
      frame and a Qt runtime to answer it. `bench/` is also where the repo
      already puts an instrument the GUI writes to and nothing else depends on
      (`metrics.py`), so the layer contract already covers this direction.
  - what: >
      Turned on by `SIEVE_RETENTION_TRACE`, not by a preference.
    why: >
      It is a developer's instrument for one experiment. A preference would
      have to be worded in the dialog, kept working after the experiment ends,
      and explained to somebody who will never run it.
  - what: >
      Line buffered, and nothing owns closing the recorder.
    why: >
      The player and the preview runner shut down independently, so whichever
      closed it first would silently truncate the other's events — a trace that
      looks complete and is not. A write syscall per event is affordable for an
      instrument that is off by default.
  - what: >
      Stall is scored in consecutive misses, not milliseconds.
    why: >
      A replay cannot know what a decode would have cost for a frame that run
      never decoded. A millisecond figure derived from an average decode would
      read as measured; a miss run reads as what it is.

rejected:
  - what: >
      Building the distance-from-playhead rule into `RenderFrameRing` in the
      same pass.
    why: >
      Adopting a policy on the strength of the harness written to test it is

# Record a tuning session, and score a retention policy against it

Split out of `docs/todo/proxy-retention-policy.md` the same day it was taken:
that item's remaining work is a measurement plus one decision, and this is
everything about it that does not depend on the answer.

Two things a reader cannot get from the diff.

**The playhead at eviction time is reconstructed, and that is not a compromise
made for the trace.** A `put` happens on the render thread, which does not know
where the user is looking, so the simulator carries the playhead forward from
the last `get`. A distance-from-playhead rule inside the real ring would have
exactly the same problem and exactly the same solution — the player would push
the playhead across the thread boundary — so the replay is not modelling
something the implementation could do better.

**One event per request, at the point the source is known.** The player has
three layers and a request can fall through two of them, so the recording sits
after each layer's decision rather than at the entry point. Recording on entry
and again on resolution would double-count exactly the requests the experiment
is about. `tests/gui/test_retention_trace.py` drives a real drag onto a
ring-held frame and then onto one nothing holds, and asserts the two events and
their sources; the unit tests build events by hand and cannot see this.

**What the harness was calibrated against.** `backward_scrub_trace` in the unit
tests is a render filling forward past a capacity while the user scrubs back
behind it — the observation that opened the parent item, made small enough to
assert on. The ring scores zero drag hits on it and the proposal scores every
one. That is not evidence the proposal wins on real sessions; it is evidence
that a null result on a real session would mean something, because the harness
can tell the two apart when the difference is there.
