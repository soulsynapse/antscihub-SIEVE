summary: >
  A graph that cannot run can now be described node by node instead of one
  message at a time: `Dag.validate` returns every rejection as a `Diagnostic`
  and `Dag.build` is that same walk plus raising the first one, so fail-fast
  and collect-all are two readings of one definition rather than two
  definitions.

settled:
  - what: One walk answers whether a graph is legal, in two consumption modes
    where: "`src/sieve/pipeline/dag.py` — `Dag.validate`, `Dag._walk`, `Diagnostic`"
    do_not_redecide: >
      `validate` is a classmethod over a `Pipeline`, never a method on a built
      `Dag`: the graph worth validating is precisely the one no `Dag` exists
      for, and an instance method would be the `is_valid()` that makes the
      checked and unchecked cases one type. A `Diagnostic` carries the
      `GraphError` itself rather than a message assembled beside it, which is
      what makes the two modes unable to word one rejection differently — the
      drift that a second spelling in a widget produces by construction. The
      five rejections keep their fixed order and the first two still stop the
      walk: an unresolved filter leaves later checks with no `FilterSpec` to
      read and a cycle leaves them with no order to read in, so collecting past
      either would report verdicts derived from what is already missing. For
      the same reason a node with a wiring verdict gets no edge verdict, and a
      node trips at most one wiring verdict — an edge into `rigth` leaving
      `right` unfilled is one typo, not two faults.

decisions:
  - what: >
      `ChainKind` and `chain_model.grade` were not deleted here, though the
      item's text said they would be.
    why: >
      `grade` does not walk a graph's edges — it walks five `ChainStep`s, two
      of which (`morlet_band`, `windowed_count`) have `node=None`. There is no
      `FilterSpec` to read an `element` or an `emits` from for those, so no
      `Dag.validate` can grade them, and the item's "independent of the
      protocol work" holds for supplying the diagnostics and not for consuming
      them. The deletion is already a bullet on `detector-state-dies`, already
      gated behind `the-graph-carries-the-crop-the-span-and-the-detector` →
      `detection-is-a-filter` → `a-kernel-that-sees-a-span` — so the real gate
      was in the DAG the whole time and this item's line about it was a forward
      reference to work another item owns. No residue item: there is nothing
      here that `detector-state-dies` does not already say.
