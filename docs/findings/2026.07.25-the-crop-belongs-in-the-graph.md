      what it is", and never hashes them so an HPC handoff can drop them without

      "Has the background crop finished" is a cache question. A cache question
      cannot change a result without breaking a rule the artifact already
      enforces, so no new declaration is needed to keep the preview honest.

    detail: >
      With the crop at the root, a local kernel at the arena's edge fabricates

      "do these agree" and becomes "should a pixel at the arena wall see outside
      the arena".

      For arena-bounded behaviour the answer is plausibly no, and there is
      nothing to build. `context_radius` earns its place when a filter with a
      radius exists and the answer is yes — not before.

# The crop belongs in the graph, so materializing it cannot change a result

The superseded finding was right about the filters and wrong about the
workflow. Its two-class analysis holds: a local kernel computed on a parent
frame and then cropped agrees with one computed on a margined crop, and a
whole-frame statistic does not agree with anything computed on a different
frame. What it got wrong was assuming the graph would ever be handed the parent
frame at all.

It is not. Entering a replicate decodes a parent frame and crops it in memory
before the first filter runs. The background crop that follows is a smaller,
faster source for the same pixels.

## Why this is an invariant and not a convention

Written down as "remember to crop first", this would decay. It does not have to
be, because two things in `pipeline_model.py` already force it from opposite
directions.

The fan-out puts the crop below the graph: one pipeline runs once per
replicate, and a root node "consumes the source directly, once per replicate".
There is no position in the graph from which a node could observe an uncropped
frame, because the fan-out has already happened by the time the graph starts.

The checkpoint rule puts materialization outside identity: `checkpoints` lives
on `Project` rather than on `Node`, is never hashed, and exists so a cluster
with the memory to skip compaction can drop it without moving a cache key. A
materialized crop is one of these. If its presence changed what the graph
computed, that rule would already be violated, and the violation would be
detectable by any cache key that survived toggling it.

So the guard is not new discipline. It is two existing rules meeting.

## What this costs, and why the crop still has to happen in the background

Nothing about correctness argues for materializing the crop, so it is worth
saying what does. A parent-frame decode on the reference footage is ~68 ms
before a single filter runs, against a 100 ms slider-drag repaint budget. The
crop is what makes the tuning clip small enough for that budget to hold with
filters in the path. It stays for that reason and no other, which is exactly the
kind of thing `checkpoints` is for.

## The reduction, if it is ever needed

If an auto-threshold filter is written later, the temptation will be a
`frame_global: bool` on `FilterSpec`. That is a smaller version of the problem
this finding closed: it asserts a domain on a spec rather than showing it in the
graph. The better shape is an explicit reduction node emitting a `TableSpec`
with columns like `(frame, threshold)`, consumed by a pointwise node that
applies it. The stream union added in
`2026.07.25-filter-contract-rate-stream-kind-output-size.md` already carries
that, the reduction's input is visible as an edge, and a per-replicate threshold
is then just the fan-out doing what it already does.

## What would have to be true for this to be wrong

If the preview ever needs to show the parent frame *and* the filter result
together — VISION step 4's three-way overlay switch is the obvious candidate —
then something is rendering uncropped pixels while the graph runs on cropped
ones. That is a compositing question rather than a domain question, and it is
only a problem if the overlay path is allowed to feed the graph rather than
just the screen. Worth re-reading this file when that overlay gets built.
