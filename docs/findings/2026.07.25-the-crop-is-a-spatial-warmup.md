findings:
  - class: 'local kernels — blur, morphology, wavelet bands, gradients'
    equivalence: >
      Computing on the parent and then cropping equals computing on a crop
      expanded by the kernel radius and then trimming. The two agree exactly.
    consequence: >
      Safe, and safe in both directions: the crop can be taken early provided it
      carries a margin of the kernel radius. Without margin the disagreement is
      confined to a border band of width r, which is a real defect but a visible
      and bounded one.

  - class: 'whole-frame statistics — Otsu and any auto-threshold, histogram normalization, per-frame mean subtraction, a background model fit over the frame'
    equivalence: >
      None. The parent's statistic is taken over the whole arena field; the
      replicate's is taken over one arena. The two differ whenever the arenas
      are not identically exposed, which is the situation replicates exist for.
    consequence: >
      Every pixel of the preview differs from the eventual run. The user tunes a
      threshold against a frame that will never be produced again, and nothing
      about the preview announces it — the same silent-plausible-output failure
      as the decimator warmup gap, in space instead of time.

# than a special case: warmup_frames answers "how many frames of context before

  - 'the parent-frame preview cannot be enabled unconditionally on entering a replicate'
  - 'a crop taken without margin is wrong in a border band for every local kernel'
  - 'nothing in `FilterSpec` distinguishes the two classes, so the executor cannot choose'

  - whether the declaration is one field (a context radius, with a sentinel or a
    separate flag for "the whole frame") or two. A radius and an unbounded case
    are different kinds of answer, and `ArraySpec.ndim`'s lesson is that two
    fields able to contradict each other eventually will
  - whether a whole-frame filter should refuse the parent-frame preview or

  - whether the margin belongs to the crop (decode-time, one expansion for the
    whole path) or accumulates per node the way warmup does. Summing radii along
    a path has the same unit problem rate had, since a downsampler changes what
    a pixel of margin is worth

# The replicate crop is a spatial warmup, and nothing declares it

> **Superseded by `2026.07.25-the-crop-belongs-in-the-graph.md`.** The premise
> was wrong: the filter tab decodes a parent frame and crops it *before*
> filtering, so the graph never sees an uncropped frame and the substitution
> this file worried about never happens. Kept because the two-class analysis
> below is sound and is what made the premise worth stating out loud, and
> because the file records why the crop's position in the graph was pinned down
> rather than left to be inferred.

`ROI.crop` exists and takes a tight rectangle. `warmup_frames` exists and is
denominated in frames. Between them there is no way to say that a filter needs
pixels from outside the region it is being asked to produce, and the intended
replicate-entry behaviour — preview against the parent until the crop is ready —
is a bet that no filter does.

## Why this is not simply "crop with margin and move on"

Margin solves the local case completely and the global case not at all. A
Gaussian with radius 9 needs 9 pixels of context; give it 9 and the parent-frame
result and the cropped result are the same array. There is no margin that makes
Otsu agree, because the quantity it needs is not a neighbourhood — it is the
histogram of whatever frame it was handed, and the whole point of cropping to a
replicate is that the histogram changes.

So the declaration has to distinguish *bounded* context from *unbounded*, and
those are not two values of one number. That is the first open question above,
and it is the same question `ArraySpec` answered by refusing to carry `ndim`:
one field that can disagree with another eventually will.

## What would have to be true for this to be wrong

If every filter that sets a threshold takes it as an explicit parameter rather
than computing it from the frame, the global class is empty and margin is the
whole answer. That is a defensible design — VISION step 5's whole premise is
guiding the user to a number rather than having the code guess it — and v1 of
SIEVE did let the user set thresholds directly. It is not obviously the design
that survives contact with twelve unevenly lit arenas, which is precisely the
case per-replicate deviation exists to serve, but it would close this gap
without a new declaration.

The measurement that would settle it does not need any of this built: take one
parent frame, run Otsu on it, run Otsu on each replicate crop of it, and compare
the thresholds. If they agree to within a few levels on real footage the concern
is theoretical. Nothing here has been measured, and this finding stays `open`
until something has.
