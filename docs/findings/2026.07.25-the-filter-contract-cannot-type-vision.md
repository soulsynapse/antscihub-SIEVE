# The filter contract cannot type what VISION asks filters to do

This is analysis, not measurement, and it is filed here rather than left in a
TODO item because it is true about the system whether or not anyone acts on it.
No filter exercising any of the three gaps exists yet — `sieve.filters` is
empty — so nothing is currently broken. All three bite in items that have not
been written, which is the cheapest possible moment to have noticed them.

**Closed.** All three are declarable as of
`docs/completed-todo/2026.07.25-filter-contract-rate-stream-kind-output-size.md`:
`ParamsBase.output_rate`, `TableSpec` under a `StreamSpec` union, and
`FilterSpec.stored_bytes_ratio`. The prediction below — that the two open
questions would be decided by the decimator's factor being a parameter — is
what decided them. The paragraph that follows is left as written, because the
warmup arithmetic it describes is now implemented by `source_warmup_frames` and
this is the statement of what that function is for.

## Why the rate gap is the expensive one

The other two are absences: something cannot be declared, so a feature cannot
be built. The rate gap is different in kind, because the affected arithmetic is
already specified in `ARCHITECTURE.md` and reads as complete:

> The executor sums `warmup_frames` over the topological path feeding a
> preview, requests `[clip_start − total, clip_end]`, and discards the lead-in.

Summing is only valid in a common unit. Warmup declared by a node downstream of
a decimator is denominated in that decimator's output frames, and the request is
denominated in source frames. Nothing in the contract records the conversion, so
an executor written straight from the specification above will compile, run,
and under-warm every temporal filter that sits behind a decimator — by exactly
the decimation factor. The failure is invisible: an IIR that should have settled
produces a plausible frame, and the tuning done against it is wrong rather than
absent.

This matters most for the filters VISION cares about most. Step 3C's list —
IIR, wavelets, MEI, MHI, temporal integration — is entirely filters with
nonzero warmup, and step 4's whole economy argument is about putting a
decimator in front of them.

## What would have to be true for this to be wrong

If no filter ever changes its output rate, the gap closes on its own. That
would require frame decimation to be implemented as something other than a
filter — a decode-time setting on the source, say, which is a defensible design
and would move the conversion into `decode/` where the index space is already
being translated. That option is genuinely open and is the reason the second
open question above is phrased as it is.
