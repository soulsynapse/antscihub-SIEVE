# A stateful filter's output is not keyed by what it is

## The argument that was wrong

The obvious reason to exclude a stateful node from the cache is that its output
at frame `i` depends on where the run began: a preview over `[100, 200)` and one
over `[150, 200)` derive identical keys for the node — same source, same params,
same backend, same replicate — and would seem to disagree about frame 160.

They do not. The test that was written to demonstrate the disagreement found
agreement, bit for bit, and the reason is `warmup_frames`.

`ExecutionPlan.decode_start` is `max(span.start - lead_in, 0)`. Any run that
reaches frame `i` has therefore seen either `warmup_frames` frames before it, or
every frame from 0 — there is no third case, because the clamp is the only thing
that shortens the lead-in. So:

- If `i >= warmup_frames`, both runs are warmed, and "warmed" is precisely the
  claim that the seed's residual influence is below the filter's epsilon.
- If `i < warmup_frames`, both runs clamped to 0 and have seen *the same frames*.
  They agree exactly.

A stateful filter with a correct `warmup_frames` is span-independent. That is
not a happy accident; it is the whole thing the lead-in arithmetic was built to
buy, and it is the first time anything in this repo has actually used it.

## The argument that holds

The invariance above is a consequence of a number the filter author wrote in a
decorator. `Dag.node_keys` derives a key from declarations; it cannot run the
filter, cannot measure convergence, and has no way to distinguish

```python
@register_filter(..., stateful=True, warmup_frames=90)   # background_ema: true
@register_filter(..., stateful=True, warmup_frames=0)    # a running sum: false
```

The second is six lines away in the test file. It is stateful, deterministic,
declares valid I/O, and its output at frame 12 genuinely differs between a run
that started at frame 5 and one that started at frame 10. Every static fact a
key is derived from is identical in kind to `background_ema`'s.

So caching a stateful node would mean the correctness of a served entry rests on
an unverified numeric claim in a decorator, with the failure landing where
`cache_key.py`'s asymmetry rule says failures must never land: the key is
well-formed, the entry is present, the frame is plausible, and the only evidence
is a machine that ran the other span.

`cacheable = deterministic and not stateful` is the version of that rule that
can be evaluated from declarations alone.

## What it costs, and why that is the right side to be wrong on

A graph containing a stateful filter has no cheap re-run. Tuning a threshold
downstream of `background_ema` recomputes the background every time, at roughly
10 ms per megapixel — the most expensive thing per pixel in the repo. That is a
real and recurring cost, paid on every preview.

It is still the right trade, for `cache_key.py`'s reason: a miss is slow and a
wrong hit is invisible. And it has a cheap mitigation that the guidance markdown
already recommends for other reasons — put a downsample in front, and the cost
falls with the square of the factor.

## What would change the answer

A key that carried `decode_start` would be correct and useless: every distinct
span would key differently, and nothing would ever hit — which is the same
outcome as not caching, with a larger store.

The version that would actually work is a key over the computation plus an
*origin that collapses to a constant once the run is warmed*: `min(decode_start,
span.start - warmup_frames)` is already that value in disguise, and two warmed
runs would key identically while an under-warmed one would key apart. It needs
`warmup_frames` to be something the system can check rather than something a
filter asserts — a convergence probe at registration, or a declared epsilon the
kernel is tested against. `test_background_ema.py` writes exactly that test by
hand for one filter. Making it general is what this is blocked on, and it is not
worth doing until a second stateful filter exists to generalise over.
