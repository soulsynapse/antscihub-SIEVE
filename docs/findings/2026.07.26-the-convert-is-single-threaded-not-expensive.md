# The convert is single-threaded, not expensive

The two numbers that overturn the previous finding are **2.95 ms** and
**26.0 ms**, for the same operation on the same 300 frames: decode this file and
hand back a full-resolution BGR frame. ffmpeg's `bench` line explains the gap
without ambiguity —

```
decode only:            rtime 0.510 s   utime  4.72 s
decode + bgr24 convert: rtime 0.884 s   utime 15.48 s
```

— 10.8 s of additional CPU appearing as 0.37 s of additional wall clock is
sws_scale running on about 17 cores. `VideoCapture::retrieve` does the same
conversion on the thread that called it, on one core, and then apparently copies
the result again: a bare `cv2.cvtColor(COLOR_YUV2BGR_I420)` over a buffer of
identical shape is 6.81 ms, so 12 of `retrieve()`'s 19 ms are not even the
conversion.

**This is the same fact `2026.07.25-decode-cost-is-colour-conversion.md`
recorded** (grab 1.3 ms, retrieve 29 ms) and the same fact the superseded
finding measured (~22 ms per frame of `decode_range`). What was wrong was the
word "decode" in the conclusion drawn from it. "Decode cost" reads as a property
of the codec and the resolution, which invites the conclusion that no arrangement
of software can fix it; the honest statement is that this reader converts 15.9
megapixels on one core in order to show the graph a 0.63 megapixel window, and
does it once per frame with nothing overlapped.

## The footage is not H.264, and that matters twice

`ffprobe` says `mpeg4 (Simple Profile) (mp4v)`, yuv420p, 183 Mbps. The `stab_`
prefix and that bitrate together say this is a stabilized re-encode, and 183 Mbps
of MPEG-4 Part 2 is what OpenCV's own `VideoWriter` with `fourcc(*"mp4v")`
produces — the same writer `tests/conftest.py` uses for fixtures.

Three findings dated 2026.07.25 record this file as `5312x2988 H.264 @ 59.94
fps`. They are wrong in a field whose entire purpose is making numbers
comparable later, and the error is not cosmetic:

- **The hardware-acceleration result changes meaning.** `VIDEO_ACCELERATION_ANY`
  reporting `HW_ACCELERATION = 0.0` is unsurprising for MPEG-4 Part 2 — NVDEC
  dropped it, and no consumer GPU decode path targets it. It says nothing about
  whether hardware decode would engage for the H.264 the cameras actually
  produce, which is what a reader of that finding would take away.
- **The decode-is-cheap result is partly a consequence of the codec.** MPEG-4 SP
  has no CABAC, no deblocking to speak of, and 183 Mbps of it decodes fast. The
  original H.264 may not be 1.2 ms/frame, and no measurement here covers it.

The old files are left alone rather than edited: this is the authoritative
correction, and a probe on the camera-original H.264 is the thing that would
settle what the numbers become.

## Four routes, and the question that decides between them

Speed is not the constraint — all four are fast enough. The constraint is
`cache_key.source_key`, which folds `decoder_identity()` into the ancestor of
every node. A route that changes a single pixel of what `read(i)` returns is
correct only if it also changes that identity, and by
`docs/findings/2026.07.25-the-crop-belongs-in-the-graph.md` a faster route to
*the same pixels* must not change it.

| route | ms/frame | pixels | random access | new dependency |
| --- | --- | --- | --- | --- |
| A. ffmpeg subprocess, `-vf crop` | 2.13-2.79 | **differs** | no | ffmpeg binary |
| B. PyAV, crop before reformat | ~2-3 (untested) | **differs** | yes | `av` |
| C. Thread the reads inside `decode/reader.py` | ~3-4 (est.) | identical | yes | none |
| D. `CAP_PROP_CONVERT_RGB = 0`, luma only | 8.22 | **differs** (drops chroma) | yes | none |

**A and B crop before the conversion**, which is where the pixels change: YUV420
chroma is half-resolution, so upsampling a sub-rect and cropping an upsampled
frame disagree along the crop boundary. They are legitimate — they need a new
`decoder_identity()` and a cache generation, which is a one-line cost — but they
may not be described as the same pixels, and `ROI.clamped_to(...).crop(...)` in
`executor._crop` would have to stop being the thing that does the cropping.

**C changes nothing semantically**, which is why it is the safest large win: N
`VideoCapture` handles positioned at strides through `decode_range`, each doing
the identical `read()`, reassembled in order. Every frame is byte-identical to
what the current reader returns, so no key moves, and the ceiling is ffmpeg's
2.95 ms because that is what threaded conversion costs. The executor already
walks `decode_range` strictly forward and takes a `FrameSource` protocol rather
than a `VideoReader` — `executor.py` says so explicitly — so a prefetching source
is a drop-in with no change above it.

**D is the cheapest and the most interesting**, because the luma plane is what
every filter in this repo actually reads: `downsample` strides, `background_ema`
accumulates. 8.22 ms for one property set, and it returns exactly the Y plane.
What it costs is that a frame stops being BGR, which the filter contract can
express (`ArraySpec` carries channel layout) and `ChannelSpec.GRAY` already
names — so this is a contract question rather than a performance one.

## What would flip this conclusion

A measurement on camera-original H.264 rather than this re-encode. Everything
above rests on decode being 1-2 ms, and that number belongs to MPEG-4 Simple
Profile. If H.264 at this resolution decodes at 15 ms/frame single-threaded then
route C's ceiling moves and hardware decode stops being a closed question — and
the `HW_ACCELERATION = 0.0` result would need re-running, because it was never
tested against a codec any GPU wants to decode.
