# Threading the reads buys 1.6x and stops

The curve is the whole finding:

```
VideoReader (sequential)   24.50 ms/frame
workers=1                  25.23
workers=2                  17.36
workers=3                  15.53
workers=4                  15.25   <- optimum, 1.61x
workers=6                  16.12
workers=8                  20.45
workers=12                 28.49   <- worse than one thread
```

Thirty-two cores are available and the optimum uses four. Whatever is saturating
at four workers, it is not the CPU, and that rules out the model the previous
finding was reasoning from — "the convert is single-threaded, so run N of them."
Running twelve makes it *slower than not doing it at all*.

What is left is memory. Each `read` produces a 5312x2988 BGR array: 47.6 MB,
freshly allocated by OpenCV and freed as soon as the executor is done with the
frame. At 15.25 ms/frame that is 3.1 GB/s of writes on top of reading the YUV,
and every one of those allocations is a 47.6 MB block the allocator hands back to
the operating system, so every frame is fresh page faults — which serialise in
the kernel no matter how many threads are asking. ffmpeg's `AVFrame` pool
recycles its buffers instead, which is the difference between its 2.95 ms and the
15.25 ms floor here.

## What this means for the route table

The previous finding's four routes were ranked by speed and the ranking survives,
but the reason has changed. A, B, and D are not faster because they thread better
— they are faster because **they never materialise a full-resolution BGR frame.**
Cropping before the convert produces a 1.89 MB array instead of 47.6 MB; the luma
plane is 15.9 MB and skips the convert entirely. That is the same wall from the
other side, and it is why 8.22 ms is achievable single-threaded with
`CAP_PROP_CONVERT_RGB = 0` while four threads of full-frame BGR cannot get below
15.25.

So the honest summary of the whole investigation: **the cheap win was 1.6x and it
is taken; the expensive win needs the frame to get smaller, and that is a contract
change rather than a threading change.**

## Why this is still worth having

Three reasons, none of them the speed:

- **It is the only route that needs no cache generation.** Every frame is
  byte-identical, `decoder_identity()` is untouched, and every entry in every
  store stays valid. That was the criterion the route was chosen on and it holds.
- **`--workers 1` costs 3%.** 25.23 against 24.50 sequential, so the abstraction
  is nearly free and the option is a real fallback rather than a different code
  path.
- **It puts the knob where HPC needs it.** The count is a parameter with one
  resolver behind it and a command-line option in front, and it is absent from the
  project document — so a cluster job passes `--workers $SLURM_CPUS_PER_TASK` and
  the artifact stays a description of what is computed rather than of the machine
  that computed it.

## What would flip the conclusion

Decoding into a preallocated `Mat`. `VideoCapture::read(OutputArray)` can write
into an existing buffer, and a ring of N reusable frames handed round instead of
allocated would test the allocation-churn hypothesis directly. If the floor moves
below 15 ms with the same worker count, the wall is the allocator and this finding
is half wrong; if it does not, the wall is bandwidth and only a smaller frame
helps. That probe was not run because it means fighting the part of the OpenCV API
this route was picked to avoid — but it is the one measurement that would settle
which of the two it is.
