# Decode is a bandwidth wall, so a faster render starves the player harder

The number that reframes everything is the third row:

```
player colour, no render          23.2 ms/frame    43.1 fps
player colour + colour render     42.1 ms/frame    23.8 fps
player colour + luma   render     50.9 ms/frame    19.6 fps   <- faster render, slower playback
player luma   + luma   render     19.1 ms/frame    52.3 fps
```

Making the render 1.88x faster made playback 18% *slower*. That is not a
measurement error and it is not a scheduling artefact: the preview's frames got
cheaper, so it asked for the next one sooner, and what the two consumers are
queueing for is memory bandwidth and page faults rather than CPU. Speeding up
one consumer of a saturated resource is a transfer, not a gain.

This is the same wall `2026.07.26-threading-the-reads-buys-1.6x-and-stops.md`
found from the other side, where twelve decode threads ran slower than one on a
32-core machine. What is new is that the wall is *shared between subsystems*,
not just between threads of one reader — and therefore that
`gui/concurrency.py`, which enforces non-negotiable #5 by summing worker counts
against core count, is counting the wrong resource. `total_workers()` returns 5
against 32 cores and `fits_machine` passes comfortably while the player loses
half its throughput. The rule is not wrong; its mechanism cannot see the thing
that actually binds.

## Why a shorter window cannot help, which is what prompted the measurement

Render wall time is `N x 22.4 ms` and watching the same window is `N x 16.7 ms`.
Both are linear in the frame count, so the ratio is a constant and no choice of
`N` moves it: the render takes about as long as one pass of watching, whatever
window is picked. Shortening the window shortens the freeze and the thing being
watched by the same factor. This is the only part of the finding that needed no
new instrument — it falls out of two rates — but it was worth stating because
the natural response to a slow render is to render less, and here that response
buys nothing.

## What the luma path did and did not buy

It halved the render: a 70 s window at 59.94 fps goes from ~94 s to ~50 s, which
is the freeze being half as long. It did not make the freeze shallower, and the
table says it made it slightly deeper. Both are true and the first is worth more
— but the honest summary is "the wait got shorter", not "playback got better",
and the second was what the work was undertaken to fix.

The only configuration in the table that is above real time alone is the luma
player at 100.8 fps, and the only one that stays watchable under load is the
all-luma pair at 52.3 fps — 0.87x real time. That is the case for the grayscale
viewport being available, and it is a preference rather than a default because
what it costs is colour in the one pane a user looks at, which is not a decision
a measurement gets to make.

## What would flip the conclusion

A decode that does not materialise a full-resolution frame at all. Every row
above is dominated by allocating and touching either 47.6 MB or 15.9 MB per
frame; a materialized crop at the replicate's ROI is ~1.9 MB and would put both
consumers so far under the wall that the contention question stops being
interesting. That is `docs/todo/materialization.md`, promoted on the strength of
this measurement — and it is the only entry in the table that removes the
second decode rather than making it cheaper or sharing it.
