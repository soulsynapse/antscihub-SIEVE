# scipy.fft's workers argument does nothing in this build

The module docstring said the transform "threads across block columns
(`workers=-1`)" and `gui/concurrency.py` was written around that claim — it
exists, in as many words, because "`scipy.fft`, whose default is *every core*"
made rule 5 stop being self-enforcing. `DETECTOR_WORKERS = 2` was chosen as the
detector's honest share of the machine, and its docstring calls that "a
judgement, not a measurement — nobody has profiled the three pools competing."

Nobody had profiled the pool that did not exist, either. The number was being
passed to a parameter that this scipy install ignores.

## Why the negative result is trustworthy

A flat curve can mean "threading is off" or "the shape cannot use threads." Both
were tested. The transform's own call is `axis=0` on a C-ordered `(T, B)` slice,
so the transform axis is strided and scipy must copy — a plausible reason for
threading to be skipped. So the same sweep was run on a fully contiguous
`(8192, 1120)` batch along `axis=-1`, the best case scipy has: 37.2 ms at one
worker, 36.8 at all of them. And `scipy.fft.get_workers()` returns 1 regardless.
There is no shape at which this build threads.

The counter-prediction is what makes it decisive: if `workers` were live, the
`(599, 8192)` probe — 8192 independent transforms, a batch large enough that
per-thread overhead is negligible — would have shown something. It shows 59.8 ms
at one worker and 59.8 at thirty-two.

## What the pool costs to own

Nothing structural. The chunk loop was already there, for memory: chunks of 512
columns so a whole-clip pass never materializes the full cube. Each iteration was
already self-contained — its own `xf`, its own `acc`, its own `buf`, writing one
disjoint column slice of a preallocated `out`. Handing the loop body to an
executor changes which thread runs it and nothing else, which is why the output
compares equal rather than merely close, and why the test asserts
`assert_array_equal` rather than `allclose`. Float addition is not associative;
the reason this survives that is that the pool never reorders an addition — the
summation over daughters happens inside one chunk on one thread, exactly as
before.

`workers=1` and the single-chunk case skip the executor entirely. That is not an
optimization for its own sake: the 1-D `squeeze` path is one chunk, and the
pooled scalogram calls it on every partial pass.

## What this does not fix

The 3 s `knob_to_graphs` ceiling is still missed at this workload — 5.2 s at
`DETECTOR_WORKERS = 2`, against 2.0 s if the detector had the machine. The gap
is now entirely a policy number rather than a defect, which is the useful form
for it to be in: `gui/concurrency.py` declares three absolute integers that sum
to five, and on a 32-core allocation `fits_machine` returns True while 84% of the
machine idles under a missed budget.

Raising it is a rule 5 decision and not a constant edit. `DETECTOR_WORKERS <=
PREVIEW_WORKERS` is a test with a stated reason — the derivation may never
outrank decode, because a coarse graph is a degraded nicety and a stuttering
scrub is a broken budget — and proportional sizing inverts it on any machine
bigger than about ten cores. The reason is about priority under contention;
whether a thread count is still the right proxy for priority is the question that
has to be answered before the number moves.

## The stress workload is the point

Block size 1 at scale 1.0 means B = 210,672: the block grid *is* the pixel grid,
and the reduction the architecture is built on has been switched off. This is not
the reference workload and the budgets are not promised here. It was measured
because a workload three thousand times the default is where a linear cost and a
missing 4.6x are visible at all — at the default block size of 64 this whole pass
is under 10 ms and the inert `workers` would have gone on being invisible.
