# The density histogram was a scatter, and it ran on every drag tick

`np.add.at` looks like the vectorized way to build a 2-D histogram and is close
to the slowest thing numpy offers. It is the *unbuffered* ufunc path — it exists
so repeated indices accumulate correctly rather than racing, and it pays for that
by going element at a time. At 126 million elements that is 4,840 ms.

The shape of the call is the tell:

```python
cols = np.repeat(np.arange(frames), blocks)  # 1,010 MB, per call
np.add.at(counts, (idx.ravel(), cols), 1.0)
```

`cols` exists only to say which frame each of 126 million values came from — a
fact the array's own shape already carried. Binning row by row throws the
question away rather than answering it:

```python
for t in range(frames):
    counts[:, t] = np.bincount(idx[t], minlength=bins)
```

599 Python iterations against 126 million scalar increments. The loop that looks
like the slow version is 18x the fast one.

## The bigger error was running it at all

`filter_tab._derive(reuse_band_power=True)` is the cheap tier: value band, count
threshold, D, centered, solo. It exists so that a drag re-derives from the
*retained* `band_power` and runs no transform. That is true and it was not
enough, because `_apply()` then calls `set_series(update.band_power, ...)`
unconditionally, and the band drawn on top of the density surface is not part of
the surface. Every mouse-move rebuilt a picture of an array that had not changed.

`filter_tab._heat_scale` was already doing the right thing three hundred lines
away — `if band_power is not self._heat_source` — for the identical reason, and
its comment says so: "the cheap tier's premise is that `band_power` is the thing
it did *not* recompute." The fix is that guard, applied at the widget.

Identity and not equality. `np.array_equal` over `(T, B)` costs within a small
factor of re-binning, so a comparison that succeeded would have saved nothing.
What makes identity sufficient is a property of `recompute`: it either passes the
previous array through untouched or allocates a new one, and `DetectorUpdate` is
frozen. A cheap tier that ever mutated band power in place would break this
silently, which is the one thing to know before adding one.

## What the clip is for

The rewrite changed one behaviour deliberately. `add.at` clipped bin indices only
at the top, because a value above the maximum was the only case anyone pictured.
A NaN through `astype(np.int32)` is a large negative, and a negative index into
`add.at` wraps — so an undefined block would have been added to the *brightest*
bin and rendered as the loudest thing in the window. `bincount` refuses it
outright instead, which is better and is still a crash in a repaint.

Neither is a histogram, so the value is floored before either path sees it. That
is acceptable here only because the case is unreachable: band power is a sum of
squares, and `block_signal`'s partial edge blocks always average at least one
real pixel, so there is no NaN to floor. If it were reachable, flooring would be
rendering undefined as quiet — rule 6's own example of the thing not to do — and
the right answer would be a bin that reads as absent rather than as low.

## Where the cost went

```
                          before      after
value-band drag tick      ~5,465 ms       0 ms   (identity cache)
expensive derive          ~5,465 ms   1,530 ms   (bincount)
```

The 1,530 ms that remains is `np.log1p` over the whole array and two 505 MB
casts, and it sits inside a derive that is already seconds long rather than
inside a 50 ms drag budget. At the default block size of 64 the entire array is
64 columns and none of this is measurable — which is why it survived until a
workload with 210,672 of them.
