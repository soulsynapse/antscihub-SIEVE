# Capacity beats policy in the render ring

The item proposed replacing the render ring's eviction with a
distance-from-playhead rule and then, correctly, refused to adopt it on the
strength of the argument alone. This is the measurement it asked for.

## The curve

Hit rate against capacity, one recorded session replayed through all three
policies:

| capacity | ring | lru | playhead-distance | ring worst run | pd worst run |
|---:|---:|---:|---:|---:|---:|
| 30 | 4.63% | 4.63% | 4.70% | 2259 | 1981 |
| 120 | 13.19% | 13.19% | 13.95% | 2259 | 1768 |
| **280** | **32.70%** | **32.70%** | **33.39%** | **2005** | **1727** |
| 480 | 56.50% | 56.50% | 57.96% | 2005 | 1727 |
| 720 | 75.17% | 75.17% | 77.19% | 2005 | 1727 |
| 1080 | 75.20% | 75.20% | 78.65% | 2005 | 1537 |

280 is bold because it is where the ring actually runs:
`RENDER_RING_SHARE`'s floor is 256 MB and its comment puts that at ~280 gray
1280-wide proxies.

## Why this settles it

The comparison the item wanted was between two policies at one size. The
answer is that the axis it chose is the wrong one. At 280 frames the policy
choice is worth 0.69 points; the *size* choice between 280 and 720 is worth
42. Whatever is wrong with the ring's hit rate, eviction order is not it —
the ring is simply too small to hold the working set, and no eviction rule
recovers a frame that was never allowed to stay.

The saturation point is the useful second number. Between 720 and 1080 the
plain ring gains 0.03 points, so ~720 frames holds essentially the whole
working set of this session and a share sized past that buys nothing. That
turns "raise the ring" from an open-ended ask into a bounded one.

## Where the proposal survives

`worst_miss_run` — the longest run of consecutive misses, which the module
docstring is careful to call a proxy for stall rather than a millisecond
figure. Distance-from-playhead shortens it at every capacity, by 14% at the
operating point and 23% at 1080, while gaining almost nothing on hit rate.
That is a coherent result rather than noise: evicting what is far from the
playhead does not retain *more* useful frames, it retains *contiguous* ones,
and contiguity is what shortens a stall.

If the ring's share is raised to ~720 on the strength of this finding, the
throughput argument for the second rule weakens further and the stall
argument is all that remains. That is the shape in which the question should
be reopened, if it is.

## Machine generality, and why the number is not a constant

This was measured on one machine with 68.4 GB available and 32 cpus, and the
temptation is to read "raise the ring to 720 frames" off it. That would be
the reference-machine mistake `resolve_worker_split`'s docstring already warns
about in the thread column, transplanted to the byte column.

Two things are and are not portable:

- **Portable: the ordering.** Capacity dominates policy. That is a statement
  about the access pattern — a ring too small to hold the working set cannot
  be rescued by eviction order — and it does not depend on how much memory the
  machine has. The 60:1 ratio at the operating point will vary; the sign will
  not.
- **Not portable: 720.** That is where *this session's* working set stopped
  growing, under the window sizes this user chose. A longer window or a
  slower render moves it. 720 gray 1280-wide proxies is roughly 660 MB, which
  is 1% of the machine measured and 8% of an 8 GB one — the same absolute
  number is a rounding error on one and a serious claim on the other.

Which is why the consequence is expressed as *the share should grow with the
allocation*, not as a new floor. `RENDER_RING_SHARE` currently has
`fraction=0.0` on purpose — the comment says how much of a bigger machine the
ring deserves is this item's question, and growing it there would decide the
policy by side effect. This finding is the answer to that question: the ring
does deserve a fraction, the fraction should be sized so a large machine
reaches its own saturation point, and the floor stays where it is so a small
machine is not starved of something else to pay for it. What a small machine
should do when its saturation point is unaffordable is not settled here and
is the first thing a second measurement on smaller hardware should ask.

For a headless or cluster run the whole framing changes rather than scales:
there is no playhead, no scrub, and no interactive working set, so none of
these numbers transfer. `gui/concurrency.py` is explicit that policy about
sharing a machine belongs to the process sharing one, and a whole-clip pass on
a node is not that process.

## What this cannot say

The scrub column is empty — 16 scrub events in the whole session, none of them
hits, 0.00% under all three policies. The item's own framing puts scrub first
("the latency a user feels"), and this finding does not touch it. A session
driven by dragging the timeline rather than by playback would produce the
missing half, and until one exists the decision recorded here is a throughput
decision wearing no other clothes.
