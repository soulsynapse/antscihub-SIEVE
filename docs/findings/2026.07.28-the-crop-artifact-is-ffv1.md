# The crop artifact is FFV1, and the qp0 route serves wrong pixels

The decision table, all read back through the unchanged `VideoReader`:

```
                          bytes     sequential   seek median   byte-identical
source (luma, baseline)   —         9.93 ms/f    82.4 ms       (is the reference)
FFV1 gray                 48.4 MB   0.093 ms/f    3.86 ms      yes
FFV1 BGR                  72.8 MB   0.154 ms/f    7.08 ms      yes
x264 qp0 gray             48.8 MB   0.129 ms/f   21.7  ms      NO — every frame
x264 qp0 BGR              163.9 MB  0.399 ms/f   65.9  ms      yes
x264 qp0 -g1 gray         57.7 MB   0.075 ms/f    2.53 ms      NO — every frame
x264 qp0 -g1 BGR          188.7 MB  0.191 ms/f    6.47 ms      yes
Zarr gray, zstd           101.6 MB  0.890 ms/f    0.89 ms      yes
```

FFV1 is not a compromise pick: it takes size, sequential decode, and
correctness simultaneously, loses seek only to Zarr (3.9 ms against 0.9 ms,
both far under any budget that will ever ask), and encodes the whole 77 s crop
in under two seconds. The write pass is therefore priced entirely by the
source decode it was already going to do — 46 s luma, 124 s BGR, one render's
worth — which is what makes "materialize while you render" a plausible later
optimization and a needless complication now.

## The identity failure is the half worth remembering

The materialization item pre-stated that `-qp 0`'s advantage would be "reusing
`VideoReader` unchanged." The measurement inverted that clause specifically:
the qp0-gray artifact is a *lossless file that serves wrong pixels*. ffmpeg
silently re-formats gray input to yuvj420p for libx264, the file round-trips
byte-exact through ffmpeg's own decode — and OpenCV's `CONVERT_RGB=0` read of
it hands back an array with the luma plane's exact shape and pixels that
match no frame of the input (max|diff| 195 against its own frame, and no
better against its neighbours). `_check_luma_plane` tests dimensionality and
shape because, for the codecs it was written against, every wrong layout
differed in one of those; here is the codec for which that stops being true.

Two design consequences, both now wired into the todo split: the artifact
writer verifies by reading its own output back through `VideoReader` and
comparing it against what it fed — the one check that catches this failure
class wherever it comes from, and one that survives the same-day demotion of
byte-parity from requirement to bonus, because what it guards against is
garbage, not drift — and any future extension of the luma path to a new codec
starts from the assumption that the shape guard alone proves nothing.
