# The density rebuild is linear in block-frames, and buys one octave below auto

The bound was stated before it was measured, which is the usual way to get a
number wrong by an order of magnitude. It survived: 84.1 ms at B = 16,384
against a 100 ms ceiling, and linear enough across 1k → 16k that the ceiling
can be moved arithmetically if the budget ever changes.

The interesting result is not the confirmation, it is what the bound costs.

## One octave, and the arithmetic that makes it one

The auto block size is 64 *source* pixels, fixed in source coordinates so that
turning the rescale knob changes compute cost rather than where a detection
localizes. On the 5312x2988 reference source that is a 47x83 grid — 3,901
blocks. The floor is 32 working pixels, which is 15,604 blocks. So the entire
legal range below auto is a single halving.

That is not the bound being stingy; it is B growing as the *square* of the
reciprocal block edge. Every halving of the block edge is 4x the blocks and 4x
the rebuild. From 3,901 blocks at 6.3 ms-equivalent, one halving lands at 84 ms
and the next would be 340 ms — three and a half times a perceptual threshold,
on the GUI thread, per partial pass while a window renders. There is no version
of this where two halvings fit.

It also means the bound is nearly invisible in ordinary use and absolute at the
edge, which is the right shape for a refusal: nobody tuning at 64 or 48 will
ever meet it, and the one wheel notch that used to take the session to a
multi-second stall now stops at 32 with a tooltip saying why.

## Why the refusal is cheap

A refused rebuild still pays `m.max()` — 4.5 ms at B = 32,768, 9.4 ms at 65,536
— because the value axis and the band handles have to keep meaning this array's
units even when the surface is not drawn. Leaving the previous grid's histogram
on screen was the alternative and it is the one rule 6 forbids: that image is a
histogram of a different population over a different grid, and it would read as
this one's.

The cost scales with B and not with the refusal, so the pathological case that
started this — B at the crop's whole pixel count, 210,672 in the original
finding — costs a single pass over the array rather than the log1p, the two
casts, and the bincount loop. That is the difference between a notice appearing
in tens of milliseconds and a window that stops answering.

## What would flip the conclusion

A `density_rebuild` measurement above 100 ms at B = 16,384 on the reference
workstation means the binning regressed, not that the bound is wrong — the
linearity above is what licenses that reading, since a genuine change in the
bound's *correctness* would have to come from the budget moving, and the budget
is anchored to the ~100 ms perceptual threshold rather than to this code.

The one measurement that would move the bound is the row-wise log1p: if the
histogram-identity question in the previous finding is settled in its favour,
the same ceiling admits roughly B = 28,000, which is still not two octaves.
