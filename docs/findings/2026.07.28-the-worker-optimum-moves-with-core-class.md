# The worker optimum moves with core class

## Why the cells are interleaved, and what it costs

The probe that led here measured `density_surface` in blocks: eight readings at
82-87 ms, then every reading after at 100-147 ms, with no condition changed.
The scheduler migrates a thread off the performance cores as it accumulates
runtime, so in a blocked design whichever treatment ran first got the fast
cores and the result would have been a measurement of running order. Every cell
here is therefore sampled round-robin. That does not remove the drift — nothing
at this layer can — it stops the drift from having a preferred cell.

It is not free. Interleaving means each cell's reads are separated by five
other cells' reads, so no cell keeps the file cache or decoder state it warmed,
and every absolute number here is worse than the same configuration measured
alone. That is the whole of why these readings must not be compared with
`2026.07.28-the-luma-path-has-almost-nothing-left-to-thread.md`, which measured
2 workers at 6.52 ms against 7.96 here. Neither is wrong. They answer different
questions and only one of them can answer this one, because a blocked design
cannot separate the treatment from the order.

## What a controller would have to be denominated in

The compensation result is the load-bearing one. At one worker the two core
classes differ by 1.67x, which is roughly the ratio the density surface showed.
At each class's own optimum they differ by 1.22x. Adding a worker recovers much
of what a slower core lost — so the right worker count is a function of the
core class the work lands on, and `resolve_workers` takes `available_cpus()`,
an integer in which the two classes are indistinguishable. This is not the
constant being tuned to the wrong machine, which is what
`docs/todo/adaptive-worker-allocation.md`'s trigger was written against. It is
the constant being denominated in a unit that is not uniform on the machine it
was tuned on.

That kills the item's own preferred cheap answer as well as the flat-surface
one. A one-shot calibration cached against a machine fingerprint measures a
fresh, short-lived process — which is exactly the condition under which the
scheduler has not yet demoted anything — and then applies that number to a
session that has been open for ten minutes and is running on E-cores.

## What would flip this

A machine with one efficiency class showing the same 2x spread would mean the
gradient is about worker count alone and the core-class half is a local
curiosity; the sweep reports `class0x<n>` only, so this is one command on any
uniform box. Conversely, a P-core optimum of 3 rather than 2 on a second run
would mean the 2-vs-3 split is inside the noise and only the *spread* survives
— the three repeats separate 7.96 from 8.55 by more than their own
best-to-typical gap, and the disturbed run put the same two at 8.33 and 8.79,
so the ordering has now held twice. It is still the thinnest claim here.
