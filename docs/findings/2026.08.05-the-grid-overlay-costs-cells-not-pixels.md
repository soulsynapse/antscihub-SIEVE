# The composite grid overlay cost cells, not pixels

## Why the slider read as an application-wide setting

The heat layer covers *every* cell — that is its argument, and the tests pin it:
an out-of-band cell is bare heat, not bare footage. So it is the one layer whose
cost is B unconditionally, while the ring layer's is B times the detected
fraction, which in a tuned detector is small. That asymmetry is the whole
report. With the slider at zero the pane painted two images and a few hundred
rings; with it anywhere else it painted 16,384 `QColor` constructions and
16,384 `fillRect` calls, on the GUI thread, before every frame and after every
hover crossing. Nothing else in the application got slower — everything else
was waiting behind the paint.

## Why not a cell-resolution image scaled by Qt

The obvious cheaper draw is a `(ny, nx)` image scaled into the grid rect with
smoothing off, and it is wrong here for a reason that does not show up in a
benchmark. `grid_edges` rounds the *line* rather than each cell's origin, which
is what closed the 1 px seam this overlay used to draw, and `block_at` reads the
same list so the cell under the pointer is the cell the pointer is over. Qt's
scale re-derives those boundaries under its own rounding, so the heat layer
would land a pixel off the ring layer and off the hit test wherever the two
rules disagree — a heatmap describing the neighbour of the pixels under it.
Expanding by `np.repeat` over the widths `grid_edges` already computed cannot
disagree with it: the pixels are the ones the loop drew, and the measurement
above says so to within the ramp table's own 4/255 quantization.
