# The swap axis is built, and what stops it is identity

## The half that already runs

Choosing per machine is not aspirational here; it is load-bearing on the axis
where it is safe. `core/shares.py` divides threads and bytes as
fractions-with-floors, `gui/resource_probe.py` samples the session against
`ledger_ceiling` every second, and
`2026.07.28-the-worker-optimum-moves-with-core-class.md` is the measurement
saying the right number is a property of the box. Same result, different speed,
decided by the machine, and none of it reaches a cache key.

That is the whole distinction. A schedule — how many threads, which pool, how
much slab — cannot change what a frame *is*, so nothing about picking it per
machine can make two runs disagree. An implementation can, and usually does.

## Why the second half stays parked

The mechanism for it is complete: registration per `(filter_id, version,
backend)`, a preference order, a runtime check that separates "no kernel
written" from "no runtime here", and a spec field —
`backend_agnostic`, in the identity channel, validated to imply `deterministic`
— by which a filter declares that its implementations agree. What is missing is
any filter that can truthfully declare it, and that is a fact about
floating-point arithmetic rather than about this repo's maturity.

So the trigger on `docs/todo/gpu-execution.md` is the right instrument and
should not be pre-empted: a filter whose CPU kernel is *measurably* the
bottleneck, with `bench/budgets.py` being missed because of it. Two things
would be built the day it fires and not before — a cross-backend equivalence
harness, whose seam is already cut (`select`'s one-element preference tuple
exists, in its docstring's words, so "a cross-backend equivalence test [can]
drive both sides"), and the A/B timing helper `bench/` has no reason to hold
yet. Building either now is an instrument with nothing to measure, which is
the failure mode the v1 doc tree died of.

## The version of the idea that is right

An adjudicating module picking the best implementation for the hardware is
correct wherever the implementations are the same result, and this repo already
says exactly where that is: `backend_agnostic and deterministic`. Elsewhere it
trades reproducibility for speed on a tool whose output is a published event
table, and an upgrade or a machine change that silently restates which events
were claimed is rule 6 at the level of the whole artifact. The generalization
worth carrying: interchangeability is a claim about *results*, so it belongs in
the identity channel and has to be declared and tested — never inferred from
two functions having the same signature.
