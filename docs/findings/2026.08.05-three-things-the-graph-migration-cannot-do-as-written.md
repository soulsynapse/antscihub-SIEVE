# Three things the graph migration cannot do as it was written

## The layer obstruction is the one that changes the design

The item asks for `model_validator(mode="before")` on `Project`, and the
reasoning is sound as far as it goes: an upgrade belongs where the document is
parsed, and pydantic gives a before-validator the raw mapping. What it misses
is what the upgrade has to *write*. A synthesized node carries a `filter_id`, a
`version`, and parameters at values only the filter knows — `crop.WHOLE_FRAME`
and `SpanParams()`'s defaults, both of which exist precisely because a writer
that has not opened the video needs a way to say "the whole of it".

Every one of those is a fact about `sieve.filters`, and `core/pipeline_model.py`
is the one module in the repo whose docstring makes a point of not knowing them:
"Deliberately not registry-aware … The split is what lets a project open on a
machine where a filter is missing." Writing the validator there would trade that
property for the convenience of a hook, and the trade is machine-checked against
you — `test_no_filter_id_is_spelled_outside_its_module_undeclared` fails, and
the fix is three permanent entries on a shrink-only list whose entries are
supposed to be the rework's work list.

So the upgrade is `src/sieve/pipeline/upgrade.py`, above `sieve.filters` in the
layer contract, and it types no filter id: the ids and versions come off
`CropParams.spec()` and `SpanParams.spec()`, and the identity values come from
the modules that own them. The consequence the flip inherits is in
`open_questions` above and is not small: if the upgrade cannot be a validator,
`Project.load` cannot be the v6 entry point either.

## The detector cannot be carried, on semantics before scope

`filters/detect.py` registers `Mode.WINDOWED` with a kernel that takes a
`FrameSpan` and returns the gate for `span.target` — trailing, causal,
per-frame. `Project.detector` is read by `detect_series`, which runs the Morlet
transform over the *whole collected series* and gates it with `centered=True`
by default. The completed entry for that filter settles the point in as many
words: do not route schema-v5 centered whole-record detection through the
executor's trailing windowed kernel.

A detect node synthesized from `Project.detector` would therefore be a node
that computes something else. It would produce a plausible gate channel of
exactly the right length, which is the migration's named failure mode arriving
through the one field the parity instrument was not built to watch — the parity
test diffs claimed intervals, and both sides would be claiming from the same
new semantics after the flip.

`carry_into_graph` refuses such a document by name rather than dropping the
field, and that refusal is the honest form of this finding in code.

## The fps problem is smaller and worth stating anyway

`DetectParams.fps` has no home in the artifact. `Project` records a source
*path*, and `2026.08.05-exact-source-frame-rate.md` settles that the rate is the
container's rational, probed off the stream — a fact about the file, not about
the document. A document-to-document transform cannot know it.

It is recoverable in practice, because a v5 project with a tuned detector has a
`block_signal` node upstream and that node's params carry `fps` as a float. But
recovering it that way is correct by luck: it depends on the detection suffix
always sitting above a filter that happens to declare the rate, and a project
that carries a detector and no such node would fall back to the field default of
30.0 — which is wrong for 30000/1001 in the direction that moves the Morlet
bank and therefore what is claimed as an event. That is rule 6's failure exactly:
a number that looks better founded than it is.
