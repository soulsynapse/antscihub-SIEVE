# Rescale cost is a local fit, not a filter table

The useful model survived the port: decode/source acquisition is a whole-frame
floor and downstream image work follows the number of rescaled pixels. The
lever therefore needs two observed scales in one comparable context before it
can answer the user's actual question: whether losing another percent of
resolution buys at least another percent of time.

This is the anchor allowed by the work-unit decision, not the coefficient table
it forbids. `CostEstimate` remains a machine-independent work declaration. The
new coefficients are a runtime calibration from completed preview spans on the
current source, window, replicate, and non-scale chain context. They are not
attached to filter declarations and are discarded when that context changes.

The one-scale branch is load-bearing. It is tempting to show the measured
milliseconds from the one pass the user just ran, but that number cannot say how
much of the pass was fixed floor and how much moved with scale. Showing a knee
from that observation would make aggressive downsampling look more justified
than the evidence supports, so the GUI says only that another scale is needed.
