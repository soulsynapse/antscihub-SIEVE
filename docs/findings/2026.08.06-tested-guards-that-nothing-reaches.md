# The overnight batch's defects are guards nothing reaches

The reverted phase-2 batch failed at the process level: the agent wrote the
problem, the steps, and the completion criteria, then judged itself against
them. That is not what happened here. All six of these items were already in
`docs/todo/` with criteria somebody else had written, and all six built what
their entries say they built — `gui/wizard_lifecycle.py` really does own the
wizard session with no back-reference to the tab, `tests/gui/test_preference_boundary.py`
really does derive the preference list reflectively so a new preference fails
the test rather than slipping past, and `frame-shrinks-before-bgr` is a clean
measurement whose negative result (the lowered route changes nearly every
pixel) is what made the next item safe to build.

The defect that recurs instead is narrower and easier to miss, because
everything compiles, every test passes, and each piece reads well on its own:
**machinery that is written and tested but that nothing in the running system
reaches.**

`protected_nodes` is the clearest instance. It is a real safety concern —
lowering the node the user is currently dragging moves that node's parameters
into an FFmpeg command line — and it is designed correctly, threaded through
two functions, checked against both the crop and the scale candidate, and
covered by a test. No production call site passes it. The test certifies a
mechanism that cannot fire.

The rescale sampler is the same shape wearing different clothes. The finding
that produced the `F + M*s^2` model records every probe as "0 from cache",
because whoever ran it knew a warm render is not a measurement of decode. The
runtime sampler that shipped alongside it reads `render.frames` off the same
`PreviewRender` that carries `reuse` and ignores the field. The control existed
in the probe and did not survive into the code the probe justified.

Both are invisible to the gate for the same reason: nothing in `nox -s checks`
can tell a parameter that is never passed from one that is passed and happens
not to matter, or a sample set that mixes regimes from one that does not.

## What was fixed

`gui/rescale_cost.py` now refuses in three cases instead of reporting a curve,
and each refusal carries its own reason rather than leaving the caller to
reconstruct one — which is rule 6's "a refused control must name its reason"
applied to the thing that is actually refusing. Samples whose `reuse` differs
by more than `REUSE_SPREAD_LIMIT` do not fit. A fit whose `M` or `F` comes out
negative is refused rather than clamped. And once three distinct scales exist
there is a residual to test the curve against, so `MIN_FIT_QUALITY` can reject
a fit the samples do not support.

The two-scale case is the interesting one. It is the minimum the model needs
and it passes through both points by construction, so nothing about it could
have come out wrong. It is still reported — withholding it would trade an
overclaim for no readout at all — but the label marks the projection with `~`
and the tooltip says a third scale is what would test it. That is the honest
position for an exactly-determined fit, and it is a different position from
both "show the number" and "show nothing".

## What was not fixed, and why it is not a small edit

The rule 3 violation in `lowering.py` cannot be repaired by moving the three
`if` branches somewhere tidier. The reason that file enumerates filters is that
there is no way from outside a filter to ask what extents it emits for a given
input — `FilterSpec` declares `accepts`, `emits`, `element` and `cost`, none of
which is a shape function. Lowering needs exactly that, and so would any future
consumer that wants to reason about a chain's geometry without running it.
Until that exists, the geometry stays duplicated; a shape declaration on the
spec is the fix, and it is an architecture item rather than a cleanup.
