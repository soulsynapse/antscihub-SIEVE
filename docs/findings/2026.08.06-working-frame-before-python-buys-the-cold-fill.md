# Working-size frames before Python buy the cold fill

The cheap threading and luma wins are already taken, and this measurement
shows the remaining gap is still the size of the frame that reaches Python.
The current route reads a 15.9 MB luma frame for each source frame, then keeps
only a 272x235 ROI and finally a 136x117 working frame. In the same window,
the FFmpeg route crosses the process boundary with only that working frame.

This is not a transparent decoder swap. The route changes both the scaler and
the gray convention, and it may change dtype. That is fine only if the source
ancestor key names it. The implementation question is therefore a lowering
question, not a `VideoReader` optimization: identify a safe root prefix,
replace it with a lowered source whose identity includes the prefix, and refuse
every case whose coordinate space is not still the source frame.

The odd-origin probe is the correctness guardrail. The current reference ROI
is even, so this session could have missed it by testing only the happy path.
v2's ROI type has no even-origin restriction, and the crop filter's parameter
is in integer pixels. Any FFmpeg crop route that omits `exact=1` is wrong for
legal v2 inputs.
