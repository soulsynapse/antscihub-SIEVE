# A lookahead node's half-served window is refused by FrameSpan, not by the gate

The prediction going in was `detect`'s: it is the node with the lookahead, so it
is the one whose needed input range and emitted range come apart, and the
expectation was a window quietly assembled from stale frames. That is not what
happens, and the reason is a property of the loop rather than of the tool. A
node keeps its history in one deque appended to in reading order. If the appends
stop while the store answers and resume when it stops, the deque holds frames
from before the gap and one frame from after it — so the very first window built
after a served range straddles the gap, and `FrameSpan` refuses a span that is
not consecutive. There is no arrangement of hit and miss that produces a short
window instead of a discontiguous one, because the window is assembled on the
first append after the gap.

`block_signal` has no such guard and cannot have one: its state is inside the
tool, the executor cannot see what it has consumed, and a state that stopped
twenty frames back produces exactly the shape a settled one does. That
asymmetry is the argument for the bit-identity gate being a comparison of
arrays rather than an absence of exceptions.

What would flip this: a windowed node whose history the executor holds
*elsewhere* — a ring rather than a deque, or per-target slicing — would lose the
consecutiveness check with nothing announcing the loss. The check is real and it
is not the loop's own; it belongs to a type this module happens to build.
