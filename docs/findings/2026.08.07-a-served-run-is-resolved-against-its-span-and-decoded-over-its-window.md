# A served run is resolved against its span and decoded over its window

The seam is one argument. `resolve` takes `want: SourceSpan` and declines a
record that does not cover it, which is right; the caller passes the span it
asked for, and the executor then reads `plan.decode_range` — the span widened
by `lead_in` at the near end and `lookahead` at the far one. Everything between
those two intervals is a frame the resolver certified and the file does not
hold.

Nothing catches it because the only graph the suite serves is `crop ->
downsample`, and both are streaming. `test_crop_serving.py` says so in its own
docstring about a different clause; the window never comes up, so the five
cases pass over a seam that fails on the first graph with a stateful tool in
it — which is every graph in `PLAN.md`'s Phase 4 list except the two used here.

Why the fix is the caller's argument and not a floor on the plan: `lead_in` and
`lookahead` fold over `dag` and `params` alone (`_fold`), and `source` enters
`ExecutionPlan.build` only to key with. So a caller can build a plan to learn
`decode_range`, resolve against that, and rebuild on whichever identity comes
back — two passes over an object that opens no container. The elision does not
perturb it either, because the only node a served run elides is `crop`, which
declares no window.

What would have to be true for this to be wrong: a record whose span is exactly
the run's span would have to be servable for a windowed graph, which requires
the missing frames to come from somewhere. They can only come from the parent,
and mixing artifact and parent pixels in one run under one root key is the
failure `resolve_source.py`'s own docstring spends a paragraph refusing. So
declining is the only answer available, and the only question this leaves is
whether a *wider* cut should be written in the first place — which is
materialization's question, not resolution's.
