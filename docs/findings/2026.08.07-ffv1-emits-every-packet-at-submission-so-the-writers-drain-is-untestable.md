# FFV1 emits every packet at submission, so the writer's drain is untestable

The line is right and should stay. `write_ffv1`'s signature takes an `Iterable`
and its docstring promises one resident frame at a time, which is a shape that
would be wrong without the drain the moment the codec name changed — and the
codec name is a `str` argument to `add_stream`, one character from being
something else. What the measurement settles is only that no test can hold it
to that, so its correctness is carried by the docstring rather than by the
suite.

The prediction that would have made this a coverage gap instead: a drain
returning even one packet for FFV1 at any frame count. It returns zero at six,
and the mechanism says it returns zero at any — an intra-only encoder has
nothing to hold back, since every packet depends on exactly the frame that was
just handed to it. libx264's 12-of-12 is the same mechanism read from the other
end: everything it emits depends on frames it has not seen yet.
