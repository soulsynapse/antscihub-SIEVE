# The clause-per-case rule covers the predicate and not the helpers under it

`test_crop_binding.py` opens by arguing that a single "the mismatch shows as
stale" case would pass with three of the four clauses deleted, and it is right:
it writes one case per clause of `CropRecord.backs` and each of those mutants
dies. What it does not notice is that `backing_for` is not a wrapper around
`backs`. It adds a window comparison, a near-miss walk anchored on region
equality, an orphan walk guarded by parentage, and an overlap predicate — four
more clause-bearing pieces of logic, written in the same commit, with no
enumeration anywhere to write cases against.

The pattern is worth stating because it is invisible from inside the file. A
run that adopts "one case per clause" reads the *imported* predicate's docstring
for the clause list, because that is where a clause list exists. Clauses it
authored in the same session have no docstring to enumerate them yet, so they
fall outside the rule at exactly the moment they are least reviewed.

The survivors are all narrow — boundary cases and guards that are currently
reached only in company with a second condition that would decide the same way.
That narrowness is why this is a pool item and not a reopen: a suite that
discriminates on every load-bearing clause and misses four boundaries is a
suite that would catch a rewrite of the module, which is what a regression
suite is for.
