# The detection chain's two non-finite guards survive their own cases

Both survivors fail for the same reason, and it is not carelessness in the
ported cases — it is that the comparison semantics already do the job the guard
was written for.

`inband_count`'s docstring says a NaN "must not become a detection by comparing
true against `-inf`". It cannot: every IEEE comparison against NaN is false, so
`arr >= -inf` is already false for a NaN block. The ported case
(`test_chain_end_to_end_with_nan_blocks_and_intervals`) feeds a NaN column and
asserts the count is 9 rather than 10, and that assertion holds with the guard
deleted. What the guard *does* exclude is `+inf`, which passes both
comparisons under an unbounded band — a block power no current tool produces,
which is why nothing sees the difference.

`count_band_to_counts`'s guard is the same shape one level up. "Unbounded above
is not a fraction and does not denominate" reads as a claim about `inf`, but
`inf * 12` is `inf`, so the multiply is harmless at every positive element
count. The one input where the branch decides anything is zero elements, where
`inf * 0` is NaN and every subsequent `w <= NaN` is false — an armed detector
that silently claims nothing.

One more result is worth carrying out of the table even though it is a kill.
`_window_future → 0` — the mutant that drops the forward half of the detection
window from the declaration — is caught only by
`test_both_halves_of_the_window_are_declared`, and not by the executor's gate
parity. That is not a gap in the parity case: at the golden's configuration the
transform's reach is 29 frames and the window's forward half is 7, so the
declared lookahead is the transform's number and the mutant does not move it.
A case that reached it through the executor would need a band high enough that
the detection window is the wider claim, which is a different fixture rather
than a different assertion.
