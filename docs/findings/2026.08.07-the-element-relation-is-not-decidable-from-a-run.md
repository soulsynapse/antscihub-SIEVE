# The element relation is not decidable from a run

The prediction that would have made this positive: an aggregating tool emits
strictly fewer values than it consumed, and a preserving one emits exactly as
many. Both halves fail against tools already on the shelf, and they fail in
opposite directions, which is why no threshold rescues the rule.

`rescale` kills the first half. It declares `AGGREGATED` and its `scale`
defaults to `1.0`, so the shipped default configuration emits exactly what it
consumed — the declaration is a claim over the legal parameter range and the
run only ever sees one point of it. Sweeping the range would fix that one tool
and not the rule: the configuration a run has to pick would then be derived
from parameter bounds, which is a second thing that can be wrong.

`crop` kills the second half, and kills it as a matter of meaning rather than of
configuration. Cropping decides *which* values survive and never what one of
them is a value of — a count over a crop of `block_signal`'s output is still a
count of blocks — so `crop` is `PRESERVED` while emitting a fraction of the
elements it was handed. A rule reading "preserving means the count is
unchanged" would convict it, and the tool is right.

What survives is the part where the count *is* the claim. `ElementKind.FRAME`
says one value describes the source frame as a whole, and "the run handed back
one value for an input of many" is exactly that sentence; the gate asserts the
equivalence in both directions, so a tool that quietly stopped reducing to a
scalar fails even though its declaration still parses. `ElementKind.BLOCK` says
the frame was divided into a grid, which is decidable as strictly coarser than
the input and strictly finer than a scalar — necessary but not sufficient,
since an aggregating relation looks identical from here.
