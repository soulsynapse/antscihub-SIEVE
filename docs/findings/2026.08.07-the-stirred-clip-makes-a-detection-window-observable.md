# The stirred clip makes a detection window observable; the ramp cannot

The interesting number is not that the clip has bursts — it was written to have
bursts — but the size of the gap between the two fixtures at the point a parity
oracle reads them. Over `synthetic_video` the per-frame in-band count has
exactly two reachable values, 0 and 80, at *every* floor including ones taken
from its own distribution. That is not a hard fixture to detect on; it is a
fixture on which the detection window, the count threshold and the value band
are simultaneously unobservable in the output, so an oracle comparing two front
ends over it certifies nothing about any of the three.

What a passing result for the ramp would have looked like: some floor at which
its count takes an intermediate value, which needs some spread across blocks
within a frame. The spread is 6e-8 — the frames are uniform by construction and
mp4v keeps them uniform (the earlier fixture finding measured per-frame
peak-to-peak of exactly 0 on the written channel). There is no floor to find.

The margin on the stirred clip's side is comfortable in time (a factor of 2547
between a burst frame and the still footage) and thin where it should
be: the three windows' intervals differ by one or two frames each, which is
what makes them a test of the window rather than of the burst. A front end that
resolved a per-replicate `D` and one that ignored it disagree by exactly that
much, so this is the resolution the oracle is measuring at.
