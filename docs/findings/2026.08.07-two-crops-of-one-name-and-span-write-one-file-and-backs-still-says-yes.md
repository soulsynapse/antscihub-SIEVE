# Two crops of one name and span write one file, and backs still says yes

The whole point of 05.1 is that an artifact which is not what it claims to be
must not be registered, and the verification pass it ports is a good guard
against the failure v2 measured — an encoder that lies. It is no guard at all
against this one, because at the moment `_verify` runs there is nothing wrong:
the file it reads back genuinely is the crop that was just fed to it. The lie
arrives later, and it arrives in the *first* record, which nothing re-checks.

What would have refuted the concern: `identity()` including the path, or
`artifact_filename` taking the region. Neither is true — `identity()`'s
docstring explicitly excludes the path ("writing the same cut twice to two names
is one cut recorded twice"), which is the right rule for the opposite direction
and leaves this one open. Two distinct cuts sharing one name is not the same
question as one cut under two names, and only the second is handled.

The reason this is a finding rather than a line in the item is the second
measurement. It reads like a v3 porting slip and it is not: v2 shipped it, ran
long enough to be the evidence base, and never hit it — which is itself the
useful datum, because it means the collision is rare rather than impossible and
a reviewer of the eventual fix should not expect a v2 regression test to exist.
