# v2's pipeline/ does not separate from the schema it is written against

The port disposition reads as a per-file judgement — this file held, that one
did not — and for `core/types.py` and `decode/` that is what it is. It stops
being that at `pipeline/`, because what `dag.py` and `plan.py` are is a
function from a `Pipeline` to something walkable. Change the input type and the
body is not the same body; the modules do not "depend on" the schema in the
sense of importing a utility, they are written in its vocabulary. `node_key`'s
docstring makes the point without meaning to: the signature takes a `Node` and
a `Replicate` *rather than a parameter dict*, deliberately, so that
`Node.params` cannot be passed by mistake. That argument does not survive being
handed a different `Node`.

The prediction that would have refuted this: if the graph layer touched the
schema only for field access, a re-derived `Node` with the same field names
under ADR-1's renames would carry the port. It does not, on two counts —
`adr/v2-does-not-import.md` forbids v3 spelling a v2 field name anywhere in
`src/`, and `adr/detector-is-a-node.md` changes the node set itself, so the
graph the ported `Dag` validates is not the graph schema v1 describes.

The backend blocker is separable from the schema one and is the sharper of the
two, because it has a right answer that nobody has written down. v3 drops
`backend/`, so there is exactly one backend; the honest key for a
one-backend build either omits the position or pins it to a constant. Both are
defensible and they are not the same edit — omitting it makes v3 keys
permanently incomparable to v2's, pinning it keeps the shape for the day the
"Not built" table's revival condition fires. Choosing is a decision, and
02.2 is a port.
