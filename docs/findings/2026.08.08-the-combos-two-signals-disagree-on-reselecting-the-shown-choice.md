# The combo's two signals disagree on re-picking the choice already shown

The superseded finding is right that the mutant survives and right that the
arrow case can no longer separate the two signals. Where it goes wrong is the
step from there to "indistinguishable for this widget": it enumerates the
states a `_ChoiceCombo` can reach, finds only programmatic `setCurrentIndex`,
and declares the survivor equivalent. The enumeration is missing the state Qt
documents `activated` *for* — a selection from the popup — in the case where
the selection lands on the entry already current. `activated` fires; the index
did not change, so `currentIndexChanged` does not.

That is not a curiosity, because the module has a rule about exactly this. The
item the work came from is titled "a value passed through is not one", and the
docstring on `_enum` says a parameter edit "has to be exactly" the user's
choice because "every value merely passed through is a re-plan, a new cache key
and a render". Opening a list and closing it on the value that was already
there is the purest instance of the thing being ruled out, and it is the one
instance the shipped signal admits. `Session.commit` appends unconditionally,
so the cost is a duplicate undo entry as well — the user's next Ctrl-Z appears
to do nothing.

The reason to write this down as a loop matter as well as a Qt one is the
shape: a surviving mutant was closed by an argument rather than by a case, and
an argument that no test *could* separate two expressions is a claim about the
whole reachable state space, which is the hardest kind of claim to check and
the easiest to write. See
`findings/loop/2026.08.08-an-equivalent-mutant-is-a-claim-about-every-reachable-state.md`.
