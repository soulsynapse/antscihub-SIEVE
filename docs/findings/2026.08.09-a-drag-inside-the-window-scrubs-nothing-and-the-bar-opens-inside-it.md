# A drag inside the window scrubs nothing, and the bar opens inside it

Before 09.6 the band was a scrub everywhere except a nine-pixel header stripe
and two six-pixel edges. After it the band is a scrub only strictly outside the
working window, and the window at open is the whole source. The two gestures
that used to share those pixels were a click (seek here) and a drag (preview
frames as I pass them). 09.6 argued the collision at length and resolved it for
the click — a press that never travels becomes `committed` on release — and the
drag has no equivalent, because travel is exactly what makes the gesture a
move.

What makes this worth a file rather than a line in a review is the direction of
the invisibility. The click restoration is the loud half: it has a case
(`test_a_click_on_the_body_seeks_on_release_and_not_on_press`), a paragraph in
the commit body, and a paragraph in the run's account. The drag half is named
once — "costs the band a scrub it used to have there" — and then the sentence
moves on to the remedy for the other one. Nothing in the tree went red, because
the only cases that exercise a drag scrub drive a strip with no window, which is
a state `TimelineBar` never produces.

The prediction that would refute this reading: if the drag scrub were still
reachable in the state the user opens in, the probe above would show `scrubbed`
filling as the cursor travelled. It is empty, and the one signal that does fire
carries a window origin the window already had.
