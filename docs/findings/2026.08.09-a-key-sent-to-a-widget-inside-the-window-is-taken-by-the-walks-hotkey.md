# A key sent to a widget inside the window is taken by the walk's hotkey

`bind_navigation_hotkeys` puts four `QShortcut`s on the window — Left, Right, Up,
Down — and a `QShortcut`'s default context is `Qt.WindowShortcut`, matched inside
`QApplication::notify` before the event is dispatched to a child. Every case in
`tests/gui/test_param_generator.py` that opens a combo's popup with Down works
because there is no window over it; the same two lines inside a `MainWindow`
drive the walk instead, and the walk's `_redraw` calls `refill_graph`, which
marks the graph stale.

That is what makes it worth recording rather than merely fixing: the contaminated
gesture is red *for the shape the case was written to catch*. A case asserting
"the panel is not stale after a no-op edit" fails identically whether the defect
is present or the key was stolen, so the proof of red does not distinguish them
and the fix appears not to work. What separated them here was listening to
`ParamForm.edited`: the walk's mark arrives with that signal silent, and the
defect's arrives with it emitted.

`_ChoiceCombo` treats PageDown, PageUp, Home and End as navigation keys for its
own reason — each steps a closed combo and emits `activated` on the way past —
so any of the four opens the popup, and none of them is bound on the window.

## Amendment 2026-08-09: the theft has a precondition, and it is activation

Measured while writing `tests/gui/test_pinned_slot.py`, which drives P — the pin
hotkey — the same way this finding says Down is driven. It did not fire. The
probe: a `MainWindow` built by the fixture, `driving.key(pane, Key_Down)` sent to
a plain pane inside it, and `window.current_node` read after.

- After `show()`: `QApplication.activeWindow()` is `None` and the walk does not
  move — the key reaches the pane it was addressed to and nothing takes it.
- After `show()`, `activateWindow()` and a `driving.pump()`: `activeWindow()` is
  the window, and the same key moves the walk. Both `activateWindow()` and the
  drain are needed; the call alone left the window unactivated for the key sent
  on the next line.

So the mechanism above is right and incomplete: `QShortcut`'s default context is
`Qt.WindowShortcut`, and the map declines a shortcut whose window is not the
active one. Activation is delivered as an event rather than set by the call,
which is why the drain is load-bearing and not decoration.

Which means the theft this finding is named for is a *conditional* hazard rather
than a standing one, and the condition is one a test arranges deliberately. A
case that drives a hotkey has to show and activate first, and a case that drives
a widget's own key handling is safe from the walk on any window that has not been
activated — including, for the two files here, on no window at all.

## Amendment 2026-08-09: a redraw takes the activation with it

Measured while writing `tests/gui/test_add_box.py`, whose fixture began as a
copy of the one above — `show()`, `activateWindow()`, one `driving.pump()`,
then `open_project`. The A shortcut fired for the first window a process opened
and for none after it, in the same file, from the same three lines. A longer
wait did not help: `driving.wait_until(activeWindow() is opened, 500)` gave five
of five in a standalone script and timed out on five of eleven cases under
pytest, which ruled out "the drain was too short" and left the order of the
lines as the thing to probe.

Two probes, and the second is the mechanism.

- A parametrized fixture opening eight windows in one process, each shown,
  activated and pumped, with the test bodies varied. Bodies that do nothing:
  activated 8/8. Bodies calling `window._redraw()`, `go_down()` or `add_step()`
  — all three reach `_redraw` — activated 1/8, the first only.
- Inside a single window: `activeWindow()` is the window before `_redraw()`,
  **still** the window immediately after it, `None` after the next
  `driving.pump()`, and the window again after another `activateWindow()`.

So it is not about which window in the process. `Control._SlidingPanes.replace_pane`
hides the pane it replaces, reparents it to `None` and calls `deleteLater()`; a
parentless `QWidget` is a top-level window to Qt, and draining that deferred
deletion is what leaves the application with no active window. `open_project`
redraws, so the amendment above's order — activate, then open — activates a
window and then immediately loses it, and every later `activateWindow()` in that
process is racing pending deletions from the window before.

The rule that follows, and what this file's cases do: activate **after** the
redraw rather than before it, and again after any redraw a case drives. With
that order, eight fixture windows in one process activated 8/8 and every A sent
to their panes opened a box.

`tests/gui/test_add_box.py` does both — it activates after `open_project`, and
its hotkey case re-activates between the two keys it sends. It also asserts the
box's bindings by reading the window's `QShortcut` children, because *which* key
is enabled when is the claim (enter and esc are live only while a box is open)
and reading it is exact where driving it is a sample.

Left open: `tests/gui/test_app.py` shows its window and does not activate it, so
on this reading the Down it avoids would not have been stolen there either. The
comment beside its PageDown is therefore either about a state that probe had and
this one did not, or about a hazard that case never faced. Nothing is red either
way — PageDown drives the popup regardless — so it is recorded rather than
chased.
