# A node-keyed input hash refuses the replicate that deviates its path

`8f4a92e` added `Project.input_hashes` as `dict[str, str]`, node id to
`content_hash`, and argued the keying in the field comment: keyed by node "and
not by path because the path is already a parameter and resolves per replicate;
what is being claimed is what a *node* reads." That clause is where it comes
apart. A path parameter resolving per replicate is precisely the condition under
which one node reads two files in one run, and a mapping with one slot per node
cannot hold two claims. `Replicate.overrides` is sparse over arbitrary parameter
names and asks nothing about stereotype, so nothing makes a path parameter the
exception.

`a50027a` made it observable by adding the only caller. `_external_inputs` loops
the walk per replicate and calls `check_input_hashes` inside that loop with the
files that replicate resolved, so every replicate is compared against one
recorded hash and at most one can match. The refusal is the safe direction — it
stops a run rather than producing wrong numbers — but the remedy the message
gives is the one that cannot work: re-recording moves the refusal to the other
replicate.

The reason this is filed `open` and not queued as a fix is that the case is
doubly unreachable. Nothing in `src/` records a hash, and the scenario that
would want two files under one node — an A/B of two backgrounds — was ruled out
of VISION a day earlier by
[whether-vision-states-the-background-ab](../todo/whether-vision-states-the-background-ab.md):
VISION binds a picked file *standing in for* a generated one, not tuning by
comparison between two. So the schema is not wrong about anything the product
currently promises; it is narrower than `Replicate.overrides` is, and that gap
is what will be there on the day the A/B returns from PLAN.md's revival table.

## The live half: a docstring citing VISION for a case VISION was ruled not to state

`run_cmd._external_inputs` justifies looping per replicate with "an A/B of two
backgrounds is that deviation, which is the case VISION states." `docs/VISION.md`
contains no A/B, no per-replicate deviation, and no second background, and the
`done` item above ruled a day earlier that it does not and that restoring it
would be its own paragraph saying what it costs.

The loop itself is right on other grounds — `resolved_params` merges overrides,
so `source_files` genuinely differs per replicate, and a walk done once would be
wrong for any deviated path. Only the citation is false. It is worth correcting
rather than shrugging at because of what it would do next: a worker reading that
docstring meets an assertion that VISION states the A/B, from a file more recent
and more central than the item that ruled otherwise, and the ruling loses. That
is the failure
[an item is drafted against an alternative a done item already refused](loop/2026.08.08-an-item-is-drafted-against-an-alternative-a-done-item-already-refused.md)
records, running one step further than it did: not a ruling re-derived at cost,
but a ruling contradicted in the tree with nothing red.
