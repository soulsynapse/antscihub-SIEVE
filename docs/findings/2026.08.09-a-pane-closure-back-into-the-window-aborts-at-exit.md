# A pane that closes over the window aborts the process, where a signal does not

The bisect is the whole of the evidence and it is short: with the cards absent
the process exits zero, with the cards present and their callbacks inert it
exits zero, and with the callbacks live it aborts every time. Nothing else in
the pane moves the exit code, including the scroll area, which was the first
suspect because it owns its child widget rather than parenting it the ordinary
way.

The prediction that would have refuted "it is the reference back into the
window": inert callbacks build exactly the same widget tree, the same number of
`ChainCard`s, the same layouts and labels, and differ only in what the lambda
holds. Had the abort survived that substitution it would have been the widget
tree, and the signal rewrite below would not have helped.

Why a signal is different is not a mystery: PySide holds a bound-method slot
through a weak reference to its receiver and drops the connection when either
end is destroyed, so the pane has no strong Python reference to the window at
any point. A closure has one, and it is held by a child the window itself is
destroying.

This is a second symptom of what
[2026.08.09-the-players-destroyed-net-does-not-catch-a-window-nobody-closed.md](2026.08.09-the-players-destroyed-net-does-not-catch-a-window-nobody-closed.md)
calls the object graph at exit not being understood, and it is a different
mechanism from that one — an access violation rather than the stack-buffer
abort, deterministic rather than intermittent, and it does not go away when
every window is closed by hand. It is filed separately for that reason. The
open question above is the part that would join them: if the pipeline pane is
safe only because `replace_pane` orphans it, then the two findings are about
one thing, and the item that owns the first one is where that lands
([todo/a-dropped-player-takes-the-process-down-and-its-net-is-a-comment.md](../todo/a-dropped-player-takes-the-process-down-and-its-net-is-a-comment.md)).
