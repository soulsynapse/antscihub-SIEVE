# A player held to interpreter exit fail-fasts the process on a green suite

The comment at `player.py:145` had the hazard exactly right — "a running
`QThread` whose wrapper is finalised aborts the process, so stopping it cannot
be left to a caller remembering to" — and the floor it built does not cover the
case that fires. `destroyed` is emitted when an object is destroyed, and an
object still referenced at interpreter exit is never destroyed. So the floor
catches a player that is *dropped* and misses one that is *held*, which is the
state every process is in that exits owning a window.

Why it survived so long: the failure is invisible from inside the session that
causes it. Every test passes, pytest prints its summary, nothing is written to
stderr at all, and only then does the process die. Under Git Bash the code
renders as `127`, which reads like a missing command rather than a fail-fast —
the true value, 0xC0000409, only appears once the exit code is asserted on from
a parent process. A reviewer bisecting by test selection is searching a space
the defect is not in, and the narrowing itself changes how many players a run
constructs, so the rate moves under the bisect.

The `libshiboken ... already deleted` tracebacks are a second symptom of the
same ordering and not a cause: they appear when the thread *is* stopped and
`destroyed` fires afterward on a wrapper Qt has reaped, and their count varies
run to run while the exit code does not follow them. The `atexit` probe
separates the two cleanly — it takes the exit code to 0 and makes the
tracebacks appear, at a fixed 190 bytes per player. That is why the regression
test asserts on stderr as well as on the code: either assertion alone leaves
half the defect free to come back.

For the mechanism to have been anything else, the held-player probe would have
had to exit 0, or the exit code would have had to track a test outcome or the
traceback count. It did neither, at three process sizes.
