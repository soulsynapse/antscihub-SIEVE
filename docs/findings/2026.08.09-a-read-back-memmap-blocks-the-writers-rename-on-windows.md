# A read-back memmap blocks the checkpoint writer's rename on Windows

`tools/checkpoint.py` maps rather than loads, and argues for it: a checkpoint
exists so an hour of footage need not be recomputed, and reading it resident
would put the run length back into the memory bound the writer took it out of.
That argument holds. What comes with it is a file handle that outlives the read,
because `_stack` is an `lru_cache(maxsize=8)` at module scope keyed on path,
size and mtime — deliberately, so an unchanged file is not reopened per frame.
`pick` has the same cache and not the same exposure: `_decoded` calls
`cv2.imread` and holds pixels, not a handle.

The collision is with `CheckpointWriter.close`, which commits by renaming each
`<node>.<emission>.part.npy` over `<node>.<emission>.npy`. POSIX lets a rename
land on a mapped file; Windows does not. The same process that previewed a
checkpoint and then writes one to that path gets `PermissionError` out of
`Path.replace` — an `OSError`, not the `CheckpointWriteError` `run_cmd` knows
how to report.

Where it lands is worse than the raise. `close` releases the arrays and then
renames in a loop, and the loop is deliberate: the writer's own comment says a
half-succeeded rename would leave one node's result in place and the next
node's beside it under a part name. The exception arrives inside exactly that
loop. `__exit__` then calls `abandon`, which — the writer not being `_closed` —
unlinks the remaining part files. So nodes before the blocked one are the new
run's output, nodes after it are gone, the manifest was never rewritten, and
the manifest still on disk is the previous run's, describing files that have
been partly replaced. Nothing is red and nothing looks wrong in the folder.

Reaching it needs one process to both read and write the same checkpoint path.
The GUI is that process by construction — it is long-lived, the module cache is
global to it, and the workflow `tools/checkpoint.py`'s own `GUIDANCE` describes
is checkpoint a step, wire the `.npy` in where it stood, tune below it. A user
who then goes back to the writing project and re-runs it has done nothing
unusual.

For the conclusion to flip, `_stack`'s entry would have to be gone by the time
the writer commits. Nothing evicts it: not closing a project, not building a new
`Dag`, not a new run. Eight distinct checkpoint files read in between would, by
displacement, which is a way of saying the failure is intermittent rather than
absent.
