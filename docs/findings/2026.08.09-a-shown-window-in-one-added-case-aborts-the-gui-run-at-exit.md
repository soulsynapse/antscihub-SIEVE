# A shown window in one added case aborts the gui run at exit

Recorded because the failure mode is the worst shape a test failure has: every
case reports passed, the summary line is green, and the process exit code is the
only thing that says otherwise. A session that read the summary and not the exit
code would have called this clean.

What would refute the reading that showing is involved: the abort surviving the
rewrite to `setActiveWindow`. It did not — the same case driving the same
handler through the same event, with no shown window, exits 0 over the whole
suite. That is enough to route around it and not enough to say what it is, and
the difference from `test_pinned_slot.py` is what an attribution would have to
explain. The candidates above are unseparated because separating them costs a
whole-directory run per candidate against a failure that appears in no smaller
run.

## Amended 2026-08-09 at this item's review: showing was not it, and one green run could not say so

[2026.08.09-a-player-held-to-interpreter-exit-fail-fasts-the-process-on-a-green-suite.md](2026.08.09-a-player-held-to-interpreter-exit-fail-fasts-the-process-on-a-green-suite.md)
attributes the abort, and it is not this case. A `VideoPlayer` still referenced
at interpreter exit never emits `destroyed`, so its decode thread is never
stopped and Qt's static teardown fail-fasts the process. `MainWindow` builds a
player in its constructor whether or not the document names footage, so the
first open question above — "this window has no player thread" — was false, and
the abort was reachable long before the handler this item added.

The probes above stand as recorded and their comparison does not. That finding
measures the same tree at 3 of 10 full runs nonzero, so each of the four rows
here is one sample of a coin that lands green about seven times in ten: the file
alone exiting 0, the directory-without-it exiting 0, and the `setActiveWindow`
rewrite exiting 0 are all the likelier outcome under no change at all. The
sentence naming a refutation — "the abort surviving the rewrite; it did not" —
is the one that needed a count and did not carry one.

What survives for the tree. `driving.activate` setting activation directly
rather than showing is still the right helper for the reason its own docstring
gives second — it reaches a window with no handle, where `requestActivate` needs
one — but not for the reason it gives first, and the citation back to this file
now means "an abort that had nothing to do with showing". The rate this file was
read through is the generalisable part, and it is written up as
[loop/2026.08.08-a-re-measurement-explains-a-gap-that-one-more-pass-of-its-own-probe-covers.md](loop/2026.08.08-a-re-measurement-explains-a-gap-that-one-more-pass-of-its-own-probe-covers.md)'s
dated amendment.
