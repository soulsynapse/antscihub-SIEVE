# A source-tool root keys in a different flavour than the footage it replaces

ADR-18 was decided on 2026-08-07, before `picked_key` existed. At that time
there was one root flavour, so "a run rooted on the written crop folds exactly
the string a source tool over that file folds" was a statement about one
function. `44b6456` landed the first source tool and split the root key in two,
deliberately and with the split argued at length in `picked_key`'s docstring —
and that same commit is what lifted the migration item's gate. The gate lifting
and the premise breaking are the same event.

The prediction that would have refuted this: if the crop half were still free,
some choice of `decode_format` or `source` argument would make `source_key`
agree with `picked_key` for one identity. None can — the flavour literal is a
hashed position and differs, so the two digests are unequal for every input.

What this does *not* say is which way the fork should go. Both readings are
live: give an artifact's source tool a way to fold `source_key` (a change to the
source-tool key contract), or accept that the crop half moves keys and re-state
the Phase 5 gate accordingly. The first preserves ADR-18's argument at the cost
of the split `picked_key` was written to defend; the second preserves the split
at the cost of a plan gate. The reason this is recorded rather than decided is
that either one, chosen inside an implementation, is exactly the shape
`cache_key.py`'s opening paragraph is written against — a wrong answer served
from cache under a well-formed key, with no symptom.

## 2026-08-09: ruled — the flavour follows the reader

Kendrick took the first fork, in the sharper form the first open question
points at: the split is reader-owned, not wiring-owned. A source tool whose
file is read through `decode/reader.py` folds `source_key`; only an own-code
reader like `pick` folds `picked_key`, whose docstring argument is correct
exactly there and nowhere else. Minted as
[adr/a-root-keys-by-its-reader.md](../adr/a-root-keys-by-its-reader.md) —
succession, not an edit to ADR-18, whose key paragraph's "free by construction"
this rule makes true again — and
`todo/crop-serving-and-checkpoint-read-back-become-source-tools.md`
un-defers with its criterion intact: the equality its first case asks for is
satisfiable again by construction.

What decided it, beyond this tree:

- v2 has one flavour for footage and it always folds the decoder:
  `../antscihub-SIEVE-v2/src/sieve/pipeline/cache_key.py`'s `source_key`
  digests `("source", source, decoder_identity(), region, luma|bgr)`, and its
  position-history comment records the format position being *added*
  (2026-07-27, the luma path) — the collision class a bare file-identity key
  reopens was hit in the wild once and closed by widening the key.
- v2's crop serving substitutes the identity inside that flavour ("by being
  passed a *different `source`*, computed from the artifact file itself"), so
  ADR-18's "the crop half is free" was v2's measured behaviour, not an
  aspiration this tree failed to reach.
- v2's lowered-source branch — its closest analogue to a source tool over an
  artifact — refuses to key without a decoder identity and folds the writer's
  (`lowered_prefix.decoder_identity`): the flavour following the reader,
  applied once already.
- The mockup's settled "Source is a step" row (`docs/MOCKUP-MAP.md`) plus
  VISION's "every input including this one is a tool" make source tools the
  eventual root of all footage, so under the second fork `source_key` loses
  its last caller the day the source card lands and the bare key becomes the
  primary path's key.
