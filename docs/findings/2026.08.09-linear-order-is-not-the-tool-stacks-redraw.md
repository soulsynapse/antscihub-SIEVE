# linear_order is not the tool stack's redraw, and nothing in src/ calls it

Recorded because the claim was load-bearing in an item's argument rather than
incidental to it: three sites were named as the places one root is assumed, all
three were said to be "real today rather than predicted", and the first turns
out to be reachable from nothing. The other two were live and were moved —
`cache_key` folded one identity for every root, and the executor bound every
node with no upstream to the reader.

What makes this worth a file rather than a line in a commit message is that the
mistake is a specific and repeatable one: `dag.linear_order` and
`gui/walk.node_order` answer neighbouring questions and each names the other in
its docstring, so a reader looking for "the walk that draws the stack" finds
the wrong one first — it is in `pipeline`, which is where a reader expects a
graph traversal to be, and it carries a refusal that reads exactly like the
symptom being looked for. The GUI's own walk is the one that draws, and it was
written above the fence on purpose
(`adr/superseded/gui-base-is-the-v25-spike.md`): a linearization is a presentation choice.

A finding rather than a correction to the item, because the item is the review's
to edit and because the fact outlives it: the next thing that wants to know
which walk a front end reads is the source card in the walk, and it will ask
this same question.
