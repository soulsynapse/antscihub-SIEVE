# The luma worker cap is right at sixteen cores and a third slower at four

The prediction that would have closed the question cheaply: worst/best within a
few percent on every core set, which is the reading `bench/sweep.py` names as
making a controller "a failure mode with no upside" and a per-machine constant
harmless. Nothing came back near it. The flattest cell group in the whole run is
a two-core set at 1.53x, and that one is flat only because the design has two
points in it.

What the core-count axis adds is the sign flip. On 16 and 32 CPUs the luma
optimum is two workers and `LUMA_WORKER_CAP = 2` is exactly right — 7.27 ms
against 8.37 sequential on the fast class, the 1.15x that v2's luma finding
described as "almost nothing left to thread". Truncate to four CPUs and the same
two workers cost 16.12 ms against 12.08 sequential. The second worker stops
overlapping anything and starts contending for the cores the decoder was already
using, and `resolve_workers`' `min(available_cpus, LUMA_WORKER_CAP)` has no term
that can see it: the cap bounds the count from above and 2 is below the clamp at
every allocation size down to two CPUs.

That is the specific shape of "wrong everywhere it was not measured" — not a
constant that gives up some throughput off its home machine, but one whose
value on a small allocation is worse than the sequential path it was introduced
to beat. A cluster node with a four-CPU job step is the case, and it is the case
`docs/VISION.md`'s headless run is aimed at.

The colour path is the benign half. Its optimum on the whole allocation is three
workers and `INFERRED_WORKER_CAP = 4` reads 11% off that on the fast class,
which is the "cap where the curve turns" the constant's comment claims for it.
Its core-count axis was not run; the luma path was chosen for it because that is
where the constant is tighter and the frames cheaper.

## Amended 2026-08-09: the resolver the second consequence describes has changed

`resolve_workers` no longer answers `min(available_cpus(), cap)`. It floors the
inference at `CORES_PER_WORKER = 4` cores per worker, so the 4-CPU and 2-CPU
allocations named in the second consequence now resolve to one worker — the
sequential path, which is the optimum this sweep read at both sizes. Every cell
above was taken against the old resolver and none of them moves; what moved is
which cell the resolver picks. The floor is slack at 16 and 32 CPUs, so the two
whole-allocation optima this sweep confirmed are unchanged on both paths.

Four is the number because it reproduces the luma optimum at every core set
here. The colour path's core-count axis is still unrun, so the floor's colour
half is an extrapolation of the contention mechanism and not of a reading — the
open question below stands, and
`todo/a-truncated-unpinned-set-is-pinned-and-duplicates-the-fast-class.md`
carries the sweep that would close it.

One reading of the instrument rather than of the machine: `unpinned[:N]` and
`class1x16[:N]` are the same CPUs on this machine and read within 2% of each
other at every size, because `class_core_sets` sorts the fast class first and
`sized_core_sets` truncates from the front, so the truncated "unpinned" set is
neither unpinned nor a different draw of cores. A third of the sized rows are a
duplicate treatment under a label that says otherwise. The whole-allocation
`unpinned` row it is derived from is not a duplicate — that one really does let
the scheduler migrate, and it beats both pinned classes at every worker count.

## Amended 2026-08-09 (review of 12217da): the floor's justification overclaims by one core set

`CORES_PER_WORKER = 4` is documented in `decode/prefetch.py`, and in the
amendment above, as reproducing this sweep's luma optimum at *every* core set
read. It does not. At `class1[:8]` the reading is 8.91 ms/frame at one worker
against 9.10 at two, so the optimum measured there is sequential and the floor
picks two workers. Five of the six core-count cells do agree with it —
`class1[:2]`, `class1[:4]`, `class0[:2]` and `class0[:4]` all read one worker
faster, and `class0[:8]` reads two workers 23% faster (10.98 against 14.18) —
and the sixth disagrees by 2.1%, which is inside the band this sweep's own
instrument note declares when it treats `unpinned[:N]` and `class1x16[:N]` as
the same mask at "within 2%".

Four is still the defensible number and nothing measured here beats it: eight
cores per worker would match `class1[:8]` and lose `class0[:8]`, and it would
also drop the colour path to two workers at 16 CPUs, where three was measured
optimum. What is wrong is the claim and not the constant — and it is wrong in a
durable comment, which is the class of error CLAUDE.md's rule about
state-dependent claims in long-lived instructions exists for. The correction to
`prefetch.py` is queued rather than made here.
