# The player's destroyed net does not catch a window nobody closed

`VideoPlayer.__init__` connects `self.destroyed` to a closure holding the
`QThread` rather than `self`, with the comment: "A running `QThread` whose
wrapper is finalised aborts the process, so stopping it cannot be left to a
caller remembering to. `destroyed` fires while the thread object is still valid
and the closure holds *it* rather than `self`". The first sentence is confirmed
by the first probe. The second is false in the case the first describes: at the
moment the slot runs, the `QThread` wrapper is already gone, `_stop` raises out
of the lambda, and Qt swallows it to stderr — so the net catches nothing, and
what actually keeps `tests/gui` green is that every window except
`test_skeleton.py`'s is closed by hand.

The prediction the second probe would have had to falsify: if the net worked,
closing the window would change nothing about the exit code, because a dropped
player would already have been stopped. It changes the exit code from an abort
to zero. That is the whole of it.

What this does not settle is the fix. `shutdown()` is the orderly path and every
caller in `src/` takes it (`app.closeEvent`), so the net's only client is a test
or a future front end that drops a player without closing it — and a guard that
raises is worse than no guard only if a reader trusts the comment, which is the
part that is unambiguously wrong today. Deleting the connection and stating the
requirement, or reaching the thread through a handle that survives finalisation,
are both open; the traceback count not scaling with the number of players says
the object graph at exit is not understood well enough to pick between them yet.
