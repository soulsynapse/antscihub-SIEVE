# The shelf reparses every project per arrow key

The number that matters is not 72 ms on its own — it is that 72 ms buys nothing.
Nothing a card says depends on which card is selected, so the parse is repeated
work by construction: the same forty documents, unchanged since the last
keystroke, read and decoded again to produce byte-identical strings. Key
autorepeat is roughly thirty a second, and a library four times this size would
put a keystroke's cost above the frame budget the whole architecture is
organised around.

What would have refuted "it is the parse": had `listings` been cheap and the
717 ms been widget construction, the fix would be the opposite one — build the
cards once and repaint. `listings` alone is 40 ms of a 72 ms keystroke and the
rest is forty `ChainCard`s with their layouts, so both halves are real and the
parse is the half that is avoidable without changing what is on screen.

The scroll result is not a performance finding and is filed here because the
same rebuild causes it. It is the more user-visible of the two: a library long
enough to scroll cannot be navigated by arrow key at all, because the thing the
arrow key moves is not on screen.

## Amended 2026-08-10: the remedy landed, and the half it does not touch is now the whole cost

Both open questions above are answered, and by both remedies rather than a
choice between them: `project_select.HeldListings` re-reads a document whose
mtime or size has moved and no other, and `gui/stack_pane.StackPane` gives a
rebuilt stack the outgoing pane's offset and then the least move off it that
brings the selection into view. The parse half is satisfied by the memo, the
scroll half by the carry, and neither remedy would have covered the other —
which is what the item's "one decision" claim turned out to mean.

Re-measured on the same library and machine, at the tree that holds them:

| probe | before | after |
|---|---|---|
| `listings()` over forty projects | 40.2 ms | 21.0 ms (uncalled per keystroke) |
| one `go_down` at the project position | 71.7 ms | 29.5 ms |
| ten `go_down`s held at the foot of the list | 71.7 ms each | 0.002 ms each |

The `listings` row is the same call measured twice on one machine and differing
twofold, which is what a cold page cache is worth here and is a caution against
reading either number as the parse's cost rather than as its order.

**What the 29.5 ms is, is the forty cards.** The finding above already said the
parse was the avoidable half and the widgets were not — that is now the whole of
a keystroke, and it is still above a frame at this library size. It is not the
same defect surviving: nothing is re-read, and the cost is the surface being
built rather than the disk being asked. Moving it needs the pane to stop being
rebuilt for a moved accent at all, which is a different decision — the card's
own arrangement is what would have to change with it, because OPEN LOCATION is
drawn on the selected card alone
(`todo/the-project-card-acts-in-its-head-and-reads-at-its-foot.md`), and no open
item asks for it yet.
