# The band drag's per-sample gate disagrees with itself under a loaded machine

The gate's own docstring makes the right argument — a median that passes over a
sample that missed is a janky drag, and one slow tick inside a continuous
gesture is a stutter the median hides. Nothing here disputes it. What the three
runs above establish is that the gate is not answering only that question: with
the source unchanged between the second and third invocation, the verdict moved,
and the only thing that moved with it was how much else was running.

This is not the same hole as
[2026.08.07-the-per-sample-gate-cannot-see-the-cold-first-frame.md](2026.08.07-the-per-sample-gate-cannot-see-the-cold-first-frame.md).
That one was about which samples the gate is allowed to read and was fixed by
widening the collection. This one is about the samples themselves: a wall-clock
measurement taken while 1200 other cases are contending for the same cores is a
different measurement, and no widening of the collection changes that.

The reason to write it down rather than re-run until it settles is that a green
obtained by repetition is the outcome that leaves the next session with the same
question and one less data point. For the conclusion to flip, a run under
comparable load would have to be green repeatedly while a quiet run went red —
which is the ordering a real regression in the repaint path would produce, and
is the discrimination the missing `over_ms` would have given cheaply.

## Amended 2026-08-10 (11.3): the gate beside it goes red the same way

Same machine, same day, one whole-suite run during 11.3 with `subtract` on the
shelf: `test_every_band_drag_the_session_published_is_gated` red *and*
`test_gui_loop_budget.py::test_every_sample_the_session_published_is_gated` red,
1292 of 1294 green. Both nine cases of the two bench modules passed on the very
next invocation of those modules alone, with nothing under them changed. An
earlier whole-suite run in the same session, over a tree differing only in the
item's `status` line and two generated indexes, was green in all 1294.

What that adds is that the load sensitivity is not one gate's. The two modules
share only `bench/budgets.py` and the live clock behind `MetricBus`, so the
common cause is the clock rather than anything the band surface owns — which
narrows the first open question above by ruling out "the surface's cost" as the
whole of it, and leaves the second one wider: a second per-sample gate is a
second population of load-dependent samples, and neither median has been seen
red yet.

`over_ms` was again not captured, and this time for a reason worth naming
because it will recur: the run's output was read through `tail`, which keeps the
summary and discards the assertion text the margin is in. A run that expects to
see this red reads the failure body, not the last five lines.

## Amended 2026-08-10 (11.3 review): the median gate goes red too

Same machine, same tree as the amendment above plus this review's doc edits.
Two whole-suite runs, back to back, nothing changed between them:

    $ uv run pytest -q
    FAILED tests/bench/test_band_surface_budget.py::test_a_band_drag_repaints_the_surface_inside_half_a_perceived_beat
    FAILED tests/bench/test_band_surface_budget.py::test_every_band_drag_the_session_published_is_gated
    2 failed, 1292 passed in 60.36s

    $ uv run pytest -q
    1294 passed in 56.91s

The new datum is the first line. Every observation until now had the *median*
gate green while the per-sample gate beside it went red, and the verdict above
says so; `test_a_band_drag_repaints_the_surface_inside_half_a_perceived_beat` is
that median gate, and it has now been red once. So the two are not a strict
gate — the per-sample gate is the more sensitive of the two rather than the only
sensitive one, and the population under both moves far enough under load to
carry the median with it. What would have to happen for this to become a
regression rather than a load artefact is unchanged: a quiet run red.

`test_gui_loop_budget.py::test_every_sample_the_session_published_is_gated`,
red in the run the amendment above records, was green in both runs here. Three
distinct cases across two modules have now been red once each and green
otherwise, which is what the shared-clock reading predicts and what a defect in
any one of them does not.

`over_ms` is missing for a third time, and the amendment above named the exact
mistake that lost it — reading the run through `tail`. This review made it
anyway, on the run that was red, and then captured the full output of the run
that was green. That ordering is the whole lesson: the capture has to be set up
before the run, because which run goes red is not knowable in advance. The
command that gets this next is `uv run pytest -q > <file>` on the *first*
attempt, with the failure body read out of the file.

## Amended 2026-08-10 (the sweep item's run): a fourth occurrence, and the tail mistake again

Same machine. `uv run pytest -q --ignore=tests/gui` (1036 cases) over a tree whose
only changes were `scripts/mutation_sweep.py` and
`tests/scripts/test_mutation_sweep.py`:
`test_gui_loop_budget.py::test_every_sample_the_session_published_is_gated` red,
1035 green; the module's own case green on the next invocation of it alone, with
nothing changed. So the load sensitivity does not need the GUI suite in the
session to fire, and the tree that fired it touches neither bench module nor
anything either reads.

`over_ms` is missing for a fourth time and for the third time to the same cause:
the run was read through `tail -4`, which keeps the summary and discards the
assertion body. The amendment above named the mistake and this run made it anyway,
which is worth recording as a property of the instruction rather than of the
runs — "read the failure body" is advice that arrives after the command has
already been typed, and the thing that would actually work is redirecting to a
file unconditionally on any bench-carrying run, red or not.

## Amended 2026-08-10 (the sweep item's next run): the first margin, and a fifth occurrence

Same machine, same command and the same shape of tree as the amendment above —
`uv run pytest -q --ignore=tests/gui`, 1038 cases, changes confined to
`scripts/mutation_sweep.py` and `tests/scripts/test_mutation_sweep.py`, neither
bench module nor anything either reads touched. Red again, and this time the
assertion body was in the output:

    AssertionError: assert ['band_drag_r...over by 11.2'] == []
      Left contains 6 more items, first extra item: 'band_drag_repaint took 92.1 ms, over by 42.1'

So the margin is finally on the record and it is not marginal: 92.1 ms against a
50 ms ceiling, nearly double, with six samples missing at once and the smallest of
them over by 11.2. That settles the first open question in the direction the
shared-clock reading predicted. A repaint path that had genuinely regressed to
92 ms would not be green on the very next invocation of the module alone, and a
sample sitting just outside its ceiling would miss by a millisecond rather than by
42; six simultaneous misses spanning 11 to 42 ms over is a population that was
descheduled, not a cost that grew. What would still flip it is unchanged: a quiet
run red.

`over_ms` was lost a fifth time only in part, and to a new cause worth naming
because the standing advice does not cover it. The run was not read through
`tail` — its whole output was read — and pytest's own diff for `assert missed ==
[]` elides the middle of a six-element list, keeping the first and the last. So
redirecting to a file, which the amendment above prescribes, would not have
recovered the other four either. What recovers them is `-v` on the bench modules,
or an assertion that prints the list rather than comparing it.

## Amended 2026-08-10 (review): the verdict names one gate and the file holds two

Four of the five occurrences above are
`test_gui_loop_budget.py::test_every_sample_the_session_published_is_gated`, and
the `title` and `verdict` name only
`test_band_surface_budget.py::test_every_band_drag_the_session_published_is_gated`,
which is the one this file opened on. The `.index.md` row shows the verdict
alone, so a reader looking for why the loop-budget gate is intermittent will not
find this file from the index. The verdict is left as written — it records what
was believed when it was measured — but the class it describes is the per-sample
gate in either bench module, not the band drag's, and whichever finding
supersedes this one should say so in its own verdict.
