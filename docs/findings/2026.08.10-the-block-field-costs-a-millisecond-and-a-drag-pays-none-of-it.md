# The block field costs a millisecond, and a drag pays none of it

The number that mattered going in was v2's: a per-cell fill loop at
B = 16,384 measured as a 34 ms repaint, slower than the frame it drew over,
which is why `_paint_heat` builds one ARGB image by `np.repeat` instead. The
port keeps that shape and the shape keeps the number — 2.11 ms is a repaint the
tuning loop does not notice, and the 1.2 ms it adds over the greyscale image is
the difference between drawing one `QImage` the canvas already held and building
one from the values first.

The second row is the one that decides the attribution. At B = 6 the field is
1.91 ms and the greyscale 0.72 ms — nearly the same gap as at B = 16,384, three
orders of magnitude of cells apart. So what the field costs is not per cell at
these sizes; it is the fixed cost of building and blitting an image the size of
the letterbox, and the block count would have to reach the pixel count before
the `np.repeat` term is visible. A regression here would therefore not look like
a slope against block count. It would look like the layer being rebuilt more
often than once per render.

The item that opened this predicted the opposite of what the drag does, and the
prediction was reasonable: `_paint_viewport` runs with `render=False` on a drag
and the viewport does repaint at pointer speed. What it missed is that the
repaint has nothing to paint. `set_frame` clears the field exactly as it clears
the input layer, on the same argument — the source frame is nothing's result, so
composing the previous step's cells over it would show a field measured from a
frame the user has scrubbed away from. `tests/bench/test_gui_loop_budget.py`
pins that: during the drag the viewport holds a frame and no field.
