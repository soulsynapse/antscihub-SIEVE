# The block field's ramp is exhausted four orders below the values it draws

10.3's body argues the reconciliation carefully and gets it right as far as it
goes: `image_of` stretches per frame because a picture has no axis, a cell must
mean the same thing at every playhead position, so `BLOCK` takes a range fixed
over the working window. What the argument never asks is *whose* window range.
`graph_panel.value_range` answers for the trace under the canvas, and the trace
is the *pinned* step's — which on the only real graph in the repo is `detect`,
whose series is a gate. So the field is drawn against 0..1.06 and holds values
to 21521.4.

The prediction that would have refuted this: if the pin and the walk were the
same position, the axis would be the walked node's own and the two numbers would
agree to within `graph_panel`'s headroom factor. They are not the same position
and nothing in 10.3 makes them so — the walk stands on `block_signal` and the
pin is wherever `default_pinned` put it.

Why this is not a defect the item should have caught: its criterion asserts
`(field.low, field.high) == window.graph.value_range()`, which is the wiring
claim and is exactly true. The number only appears when the equality is broken
on purpose. A criterion over a wiring identity cannot see that one side of the
identity is the wrong quantity, which is the general shape and the reason this
is written down rather than argued in the item.

## 2026-08-10: the pin landed, and it is a gesture rather than a default

10.4 gave a `BLOCK` step a trace — the solo picks one cell and the collector
takes that cell's numbers — so a block step can now be pinned, and its field is
then coloured against its own trace's axis. `tests/gui/test_soloed_block.py`
holds it: with the block step pinned and a cell soloed, the soloed cell's value
lies inside the range the field is drawn against, which is the assertion the
numbers above would have failed by four orders.

Two things the verdict still describes, and neither is work that item left half
done. `status` stays open for the first of them.

The *default* screen is unchanged. `pinned.default_pinned` gives the slot to the
last step whose values describe whole frames, which on the reference chain is
`detect`, so a user who has not pinned the block step is still looking at a field
coloured against a gate. Whether the default should instead follow the walk onto
a step whose picture is on the canvas is a question about `default_pinned` and
not about the solo, and nothing has argued it.

The axis is the *soloed cell's* series range and not the whole grid's, so a cell
louder than the one the user picked still clips to the ramp's hot end. That is
what soloing means rather than a residue of this finding — the trace and the
field read one axis, and it is denominated in the cell being read — and it is why
the alternative in `open_questions` is not made moot by the pin: a range derived
from the window's own block values would colour every cell comparably and would
put `emission_paint` back in the business of computing something.
