# The footage field's removal is atomic across the whole corpus

The item inventories the cost as four source files and reads, in its own words,
as though `cli/run_cmd.footage_of` were "the one reader". It is the one reader
of `Project.source_path`, and that is not the same claim. What `footage_of`
returns feeds four things the item does not name — `cache_key.source_identity`
into `ExecutionPlan.build(source=)`, `footage_end` into the fallback span and
the trailing clamp, `frame_source` for every root the graph does not root on a
file, and the checkpoint writer's idea of what was decoded. None of those has a
graph-side answer today, because until this ADR the graph was never asked.

There is one, and it is cheap: `ToolSource.decoded` already separates the root
whose file is opened through `decode/` from the root whose file is an image, so
"the footage" is the first decoded source root and the string it folds is the
string a reader-fed root already folds (`adr/a-root-keys-by-its-reader.md`,
`tools/footage.py`'s key paragraph). That derivation is not the expensive part.

The expensive part is that the *corpus* encodes the absence. A project whose
graph roots on `downsample` was a legal document for the whole of Phases 3
through 11, and every case that runs one asserts against a node count, a walk
position, or a reported output tally that a footage root moves by one. Those
assertions are correct today and correct after the migration, and no rewrite of
them is mechanical: `"4 frames, 4 node outputs computed"` becomes eight because
the root computes too, and `window.go_down()` from the head of a chain lands one
step earlier than it did. A helper that wires a footage node above every
reader-fed root of a graph takes the fixture layer most of the way — 63 failures
to 51 — and the remainder is one judgement per case.

What that means for the loop is the thing worth recording: this is the second
session to reach the conclusion the item's own dated fold already states, that
the criterion is five jobs behind one command. A run that reaches that
conclusion cannot act on it, because `done_when` is the review's to edit; so the
cost of the item staying as it is, is one full session per attempt.

## Amended 2026-08-10 (review): the inventory probe does not reproduce as written, and one probe has no build

The first probe reads "grep for SourceRef, for_video, source_path, NoFootage,
project.source over src/ and tests/" and returns 4 source files, 41 test
modules, 107 lines. Run as written on the same build it names, it returns
different numbers in both directions:

    $ P='SourceRef|for_video|source_path|NoFootage|project\.source'
    $ git grep -l -E "$P" -- src | wc -l      # 7
    $ git grep -l -E "$P" -- tests | wc -l    # 38
    $ git grep -h -E "$P" -- src tests | wc -l  # 130

The source-file gap is explicable and the file count is the curated one, which
is the better number: of the seven, `pipeline/materialize.py` and
`pipeline/resolve_source.py` hit on the words `SourceRef` inside prose, and
`pipeline/source_home.py` hits on `SourceHome.for_video`, a different symbol
that this removal does not touch. The four the body names are the four readers.
The module count cannot be reconciled the same way — 41 is larger than the 38
the pattern finds, so it is not a filtered subset of it — and the line count
runs the other way, 107 against 130. Whatever narrowing produced the body's
figures is not the command the probe states, so the next session's re-derivation
will not match this one and the difference will not mean the tree moved.

Second: the `1234 passed, 51 failed, 12 errors` probe has no recoverable build.
`source.build` names `be6ddb6`, which is right for the inventory and wrong for
this one — the numbers were taken on a working tree carrying the whole removal
plus a partly-migrated corpus, and that tree was reverted rather than committed,
so it exists in no commit and on no branch. The number is still worth having as
an order of magnitude for what the migration costs. It is not a baseline: a
later attempt reporting 40 or 60 reds is a fresh measurement of a differently
migrated corpus, not a change in the tree.

Third, the clause arithmetic, since the file uses two counts. `done_when` was
four `&&` legs over six case names when this was written; one of the six (the
anchoring case) landed with 11.3, so "the criterion's five clauses" and "five
jobs behind one command" mean the five unlanded ones. The review of this run
split the first leg's `or` into three, so the command is six legs over the same
six names.
