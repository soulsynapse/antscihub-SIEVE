The full per-activity table — which file, which decode route, which policy,
at what measured cost, with per-row evidence — lives in
`experiments/decode-experiments/2026.08.21-best-combinations.md`, beside the
result files and explorer logs it cites. This entry is the shelf pointer and
the summary.

What one day of measurement settled: **the container the footage is in
matters more than any decoder configuration run against it.** In the right
derived file — a display-size intra proxy for exploring the whole timeline, a
lossy-intra cut for the tuning loop — every access pattern SIEVE has (drag,
play, reverse, random hop, sorted batch, flat-out sweep) is interactive
through any competent route, and the differences between routes shrink to
single-digit milliseconds. All the exotic machinery that was measured —
NVDEC seeks, hybrid sw/hw routing, keyframe-snap scrubbing — earns its keep
only against the *uncut original*, in the window before derived files exist
or when a committed action needs exact source pixels.

Three supporting results, each with its own shelf finding or result file:
the analysis side is dominated by dense optical flow alone (everything else,
the Morlet CWT included, is noise beside decode); parallel decoding pays
only on the heavy source and inverts on everything derived; and frame
identity must be pts, because on the real footage the metadata count, the
packet count and the decodable-frame count are three different numbers.

Machine dependence is handled by measurement, not assumption: seek routing
is probed at first open and cached per machine and source shape
(`experiments/decode-experiments/explorer-logs/probe-cache.json`), so the
stack's shape re-derives itself on hardware unlike the one that produced
these numbers.
