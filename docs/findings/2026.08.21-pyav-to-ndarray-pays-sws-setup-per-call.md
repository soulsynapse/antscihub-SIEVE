`frame.to_ndarray(format="bgr24")` constructs a fresh SwsContext (coefficient
tables, SIMD path selection) on every call and frees it after one use. That
setup is roughly fixed cost, so it dominates exactly when frames are small:
on the 462x456 clip the per-call route costs 3.9 ms/frame against 0.08 ms
through one reused `av.video.reformatter.VideoReformatter` — 49x of pure
setup. On the 5.3K frame the same fix is worth only ~1.4x (11.1 → 7.7 ms)
because conversion dominates.

The trap this documents: measured naively, this reads as "PyAV conversion is
slow on small frames" and would have entered the corpus as a decode fact. It
is an API-usage fact.

## How to recreate

```
uv run --group experiments python experiments/decode-experiments/01-pyav-vs-opencv.py
```

Compare the `pyav/threads=AUTO/bgr24` and `bgr24_cached` cases per file in
the new result.
