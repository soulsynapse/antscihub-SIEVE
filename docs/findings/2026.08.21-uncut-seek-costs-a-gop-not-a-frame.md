On the uncut 5.3K HEVC source (GX010047c2, 5312x2988, 23.976 fps), a
frame-accurate random seek costs ~300 ms through software PyAV and ~430 ms
through cv2, flat in jump distance and direction — the inherited "tens of
ms" budget was wrong by an order of magnitude on this footage. The cost is
throughput-bound GOP replay: decoding forward from the landing keyframe to
the target. Fewer decoder threads make it *worse* (threads=1: 1542 ms;
threads=16: 356 ms), and NVDEC halves it (cuda: 151 ms, d3d11va: 184 ms)
because its serial per-frame latency beats 16-thread software on a
12-frame-average replay.

Grab-forward crosses over with seek at ~40 frames on this file (~120 on the
small post-cut clip, where seeks cost 2–15 ms and the whole problem is an
order of magnitude smaller).

Machine: 22 logical CPUs, RTX 4060; builds and footage probes are inside the
result files.

## What it changes

The v2/v3 scrub-defense subsystems (coalescer, scrub policy, request
intents, proxy cache) defend a real budget — but only on uncut footage, and
no decoder configuration rescues it into interactive territory. The cut does
(see the lossy-intra finding). Hardware decode's value is seek latency, not
throughput.

## How to recreate

```
uv run --group experiments python experiments/decode-experiments/02-random-access.py
```

Footage in `video-tests/` (gitignored; the result file records what was
probed). The new result lands beside the old ones in `results/` and
supersedes by sitting next to them.
