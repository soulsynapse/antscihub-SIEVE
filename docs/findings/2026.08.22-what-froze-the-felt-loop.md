The session explorer's tuning loop reported as "frozen while it does
everything" — while every storage-stack serve stayed fast (play p50
0.01 ms, p95 under 0.5 ms even mid-fill, per the session logs). Every
freeze traced to presentation-layer or ordering causes, none to the tier
stack, and each cost real instrumentation to find because the obvious
suspect (decode) was innocent:

| culprit | felt as | measured | fix |
|---|---|---:|---|
| autosave re-probing provenance (git + ffmpeg subprocesses) per save | 2 s hang every ~30 s of looping | 2.1 s per save | probe once at init |
| fill starting at window start while loop played from the click | frozen picture ~2 s at landing (40–54 same-frame nearest-serves per landing) | click→first advance 283–527 ms | fill from the playhead's chunk, wrap after |
| matplotlib Agg rasterizing on the GUI thread (deferred via draw_idle, invisible to a probe around the redraw function) | 150–400 ms hiccup per graph refresh | stalls 29→8 once moved | render on a worker thread; graph pane is a pixmap label |
| blocking miss decodes on the GUI thread for non-exact requests | 200–370 ms per drag into unfilled ground | drags → ~8 ms | proxy-crop placeholder ("lo" route), display-only, never admitted |
| content driving layout: video/graph pixmap size hints and half-second HUD text nudging the splitter | video visibly resizing every few seconds | 12 reflows/session, canvas width oscillating 822–900 px | Ignored size policies on everything the session updates; 0 reflows after |
| event flood: a looping session logging every 0.01 ms play-hit | GUI-thread JSON dumps and 37k-point scatters | one session: ~37k events | decimate steady play serves 1-in-8, counted; throttle saves under the loop |

Two residues, deliberately kept: exact-release misses (~300 ms — release
always shows true pixels; an NVDEC route would cut it to ~60–115 ms per the
decode shelf, unwired) and kf-route hunt drags (~150–180 ms — the honest
route price, moot wherever the proxy exists). A few 110–190 ms hiccups
under heavy fill remain unattributed beyond GIL scheduling; chasing them
below that floor wasn't worth it in-process.

The transferable claims, for the day the real app is built:

- **Blame instruments, not intuition.** The stall stacks named matplotlib
  when every intuition said decode; the geometry probe named a *text
  label* as the video-resizer. A 10 ms heartbeat plus
  `sys._current_frames()` sampling is ~30 lines and settled in minutes
  what felt-reports argued about for a day.
- **Nothing that updates may participate in layout negotiation** — panes
  get geometry from the user and the window; content scales or elides
  into it.
- **The GUI thread may block only for an exact request the user just
  released.** Everything else serves a placeholder from a cheaper tier
  and lets the fill overtake it.
- **Coverage order follows attention**: fill from the playhead, not the
  region boundary — the same decode work in a different order is the
  difference between a frozen landing and a seamless one.
- Numbers here are one machine (32 logical CPUs, Windows 11) and the 5.3K
  HEVC source; ratios and mechanisms are the finding, not the absolute ms.

## How to recreate

```
uv run --group experiments python experiments/storage-experiments/session-explorer.py
```

Drive it: click around the timeline, drag through unfilled windows, wiggle
the signal slider; every request and background span autosaves to
`explorer-logs/session-explorer-*.json`. The stall/geometry probe harness
that produced the attributions lived in a session scratchpad and is
reconstructable from this file's table: wrap `_serve` and the window/crop
methods with timers, run a 10 ms QTimer heartbeat recording gaps >100 ms, a
watchdog thread sampling `sys._current_frames()` when the beat runs late,
and a 50 ms timer recording canvas/graph geometry changes.
