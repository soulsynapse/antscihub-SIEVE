measured: 2026-08-30
where: experiments/orchestrator-experiments/explorer.py driven by a one-window probe (no interaction), GX010047c2_02_17_26.MP4, 5312x2988 @ 23.976 fps

The orchestrator explorer holds whole luma frames rather than the crop, so
the interactive window is the first configuration where holding is a real
memory decision. One window, landed and left alone — no scrubbing, no
transport:

| | value |
|---|---|
| window | 480 frames (20.0 s at 23.976 fps) |
| fill wall | 3.670 s |
| dispatcher | 2 seeks / 479 steps / 0 stale |
| fetch, `dispatch:fill` | min 3.47 · p50 5.57 · p95 17.50 · max 36.16 ms |
| pool at rest | 481 frames / 7.11 GB |
| evicted, refetched, forced | 0 / 0 / 0 |

480 frames of 5312x2988 luma is 7.62 GB by arithmetic and the pool reports
7.11 GB held for 481 frames, so the copy is the plane and nothing else. That
copy is not optional: at this width the plane stride equals the width, so
the decoded slice is already contiguous and `np.ascontiguousarray` returns
the view it was handed, pinning the whole ~24 MB yuv420p frame per hold.
`.copy()` is what makes 7.1 GB rather than ~11 GB.

**A second tool over a window already in RAM costs no decodes.** Swapping
`absdiff` for `dis` over the same 480 frames: **0 new decodes**, 479 shared
serves from the sweep to the tool, wall bounded by the field work alone.
`absdiff` field p50 1.57 ms and `dis` field p50 9.25 ms against that 5.57 ms
fetch — ratios of 0.28x and 1.66x, both FREE under `tools.FREE_RATIO = 2.0`,
though `dis` sits close enough to the cut that moving the cut would move it.

Caveats. The field figures here are **not comparable to
`tool-experiments/03-free-while-hot`**, which measured field+reduce on an
already-cropped 1024x1024 array; the envelope here also contains the
derivation of that crop out of the full frame, and how much of the
difference is derivation is unmeasured. So this does not supersede 03's
class assignments and should not be read against them. The fill wall is one
window at one position on one file, n=1. Legs of the scripted walk are
slower (6.1–6.7 s) because the walk scrubs 90 times while the window fills;
that difference is the subject of a separate finding.

## How to recreate

Land one window and touch nothing until `WINDOW n/n covered`:

```
uv run --group experiments python experiments/orchestrator-experiments/explorer.py
```

Read the wall from the HUD, the rest from `pool` and `timing_by_node` in the
`explorer-logs/*.json` the session writes. `POOL … GB` and `REFETCH n` are
on the canvas overlay while it runs.
