`orchestrator-experiments` README question 2 pre-registered both outcomes:
a derived window larger than the fixed one is a finding against the
approach, one that tracks actual need is the result that retires the fixed
window. The answer is neither. For any workload that permits scrubbing, the
derived window **is** the fixed window, to the frame.

| | derived holds | pool at rest | forced evictions |
|---|---:|---:|---:|
| 20 s window, playhead parked | 480 | 481 frames / 7.11 GB | 0 |
| 20 s window, playhead live | 480 | 481 frames / 7.11 GB | 0 |

The mechanism is not subtle once seen. A consumer that may be scrubbed to
an arbitrary position in a window has to declare that whole window, because
a declaration is also the hold — so `Sweep` declares `end - start` positions
and the graph's refcount holds exactly that many. The byte ceiling never
fired in any run, meaning nothing was evicted for any reason except a
declaration ending.

This does not contradict `02-derived-eviction`, and the two should not be
read as arguing. That experiment measured a **marching point set** — the
GUI at reach 1 and two tools declaring only `needs(row)` at each position,
never a span — and under that declaration peak holds are 6 against a fixed
window's 600. The number is correct and the model is not the interactive
one: it drops every frame the instant the playhead passes, so dragging back
one frame is a seek. The fixed window exists to defeat exactly that. The
100x is the distance between a point set and a window, which is arithmetic,
not a scheduling result.

What the derived model does buy is correctness and reach-awareness, not
bytes: `02` records no eviction-correctness violations over 600 positions
and `03-non-frame-nodes` shows a series writer releasing frames the graph
tracks. A step with reach 5 beside a step with reach 20 will hold the union
rather than the larger, which the fixed window cannot express. But the
headline memory win is not available to any consumer that can be scrubbed,
and the window size remains a hand-set parameter (`WINDOW_SECONDS`) — the
graph moved where it is spelled, not whether it must be chosen.

Caveat: one topology only — source -> pool -> {gui, sweep, tool}, single
form, one window live at a time. A graph holding two windows for two
consumers with different reaches is the case where derived and fixed could
still diverge, and it is unmeasured.

## How to recreate

```
uv run --group experiments python experiments/orchestrator-experiments/explorer.py --walk
```

`graph_holds` in the log reads 1, not 480: `closeEvent` releases the sweep
before saving. Read `pool.frames` and the `WINDOW n/n covered` overlay
instead, or `len(graph.held())` while a window is live.
