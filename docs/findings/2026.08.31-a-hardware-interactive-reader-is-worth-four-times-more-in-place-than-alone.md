ADR-0020 says which decoder opens a source is probed per machine rather than
assumed, and ADR-0021 lists the asymmetric pair — software for the sweep,
hardware for the interactive cursor — as a candidate for how many decoders run
at once. This is that pair, run in the explorer with nothing between the arms
but which route reader 1 opens.

| | software reader 1 | NVDEC reader 1 |
|---|---:|---:|
| GUI seek p50 | 245.1 ms | **61.4 ms** |
| GUI seek total | 6.41 s | 3.05 s |
| leg 1 hunt p50 | 269.9 ms | **136.9 ms** |
| snapped frames landed, legs 2/4/5 | 7 / 7 / 3 | **16 / 14 / 11** |
| snap p95, legs 2/4/5 | 140.6 / 149.9 / — | 50.4 / 81.4 / 37.9 |
| window covered, legs 2/4/5 | 4.284 / 4.754 / 4.717 | 3.580 / 4.054 / 4.228 |
| fill step p50 | 6.5 ms | 6.0 ms |

**An isolated bench underestimated this by about four times, and that is the
result worth keeping.** Timing one seek on each route with nothing else running
put hardware 14% ahead — and on that number the pair would not have been worth
a second code path. In place it is four times ahead on the same axis. The
difference is contention: the software arm runs two software decoders on one
file, which is the shape
[software decoders collapse under contention](../findings/2026.08.21-software-decoders-collapse-under-contention.md)
measured destroying each other, and NVDEC is the worker that holds its rate
under every shape there. A microbenchmark of a route removes exactly the thing
that makes the route matter.

**The fill gets faster too, which nothing was asking for.** Covered walls fall
about half a second a leg and the fill's own step p50 falls from 6.5 ms to
6.0 ms, because moving the interactive reader onto the GPU takes a software
decoder off the CPU rather than merely serving the person elsewhere. The band
partition already stopped the two readers taking each other's cursor; this
stops them taking each other's codec threads.

**Snapping and the hardware route compound rather than overlap.** With kf-snap
alone the drag legs delivered 7 / 7 / 3 frames; with both, 16 / 14 / 11 — the
snap decides *which* row is asked for and the route decides what that row
costs, so a cheaper seek means more of the snapped requests survive to land
before the hand supersedes them.

## What this does not establish

**That hardware should be hardcoded.** ADR-0020 rejects a checked-in route
table precisely because this is one machine, and
[the decode stack](2026.08.21-decode-stack-best-combinations.md) has hardware
losing on a sustained read — which is why reader 0 stays on software here. What
the result licenses is building the probe, not skipping it.

**Anything about the sweep's route.** Only reader 1 changed. The asymmetric
pair is the arm; software-for-both and hardware-for-both were not run.

**One walk per arm, one file, one machine with an RTX 4060.** The scrub legs'
frame counts are single digits to low teens, so the shape — two to three times
as many frames landing, at a third to a quarter of the latency — is the claim,
not the figures.

**Nothing felt.** A scripted walk with the hand held down is not a person, and
the driven session that started this line of work is the reason that
distinction is worth repeating.

## How to recreate

```
uv run --group tools --group experiments python experiments/orchestrator2-experiments/explorer.py --walk
uv run --group tools --group experiments python experiments/orchestrator2-experiments/explorer.py --walk --hw-interactive
```

`topology.hw_interactive` says which arm wrote a log. A route that cannot open
is recorded in `dispatcher.errors` rather than killing the reader silently.
