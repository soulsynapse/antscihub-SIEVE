ADR-0005 stated an acceptance test and never took it: *whether the set of
recorded values would differ on a slower machine*. It differs. Recording on
the cadence a display paints at produced a different set of rows every time
the machine's load changed; recording when a row's inputs landed produced the
same 159 rows under every condition.

Two arms over the same window, same footage, same fetch thread, same
arithmetic, each run quiet and under four contending matmul threads. The
comparison is each arm against **itself** across loads — the two arms' sets
differ by construction, since one records every row and the other records
whatever the fill's frontier was when it painted. Three interleaved repeats:

| arm | recorded, quiet | recorded, loaded | identical sets | rows only quiet | rows only loaded | values disagreeing |
|---|---:|---:|:---:|---:|---:|---:|
| landed | 159 / 159 / 159 | 159 / 159 / 159 | **3/3** | 0 / 0 / 0 | 0 / 0 / 0 | 0 |
| drawn | 72 / 76 / 84 | 90 / 103 / 97 | **0/3** | 25 / 26 / 31 | 43 / 53 / 44 | 0 |

The load bit, which is the guard this reads through: the renderer's paint p50
moved 2.16 → 2.56, 2.34 → 2.92, and 2.54 → 2.87 ms across the three repeats,
and per-row arithmetic went from 2.35 ms p50 quiet to 3.00 ms loaded with the
p95 more than doubling, 3.22 → 7.39. A loaded arm whose paint cost had not
moved would not have been a slower machine and nothing here would be a result.

**The direction is not the one the defect is usually described with, and that
is the sharper half.** Loading the machine made the drawn arm record *more*
rows, not fewer — 90/103/97 against 72/76/84 — because the contention slowed
the fetch thread more than it slowed the paint, so the frontier advanced more
slowly and the renderer caught rows it would otherwise have passed. The
recorded set is a race between fill rate and paint rate, and load moves both
by different amounts. So "the display records less on a slow machine" is not
the failure mode: the failure mode is that the set is a function of the ratio,
and the ratio is not a property of the work. Twenty-five to thirty-one rows
present in the quiet run and absent from the loaded one, and forty-three to
fifty-three the other way, in the same experiment.

Values never disagreed on rows both runs recorded — 0 in every repeat, in both
arms. The defect is entirely in *which* rows exist afterwards, never in what
any of them says, which is why four cost experiments could not see it and why
a checksum over the values would not have found it either.

## How to recreate

    uv run --group experiments python experiments/orchestrator2-experiments/04-cadence.py

Topology: `source -> pool -> {sweep declares the window; one recorder at reach
1}`, one form throughout at the full luma plane, the crop derived inside the
recorder's envelope — 01-reentry's topology exactly. Core shape: one fetch
thread, two recorder threads, every node PARALLEL, request depth 1; the drawn
arm adds one display thread at a 16.7 ms cadence and the landed arm adds none.
Load is four threads doing 512² float32 matmuls, which release the GIL and
contend for cores rather than for the interpreter.

The renderer draws the newest row whose inputs are resident and never returns
for one the frontier passed. That is the property under test rather than an
oversight: a renderer that came back for skipped rows would be a background
pass in a renderer's clothes and would measure nothing.

`compute_ms` is not comparable across arms — `StepNode` holds its derived
crops between rows and the renderer re-derives both every paint, because a
display draws the row it is on. Within an arm across loads it is the same
code, which is the only comparison made of it.
