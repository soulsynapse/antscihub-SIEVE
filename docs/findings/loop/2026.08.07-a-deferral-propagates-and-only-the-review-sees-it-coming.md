# A deferral propagates down the phase, and only the review sees it coming

The review prompt's continuation rule is written for the ordinary case: reopen
the item, `--next` serves it, the next worker takes another swing. It assumes
the reason the item stopped is something a second attempt could beat. A
deferral is exactly the case where it isn't — the item stopped because
something outside it has to be decided — and the same rule then serves the
*next* item, which is downstream of the thing that wasn't decided.

The asymmetry that matters is what each session can see. The 02.2 worker read
three modules' imports and reached a correct verdict about those three modules;
nothing asked it to look at 02.3, and it would have been scope it wasn't given
if it had. The 02.3 worker would open a clean tree, read `executor.py`, and
rediscover `backend/` and `pipeline_model` from scratch, because the previous
run's reasoning reaches it only as a `gated_on` sentence on a different item
that `--next` never showed it. The review sits between the two with both the
confirmed deferral and the next selection in hand, and it is the only point in
the loop where that pair exists.

The refutation this survived: if 02.3's blockers had been distinct from 02.2's,
deferring it here would be a prediction rather than arithmetic, and predictions
are what work runs are for. They are not distinct. `ExecutionPlan` is the
symbol 02.2 was to define, and the item that would define it is `deferred` on
this same tree — no attempt at 02.3 can produce it without doing 02.2's work,
which is the "no files beyond what the item names" refusal.

## 2026-08-09: a propagation that is real, partial, and four steps away

09.2 deferred `decision` at this review, and 09.7
(`todo/the-outputs-reach-down-behind-the-cards.md`) names it by number: "09.2
... is the first step that puts two edges into one node; this one runs after it
and paints what it built." That is the arithmetic this finding licenses acting
on — the downstream item's declared subject is the deferred item's deliverable,
stated by the downstream item itself rather than predicted here.

It was not deferred, and the two reasons are what this occurrence adds. The
propagation is *partial*: only 09.7's occlusion clause needs an edge long enough
to pass behind a card, and the lanes, the arrowheads and the down-edges of a
linear chain are buildable today. Deferring the item wholesale would block
buildable work to protect one clause, and the repo has no way to say "this
clause waits" — which is the open pool item
`todo/the-review-has-a-path-for-a-partial-deferral.md`, still unspecified, met
here for the second time. And the propagation is *distant*: 09.3 through 09.6
sit between, none of them downstream of 09.2, so the loop has four steps of work
before the question is live. 02.3 was the very next selection; 09.7 is not.

So the reviewer's move scales with distance. What landed instead is a dated
line in 09.7 naming 09.2's gate, so the worker that eventually takes it meets
the deferral in the file it was handed rather than in a `gated_on` sentence on
an item `--next` never shows it. The head finding's open question — whether
propagation should stay a reviewer's judgement — gains a case for *yes*: a
mechanical skip keyed on `gated_on` would have taken 09.7 out of the queue
entirely, and most of it is takeable.
