# A fresh interpreter is where the fixture and the subject come apart

The earlier finding named the failure — a fixture the test file imports supplies
the state the subject was supposed to supply — and left open whether a fresh
interpreter is the general remedy. It is, for this shape, and the reason is
narrower than "subprocesses are more isolated": the corruption here happens at
*import* time, before the first test body runs, so it is not something a test
can undo from inside. Clearing `REGISTRY` would not help, because clearing it
does not unload `sieve.tools.downsample` and `discover()`'s own idempotence then
re-registers nothing — the function's docstring says exactly this. The only
process in which `discover()` is the sole route to a populated shelf is one that
has not imported a tool module by any other route, and pytest's has, necessarily,
because two tests in the same file need `DownsampleParams` as a fixture.

That is the generalisable part: when the subject's observable effect is an
import side effect, the test file's own imports are part of the system under
test, and the boundary of the experiment has to be the process, not the test
function. The same will apply to any decorator-populated shelf v3 grows.

The two surviving mutants were re-checked rather than assumed, and both are
absent-subject rather than untested-behaviour. The ordering key cannot be
distinguished from no key while `sorted` is applied to a one-element sequence;
the `_` skip cannot fire while no `_`-prefixed module exists. Faking either — a
second spec shoved into the process-wide registry, a `_scratch.py` written into
the package for the duration of a test — would produce a green line that proves
the fake and not the code, which is the same defect one level along. What would
refute the ordering judgement is a second tool arriving whose `pkgutil` order
differs from its `(tool_id, version)` order; until then the docstring's claim is
a design statement, not a tested one, and this file is where that is written
down.
