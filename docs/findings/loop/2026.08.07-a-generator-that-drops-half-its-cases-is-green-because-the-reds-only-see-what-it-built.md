# A generator that drops half its cases is green

The item asked for a gate that "cannot go stale when a line is added", and it
got one. Staleness has a second direction, and the file's own two guards are
both shaped for the first: they ask whether a contract contributes *anything*.
A refactor does not empty a contract. It narrows a fold — `product` to `zip` is
one character of intent — and the contract still contributes, every case it
still builds still goes red, and the count silently falls from 36 to 33.

Nothing in the reds can see this, and that is not a gap in the assertions. A
case that was never built cannot fail. The only witness is a second computation
over the same config, which is why `_owed` multiplies where `_cases` walks: two
statements of one rule, kept apart on purpose, so the fold that eats one does
not reach the other. The repo's usual refusal of a second statement of a rule
does not apply where the first statement is a generator — that is the one
construction with no other subject available.

## The shape was copied without the property that made it work (2026-08-08, review of 0920764)

`tests/docs/test_vision_table.py` generates its cases out of `.importlinter`
the same way, and it shipped `test_the_walk_has_a_denominator` for exactly the
reason above — its docstring names "a renamed key under a contract contributing
no cases" and cites `test_contract_lines_go_red.py` as the file that counts its
own cases against that. It does not see it. Renaming `headless`'s
`source_modules` to `source_module` drops 7 of the file's 31 cases and the file
stays green, that guard included: both sides of its equality call
`modules(section, key)` on the same literal keys, so a key that stops parsing
zeroes the walk and the count together. That is the all-or-nothing guard this
finding's `closed` entry already convicted, re-derived as if it were `_owed`.

What `_owed` has and this does not is that the two statements are *spelt
differently* — it multiplies where `_cases` walks — so no single fold lands on
both. Copying the arithmetic without the spelling is the cheap half. The guard
is not inert: a sweep over `refusals()` kills the folds it is shaped for
(source list truncated, forbidden list truncated, `type` test inverted — 3 of 3;
the fourth mutant of the sweep sat inside an assertion's own condition and is
the by-construction survivor
`2026.08.07-a-mutant-inside-an-assertions-condition-survives-by-construction.md`
describes). And no coverage is lost in the tree, because `lint-imports` refuses
a renamed key outright — "source_modules: This is a required field" — so the
shape the docstring claims is caught one command over.

So the defect is the sentence, not the guard, which is the worse half to leave:
the docstring is what a later reader consults to decide whether this walk's
denominator can be trusted, and it currently answers yes about a case where the
answer is no. **A second computation only witnesses a drop that cannot reach
both statements — so a denominator guard's comment has to name the fold it
catches, not the failure it was inspired by.** The general rule this finding's
`open_questions` asks for still has no owner: sweep the generator, not only its
input.
