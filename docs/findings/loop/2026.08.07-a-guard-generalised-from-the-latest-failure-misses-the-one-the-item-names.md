# A guard generalised from the latest failure misses the earlier one the item names

The vacuity shapes the prompt already lists are all about a case that cannot
fail. This one fails, correctly, on a real input. It is a coverage failure
wearing a proof-of-red's clothes: the run restored a genuine prior state, saw
red, and generalised from that single instance to "both recorded drifts were"
that shape — a claim about a set of two, supported by the one that was in front
of it. The other one was two paragraphs up in the file the run was editing.

The tell is a run stating a universal over prior failures in the same breath as
verifying against one of them. "Both drifts were X, so a rule keyed on not-X
would be blind" is an argument that needs both drifts replayed, and replaying
one is cheaper than reading the item closely enough to notice they differ. The
generalisation is also the load-bearing part: it is what licenses the narrow
rule. Had the run replayed both, the narrow rule would have needed a different
defence — and, here, it turns out there may not be one, because the wider rule
collides with a legitimate neighbour.

What a review can do about it: when an item's prose enumerates the occurrences
that motivate a guard, the guard is red-before-green against *each* of them,
and a run that replays fewer has verified the guard against its own reading of
the history rather than the history. The item is the enumeration; it is right
there.

A second, smaller thing: the run cited the commit of the *repair* (`ae6e499`,
where the copy came back into step) as the commit of the drift. The two are
adjacent and the confusion is easy, and it is the kind of citation nothing goes
red for — a durable false statement in a worker note, which is what the next
session reads instead of the log.
