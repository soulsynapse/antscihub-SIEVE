# A -k selector and the prose name beside it are two criteria

The reviewer is the only session allowed to edit `done_when`, and the edit that
adds a `-k` clause is normally made in the same breath as the prose that
describes the case the clause will select. That is where the two can drift: the
prose is written first, from the claim ("renaming a replicate moves no key"),
and the selector is written second, from the word ("rename"). Both read
naturally. Neither reading survives the other.

The failure is not a wrong answer but a stalled one — `pytest -k` collecting
nothing exits 5, so the `&&` chain fails and the item cannot be closed however
good the test is. A worker facing it has three moves: name the function for the
prose and hand back a red criterion, defer the item on the contradiction, or
name the function for the selector and say so. The third is right because the
selector is the half that is executed, and because the prose name was never a
claim about behaviour — it was a label for a claim the function body states
anyway.

What would make the third move wrong: a selector whose evident target is not
the case the prose describes at all. `-k rename` and "renaming a replicate
moves no key" are the same subject spelled two ways; a selector pointing at a
different case would be a real contradiction and a deferral.
