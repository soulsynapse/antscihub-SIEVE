# A mutant anchored on a token that also appears in prose reports a false survivor

This repo's comment discipline is what makes the failure likely rather than
freakish. Modules here explain their own kernels, so the identifier a mutant
wants to change is usually also spelled out in the docstring defending it —
`cv2.INTER_AREA`, `INTER_AREA`, `MIN_STD`, `TARGET_SD` all appear twice or more
in the two files under review, prose first and code second, because the
docstring comes first in the file. A first-occurrence replace therefore hits
prose *by default* for exactly the decisions worth mutating.

The consequence is not a missed defect but a manufactured one, and it points at
the run under review rather than at the reviewer. Had the sweep's output gone
into a finding unchecked, this review would have reported that 04.3's golden
does not pin its interpolation — the single claim the run's commit message
leads with — and the report would have been wrong in the direction that most
damages the loop's record of itself.

The cheap discriminator is that a real survivor should be surprising in
proportion to how load-bearing the mutated line is. A mutant of the one line an
item exists to pin surviving a golden written for it is not a plausible defect;
it is a broken instrument until shown otherwise. That heuristic is what caught
it here, and it is the same shape as
[a test named for a semantic is the one nobody mutates](2026.08.07-a-test-named-for-a-semantic-is-the-one-nobody-mutates.md)
read from the other side: there, an unsurprising line went unmutated; here, a
surprising survival was believed for a moment.
