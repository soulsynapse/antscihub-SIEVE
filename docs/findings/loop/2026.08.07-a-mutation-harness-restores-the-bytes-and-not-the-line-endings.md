# A mutation harness restores the bytes and not the line endings

The prompt already tells a reviewer to restore a tree it perturbed, and this
harness did — in a `finally`, on every path, with the exact string it had read.
It was still wrong, and the way it was wrong is the part worth recording: the
tree ends up in a state where the two commands a reviewer uses to check
cleanliness disagree, and the more detailed one is the one that says nothing is
there.

That asymmetry is what makes it a loop failure rather than a Windows footnote.
`git diff` is the command that answers "what did I change", so an empty diff
reads as an answer. It is not: git compares content after its own newline
normalisation, while the index entry that `status` consults was invalidated by
the mtime and size change. A reviewer who trusts the diff commits the rewrite
inside its own review commit, where it is indistinguishable from the work under
review — three source files touched by a commit whose message says it only
flipped a status field.

The remedy is to stop writing at all. `git checkout -- <path>` restores from the
index, which is the definition of the state the sweep was supposed to leave
behind, and it is correct even for a mutant the harness crashed halfway through
writing.

## The remedy this file prescribes was overturned the next day (2026-08-08, review of 07.3)

The `consequences` above say "Restore a mutated file with `git checkout -- <path>`,
not by writing the string back", and the body closes on "the remedy is to stop
writing at all". Both are now wrong, and wrong in the destructive direction, so
a reader reaching this file first should not act on them:

- [git checkout restores a sweep onto the commit and deletes the work under test](2026.08.07-git-checkout-restores-a-sweep-onto-the-commit-and-deletes-the-work-under-test.md)
  — `checkout` restores to HEAD, so a sweep over a file the session has edited
  but not committed loses the work under test, which is the worst outcome
  available to a mutation harness.
- [git checkout restores the content and rewrites the line endings under autocrlf](2026.08.07-git-checkout-restores-the-content-and-rewrites-the-line-endings-under-autocrlf.md)
  — it does not even solve the problem this file was written about: with
  `core.autocrlf=true` it writes CRLF over a file that was LF on disk.

The live remedy is `scripts/mutation_sweep.py`, whose module docstring cites all
three of these findings and implements the correct form: `read_bytes` /
`write_bytes` in a `finally`, a re-read afterwards proving the restore was
byte-exact, and anchors adapted to the file's own endings by `_match_eol`. What
survives here is the diagnosis — `read_text`/`write_text` round-tripping
retranslates newlines, and `git diff` reports nothing while `git status` says
modified — not the fix.

`supersedes` is untouched deliberately: nothing overturned the *truth* recorded
here, only the remedy proposed from it, and the file is left in place because it
is why the harness has the shape it does. The tree the CRLF half of this file
argues from has itself moved on
([the tree is half LF and two durable instructions still call it CRLF](2026.08.08-the-tree-is-half-lf-and-two-durable-instructions-still-call-it-crlf.md)).
