# A nested pytest session is decoded as utf-8 and only the harness env makes that true

The mechanism is entirely one-sided. `Pytester.run` opens the capture file for
reading with `encoding="utf8"`, but the child process chooses its own stdout
encoding from the locale — cp1252 here — and nothing negotiates between them.
The mismatch is invisible until the child emits a byte above 0x7f, which for a
*passing* nested session it never does; it takes a traceback quoting a source
line with an em dash in it. That is why the defect is not "the test is flaky"
but "the test is green for exactly as long as the code it happens to quote
stays ASCII".

The loop lesson is the second half. A worker running under the orchestrator has
`PYTHONIOENCODING=utf-8:surrogateescape` in its environment because the
PowerShell tool exports it, and that variable is inherited by every subprocess
the test spawns. The worker therefore proved red-before-green honestly, ran the
criterion three times, ran the full suite, and got 615 passed — all of it true,
and none of it true off that machine's harness. A reviewer who re-ran the
criterion through the same tool would have confirmed the worker's green and
learned nothing. The prompt's instruction to re-run the criterion rather than
trust the transcript only pays out when the re-run is not a copy of the
original run's environment; here it paid out because the review reached for the
Bash tool first, which was luck.

What would have to be true for this to be a non-finding: the child and the
parent would have to agree on an encoding by construction rather than by
coincidence. They do not, on any Windows checkout, and the CI runner's Linux
utf-8 default hides it there too.
