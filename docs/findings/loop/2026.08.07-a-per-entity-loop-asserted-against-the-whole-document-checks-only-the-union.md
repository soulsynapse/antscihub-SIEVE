# A per-entity loop asserted against the whole document checks only the union

This is the same root as [a substring assertion is satisfied by the identifier
printed beside it](2026.08.07-a-substring-assertion-is-satisfied-by-the-identifier-printed-beside-it.md)
— an under-specified anchor in a small, deliberately repeated vocabulary — but
the mechanism that widens the anchor is new and does not need the vocabulary to
be repeated at all. Here the strings are distinct: `9 frames` and `5 frames`
cannot be confused for each other. What collapses is the *scope*. Loop over N
entities, assert into a document containing all N, and the N assertions are
individually true whenever the multiset of values is right, in any assignment.
The information the test was written to check — which value belongs to which
entity — is exactly the information the scope throws away.

The reason it survives review by eye is that the loop variable appears in the
assertion. `assert f"detection window: {window} frames, centered" in readme`
reads as per-replicate because `window` came from the replicate; the substring
search is what is not. A reader tracing the data flow sees the coupling and
stops there, because the coupling is real — it is just on the wrong side of the
`in`.

The prediction that would have flipped this: if the assertion had been scoped,
permuting the two windows would fail the README test *first*, before the gate
comparison, and it would name the correspondence rather than a frame of
footage. It did not. That the gate tests caught the permutation is why this is a
finding and not a defect in the oracle — the file's load-bearing assertions are
sound, and the one that is decorative is the one whose docstring claims the most
("the 'same pipeline' claim is checked against v2's own account of itself, not
asserted here"). A test whose docstring is stronger than its assertion is worth
more attention than one with no docstring at all, because the docstring is what
the next reader will trust instead of reading the assertion.
