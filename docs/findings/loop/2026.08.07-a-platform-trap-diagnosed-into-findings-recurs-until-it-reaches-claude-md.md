# A platform trap diagnosed into findings recurs until it reaches CLAUDE.md

Two of the four recurrences were review runs, whose prompt opens by telling them
to read `docs/findings/loop/` before starting. So the failure is not that the
finding was unavailable — it was read, in the same session, by the run that then
made the mistake. Reading a finding puts its *conclusion* in context; it does not
put the trap in the slot the run reaches for when it needs a multi-line string
two hours later. `CLAUDE.md` is in that slot because it is reloaded rather than
recalled.

That distinction is the operational one for the whole findings system: a finding
is the argument, and something that is loaded every session is the instruction.
A finding whose consequence is "do X instead of Y" is not finished until the
sentence lands where the doing happens — and nothing in the loop currently
performs that move, which is why this one took fifteen hours and four permanent
records to make a fifty-word trip.

The count is the smaller half and the same shape as
[the run that corrected an inherited miscount wrote its own](2026.08.07-the-run-that-corrected-an-inherited-miscount-wrote-its-own.md):
two consecutive runs wrote "twice" over a log holding six, the second while
deliberately correcting the same sentence on a neighbouring axis. Neither ran
the grep. The corrective there was "put the count where the gate is"; here there
is no gate to put it in, so the count came out of the sentence entirely and the
command that produces it went in.

What would refute the placement reading: an artefact landing now that the
CLAUDE.md line exists. That would mean the channel is not the variable and the
only remaining fix is mechanical.
