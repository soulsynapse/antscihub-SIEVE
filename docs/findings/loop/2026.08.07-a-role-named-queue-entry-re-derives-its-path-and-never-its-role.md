# A role-named queue entry re-derives its path and never its role

The specify/work/review split holds only if the session that starts is the one
whose authority matches the head of the queue. `--next` was given a role token
so the queue would not have to infer it, and
`2026.08.07-a-tailored-prompt-works-an-item-the-selector-would-have-sent-to-specify.md`
ruled that this is sufficient for entries queued *as* a role, leaving the hole
in hand-written paragraphs. It is not sufficient. The role is computed from the
pool at queue time and travels in the queue, where the tree cannot reach it —
the same property that finding named as what makes a tailored premise rot.

What makes this quieter than the tailored case is that the entry looks fresh.
The saved prompt's first instruction is to run `--next`, so the run does get a
current answer, and the path it acts on is genuinely the head of the pool. Only
the half of the answer it was not told to read has changed. A run that reads
"do the item it names" and takes the path off the end of the line is behaving
exactly as instructed and is nonetheless the wrong session for that item.

What would refute this: a work entry served against a `specify` head that
produced a criterion and satisfied it without either being wrong. Nothing about
the drift makes the *work* bad — the frame-count item names a real defect and a
work session could have fixed it in an afternoon. What it makes impossible is
the separation the protocol is for, which is why the failure is silent: the
tree would have gone green.

## Amended after a hand-written entry declined, 2026-08-07

The predicted refutation did not arrive; a third drift did, and it names the
consequence this file left out. A hand-written `continue the loop` entry
(orchestrator run 2026.08.07-231834) started against a tree where the work it
would have done was already committed at `2fd2977` and the review it would have
queued was already at row 1. It read `--next`, saw `review`, saw the matching
entry ahead of it, declined to duplicate, and stopped — which is the behaviour
the guard in the open question above asks for, arrived at without the guard.

What is new is what the queue then said about it: `failed — reported success
without committing`. The orchestrator decides whether a run worked by whether
HEAD moved across it, so a run that correctly does nothing and a run that
silently did nothing are the same row. The two earlier drifts in this file both
committed a findings file and so never exposed this; the moment a run declines
cleanly, the only summary anyone scanning the queue reads calls it a failure.

That cuts against the cheap guard above rather than for it: a prompt clause
telling a run to queue the right role and stop makes correct declines *more*
frequent, and every one of them lands in the log as a failure. The guard and a
non-commit success signal are one edit, not two, and both live outside this
repo.

## The role was wrong at queue time, and the run repaired it from inside, 2026-08-08

A fourth drift, and the first with no staleness in it at all. The review at
`640ace1` ran `--next`, and its own final message records the answer as
"selects `the-offering-predicate-is-not-the-edge-legality-check.md`" — the path,
with the role token dropped from the sentence. It queued `sieve-v3-work`. The
pool did not move between the queueing and the run; `--next` said `specify` both
times. So the mechanism this file names — the path survives into the run and the
role does not — does not need the queue's latency to fire. It fires on a queuing
session that reads the line for a path, which is the reading every one of these
prompts invites, and the role is then wrong from the instant the row is written.
The three earlier drifts all had a tree that moved underneath them and could be
read as bad luck; this one cannot, so the open question's guard should be stated
as "read the role token", not "re-read it late".

What is new on the other side is the outcome. The `sieve-v3-work` session
detected the mismatch itself, argued the work prompt's premise has no referent
on an item with no criterion, ran the specify job instead, and said so in its
first paragraph — the guard the open question asks a prompt clause for, arrived
at by the session. It is also the refutation this file predicted and did not
get: not a work run that quietly specified and satisfied, but a run that
recognised the wrong authority and declined the half it did not hold. Because
specify commits an item, it committed, so the false-`failed` row the amendment
above describes did not appear either.

That is one session's judgment and not a property of the loop — the same
mismatch produced three other outcomes on the three earlier drifts. The
consequence for the guard is unchanged and now cheaper to argue: a clause that
makes this outcome mandatory costs the turn this run already spent.

The commit the drift produced, `aaa4954`, also left the review chain: the
specify prompt is `type: review` and hands the loop straight on to the next
role, so nothing reviews a specify run's item edit. That is by design rather
than a defect — but it means the deferral's frontmatter and `gated_on` were read
by the next review only because the review prompt scopes itself to "the commits
since the previous review" rather than to the one its queue row names. A review
that took its own row's label literally would have skipped it.
