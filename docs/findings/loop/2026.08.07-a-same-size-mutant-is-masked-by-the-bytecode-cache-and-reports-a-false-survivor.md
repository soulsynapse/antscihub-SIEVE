# A same-size mutant is masked by the bytecode cache and reports a false survivor

The sweep that raised this was a review's, not a worker's, and it convicted a
test that was fine. That is the shape worth naming: the false survivor does not
look like a tooling error. It looks exactly like the finding this loop is built
to produce — a check that names a semantic and does not enforce it — and the
next move it invites is to write a test that already exists, or to mint a
finding asserting a gap in the tree that is not there.

What makes it intermittent is that the masking needs two coincidences at once.
The mutant must not change the file's byte length, which rules out most edits
to prose or to a set literal but is the *normal* case for the edits a sweep
most wants to make: `0.0` to `1e9`, `in` to `is`, one digit of a limit swapped
for another, a set entry respelled. And the write must land in the same
second as the write before it — which a scripted sweep does by construction and
a hand-run one usually does not, because typing is slow. So the failure is
rarest exactly when a human is watching and commonest in the automated sweep
that is meant to replace the watching.

The prediction that would have refuted the reading: if the survivor were real,
running that mutant alone would also report SURVIVED. It reported three
failures. And if the mechanism were something other than the bytecode cache —
a `-x` ordering artefact, a `uv` reinstall, a stale editable install — the
minimal out-of-repo reproduction with no pytest, no `uv` and no package would
have printed the new value. It printed the old one.

The neighbouring finding on line endings
([[2026.08.07-a-mutation-harness-restores-the-bytes-and-not-the-line-endings]])
is the same class from the other side: a sweep is a piece of software that can
be wrong about its own subject, and the cost of that is a wrong claim about the
repo rather than a crash.
