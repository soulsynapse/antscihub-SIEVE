# A tailored prompt outlives the defect it names

The queue's entry `docs/todo/a-merge-keys-its-inputs-by-port.md is deferred on
a trigger nothing` describes a state the tree left at `aed40f5` (12:34), which
gave that item `deferred_for: subject` and `gated_on: the first two-input
tool, which is what gives a - b and b - a a subject`. The entry was queued
before that and is still pending. It was served once at 16:40, ran 1m47s
reading the item and the contracts around it, and died at exit 1 with no
commit, no deferral and no final message beyond its opening sentence — so the
loop cannot even tell from the outcome that the premise was stale. It is
queued again behind this review and would be served again.

The shape is general and the `done_when` mechanism is immune to it, which is
why it is worth writing down. An item carries its criterion inside the file, so
a criterion cannot describe a tree the file has left — the file and the claim
move together. A tailored prompt carries the claim in the queue, where the
tree cannot reach it, and the queue holds no reference back to the item that
would let a later fix invalidate it. `--next` re-derives its answer from the
pool on every call; a queued paragraph derives its answer once.

Two things follow for a reviewer. A tailored prompt is worth queueing only
when the generic re-take would waste a diagnosis, which the review prompt
already says — and the reason is now measured rather than stylistic: the
tailored one is the entry that can rot. And a review that finds a stale entry
at the head of the queue should cancel it and say so, because the alternative
is a run that spends its whole budget establishing that there is nothing to do,
if it survives to say so at all.

## A second occurrence, on reviews rather than work

The same shape reached the review side within the day, twice over one pair of
commits. `4de09b3` minted a `deferred_for: decision` item and queued a tailored
review of it; `dd333f8`, three minutes later, was Kendrick answering that
question, which deleted the item and edited the VISION paragraph the review was
told had deliberately been left alone. The review ran hours later against a
premise that no promptness could have saved — its subject was gone before the
next run started — and had no item to mark `done`. Meanwhile the review of
`dd333f8` was queued twice, once tailored and once generically; `9b6fd25` ran
the generic one and found the tailored duplicate still pending behind it.

What that adds is where the rot is *caught*. Both runs saw the stale entry and
neither cancelled it: the run at `4de09b3` because it could not read a pending
entry's text and would not cancel blind, the run at `9b6fd25` because it read
the label, identified the duplicate, and declined to touch someone else's
queue. The rule that says to cancel is in this finding, and a finding is not in
a review's prompt, so each run re-derived the hesitation from scratch. A
consequence recorded here binds the run that happens to read it.

## Consequences

- This review cancelled the pending entry. The item is `deferred` on a real
  trigger and no boundary waits on it.
- The review at `27bd822` cancelled `review: the promise grew to name
  external inputs`, the duplicate two prior runs had each left standing.
- The crash itself is unexplained — the log ends mid-thinking with no error
  record — and is not attributed here to the stale premise. What is attributed
  is that the run had no work to do either way.
