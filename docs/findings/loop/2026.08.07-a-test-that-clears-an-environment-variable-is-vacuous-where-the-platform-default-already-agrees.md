# A test that clears an environment variable is vacuous where the platform default already agrees

The shape generalises past encodings. Clearing a variable and asserting the
outcome tests the subject only when the *fallback* is observably different from
what the subject would set. `PYTHONIOENCODING` unset does not mean "no
encoding"; it means "whatever the locale says", and on two thirds of the
machines this repo runs on the locale says utf-8 — the same answer the pin
gives. The assertion is then a tautology dressed as a control, and it reads as
a control because the developer who wrote it watched it fail.

That is what separates this from ordinary flakiness and makes it hard to catch:
the red-before-green evidence was real, obtained by a mutation sweep, correctly
reported, and reproduced independently in this review. All of it happened on
cp1252. The prediction that distinguishes a working control from this one is
not "does it fail when I break the subject" but "does it fail when I break the
subject *and* the platform already does the right thing" — and the second half
has to be simulated, because the machine that would answer it is not the one
running the sweep. `PYTHONUTF8=1` is that simulation and costs one environment
variable.

## The harness can be the machine that already agrees

`scripts/mutation_sweep.py:132` builds the child's environment as
`{**os.environ, "PYTHONDONTWRITEBYTECODE": "1"}`, and a sweep *of that module*
runs pytest as the child. Deleting the pair and sweeping reports SURVIVED: the
pytest the sweep launched already carries the variable, so `run_sweep` called
inside it hands it down to the grandchild whether or not the line survives. The
mutant is masked by the harness that was hired to expose it, and the direction
is the dangerous one — SURVIVED convicts a test that is in fact fine everywhere
except under the sweep.

`monkeypatch.delenv(..., raising=False)` in the case is the fix, and the general
form is the one this file already states: a variable-clearing test has to name
what supplies the fallback, and "the process running the sweep" is now one of
the answers. It is also the first place where two different runs of the same
command disagree — the case kills the mutant under a bare `uv run pytest` and
survives it under a sweep — which makes a bare run's green a weaker statement
than it looks.

The stronger control is available and no harder to write: set the parent to a
value the child would *fail* under, not to nothing. Then the fallback never
enters, the two behaviours differ on every platform, and the test's failure
depends on the code rather than on where it ran.

## The ambient state can be the process's own CPU mask, and the file says so three lines above (2026-08-09, review of 47bf42c)

The shape has a second instance and it is not an environment variable, which
is the generalisation the body above predicted. `tests/unit/test_sweep.py`'s
`test_affinity_is_restored_when_the_objective_raises` reads
`psutil.Process().cpu_affinity()`, runs a sweep over one cell whose core set is
`available_cpu_ids()`, and asserts the affinity came back. Deleting
`process.cpu_affinity(original)` from `bench/sweep.py`'s `finally` leaves all
seven cases green, confirmed both by hand and by
`scripts/mutation_sweep.py` (`process.cpu_affinity(original) ==> pass`,
SURVIVED). The cell pins to the mask that was already in force, so "restored"
and "never restored" are the same state and the assertion cannot discriminate.
What still works in the case is the `pytest.raises` — the objective's error
propagates rather than being swallowed — which is not what the name claims.

The new part is where the fallback is stated. In the encoding case the
platform default was unwritten and had to be reasoned out; here the test
module's own docstring opens with it: "Every cell here pins to the *whole*
current allocation, so the mask the tests set is the mask that was already in
force." That sentence is a complete proof of the vacuity, and it is written as
a justification — the paragraph goes on to argue, correctly, that a test suite
pinning itself to four cores would be the thing `bench/sweep.py` refuses. Both
halves are true and the conclusion drawn from them was to assert the property
anyway. So the tell a review can use is not "is the fallback documented" but
the reverse: a docstring that explains why the fixture equals the ambient state
is naming the exact condition under which the assertions below it are dead, and
should be read as a hazard rather than as diligence.

The constraint is real and the assertion is still available: the subject takes
its `psutil.Process()` internally, so a seam — an injected process object, or
`psutil.Process` patched in the sweep module — lets a double record the
restore call without any real mask ever changing. The vacuity is not the price
of the module's refusal; it is what happens when the refusal is accepted as
also settling how the property gets checked.

A second survivor in the same file is the plainer form of the same thing:
`Reading.best` (`return min(self.samples) ==> return max(self.samples)`)
SURVIVED, because no fixture in the file holds two samples that differ — the
interleaving case's objective returns a constant and every other case builds
one-element tuples. `best` and `typical` are argued apart at length in the
docstring and no case can tell them apart, which is the uniform-fixture shape
rather than the agreeing-default one, reached by the same route.
