# A worker on a reopened item leaves the status the review set

The run did its work correctly and reported the status question with an
argument attached, which is why this is a finding about the loop rather than
about the run. Its sentence is "the selector still names it, which is correct —
a work run does not write `done`", and both halves are true statements that do
not support each other. A work run may not write `done`; the status it must
write is `awaiting-review`; and what the selector names the item *for* is the
whole content of the question. The worker checked that the item was still
visible and stopped there.

The prediction that separates this from ordinary lag: if the item had been
merely slow to reach a review, the selector would still have been pointing at
it as a review — that is what the `awaiting-review`-first ordering guarantees
for anything a worker has finished. It pointed at it as work. The state the
ordering protects is one the item never occupied, so the protection was not
slow, it was absent, and nothing in the tree would have said so.

What made this harmless was the queue, not the repo: the worker queued the
review itself as the next entry, so no work run got the chance. That is the
same mechanism the `awaiting-review` finding recorded as the thing being
replaced — a human or a run remembering to type the right next entry — doing
the work the status field was supposed to take over.

## 2026-08-08 — the queue did not save it the second time, and a review watched it happen

The open question above asked what a run served an already-green criterion
looks like. It is now observed rather than predicted, on
`docs/todo/the-gui-skeletons-argued-branches-have-no-case.md`.

`f32e74d` answered that item's expander criterion and left `status: open`.
The review that ran next (`d2510cf`) was reviewing a different item, saw this
one on the way past, swept its criterion itself — "5 killed, 0 survived" — and
named the recurrence by this file's slug in its own final message. It then
queued `sieve-v3-work`, because that is what `--next` selected, and wrote that
the work run "should find the criterion green in seconds and move the status
rather than rebuild anything."

The work run did find it green in seconds and did not move the status,
declining on the ground that `status` and `done_when` are the review's and that
"a stale-looking item is one the next review has to see as it was." Half of
that is the contract — `done_when` is the review's — and half is the same
conflation the verdict above records, now made by a second worker with the
diagnosis already written down one commit behind it. It cost a work run
(13m 03s, no commit) and then a review run to move one word.

What is new is not the worker's half. It is that the guard the original entry
credits — a run remembering to queue the right next entry — was itself the
failure this time. The reviewer had the power to set `status` on any item it
ruled on, had already run the criterion, and instead wrote the instruction into
a queue entry, where it reached a run that read the item and not the queue
label. An instruction routed through a work run is a request; a status field is
a fact the selector reads. The reviewer chose the request.

So the open question narrows: the detectable shape is not only "a work run is
served an item whose `done_when` already passes" but "a *review* has already
observed that and left the item `open`". The first is checkable at selection
time and would have caught both instances; the second is checkable in a review's
own diff, and would have caught this one at the point where fixing it was one
line. Neither check exists.
