# A worker's hand-enumerated mutation sweep held under an independent one

The prior finding's worry is real in general and did not bite here, and the
reason is worth separating from the result. 03.6's worker enumerated seven
mutants against the *change* it had made — the delay, the lag accumulation, the
window length, the index check. The review's thirteen were chosen the other way,
by reading every branch in the file and mutating the ones the worker's list did
not mention, which is where the inherited v2 lines live: `_check_format`'s
comparison, the `rate_changing` refusal, the lead-in suppression in `_completed`.
Those are exactly the lines a worker re-deriving a module does not think to
mutate, because it did not write them — and all of them died, because the case
table carried v2's cases for them.

So the two sweeps were complementary by construction rather than redundant, and
the re-derivation table is what made the second one land: the inherited lines had
inherited cases. A module written from nothing would have no such table, and this
result would not transfer to it.

The one thing the review's sweep added is that the store call has two halves.
`keep.put(key, answers_for, produced)` is the one the worker's finding named;
`keep.get(key, answers_for)` two lines above it is the same choice of index and
survives for the same reason. The disjointness case asserts the property that
licenses both, so nothing is owed — but a finding that names only the write half
reads as though the read half were covered by a case.

## 2026-08-10 amendment: the counter-instance this file's own last paragraph predicts

The review of `todo/the-intent-kind-list-has-no-referent.md` swept
`src/sieve/session/intents.py` with two mutants the worker's list did not name,
each dropping one conjunct of `intent_kinds`' membership test, against that
item's own criterion as the oracle:

    $ uv run python scripts/mutation_sweep.py --file src/sieve/session/intents.py \
        --mutant '<the three-term filter> ==> isinstance(member, type) and is_dataclass(member)' \
        --mutant '<the three-term filter> ==> isinstance(member, type) and issubclass(member, Intent)' \
        — uv run pytest tests/unit/test_intents.py -q \
           -k "the_kinds_are_the_modules_own or a_new_kind_fails_the_list"
    SURVIVED  (Intent conformance dropped)
    KILLED    (is_dataclass dropped)
    mutation_sweep: 1 killed, 1 survived

The worker had reported "both halves kill a mutant" — the last member of the
namespace scan, and a `member.__module__ == __name__` narrowing — two mutants
chosen against the change it had made. Neither anchors a conjunct of the rule,
and the conjunct is where the survivor is: every frozen dataclass in that
module's namespace is an intent, and the eighth kind the test injects is
intent-shaped too, so nothing in the fixture set separates `is_dataclass(member)`
from `is_dataclass(member) and issubclass(member, Intent)` — the shape
[2026.08.08-a-per-subject-revert-is-green-when-the-two-expressions-agree-on-every-fixture.md](2026.08.08-a-per-subject-revert-is-green-when-the-two-expressions-agree-on-every-fixture.md)
records, reached here by a sweep rather than a revert.

So the answer above — re-enumerating found nothing the worker's list had missed
-- does not generalise, and this file already says why it would not: the
executor's inherited lines came with inherited cases, and "a module written from
nothing would have no such table". `intent_kinds` is written from nothing. The
cheap version the open question proposes, mutate what the worker's list does not
mention, is what found it, at two mutants. Read beside
[2026.08.07-a-mutation-sweep-enumerated-by-hand-misses-what-it-did-not-look-for.md](2026.08.07-a-mutation-sweep-enumerated-by-hand-misses-what-it-did-not-look-for.md),
whose worry this is the first v3 instance to confirm.
