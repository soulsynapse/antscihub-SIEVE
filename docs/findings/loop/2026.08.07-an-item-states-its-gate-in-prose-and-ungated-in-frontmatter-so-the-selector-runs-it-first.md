# An item states its gate in prose and `nothing` in frontmatter

The interesting part is not that the run got a field wrong. It is that the run
*derived the gate correctly*, wrote it down in the only place a reader will
find it, and then filled in the field that actually drives the loop from a
template rather than from what it had just concluded. The body is where the
thinking happened; the frontmatter is where the machine reads.

That asymmetry is general to this repo's item format and not to this item. Two
of the frontmatter fields — `status` and `gated_on` — are the only ones with an
operational consequence, and they are the ones a run fills in last, after the
argument is already made. Everything the run knew was in the body four lines
above.

What would refute the framing: an item minted with an ungated frontmatter and a
body that also says nothing about waiting, where the gate was simply never
noticed. That is a different failure — not seeing the dependency at all — and
it would be worse and would not be fixed by any check on the two fields
agreeing. This one is the recoverable kind, because the evidence is in the
file.

The near neighbour is
[2026.08.07-a-settled-adr-discharges-its-unfinished-half-onto-an-item-nobody-minted.md](2026.08.07-a-settled-adr-discharges-its-unfinished-half-onto-an-item-nobody-minted.md):
there a document named a referent that did not exist, here a document names a
prerequisite the selector cannot see. Both are a sentence of prose standing in
for a link the machinery reads.

## 2026-08-08: the same asymmetry read from the other end, and a fork built on it

`a-served-run-elides-the-node-its-file-already-holds.md` closed with a fork it
declared to be Kendrick's alone, because either branch changed what a phase
commits to. The fork's antecedent was a claim about a *different* item's
frontmatter — that
`the-first-source-tool-moves-the-three-single-root-assumptions.md` is phase 3,
so it drains first and the migration behind it becomes reachable. That item
carries `phase: 8` and no step. The fork therefore never had a subject, and the
worker that met it established that by reading the frontmatter and by watching
`--next` select against it, rather than by stopping for a decision.

This is the finding above with the two roles swapped. There, a body stated a
gate the frontmatter did not carry, and the machine ran the body's prose past.
Here, a body quoted *another item's* frontmatter into an argument, the
frontmatter moved, and the prose kept asserting the old value — the failure a
durable instruction always has when it quotes a value rather than citing where
it lives, arriving inside the item format. An item may cite a neighbour and say what it is waiting on; a phase
number copied into a sentence is a measurement written into a durable
instruction, and nothing goes red when it drifts.

What it costs when it goes unchecked is larger here than a mis-ordered queue: a
fork that reserves a decision for Kendrick, resting on a premise the tree
already contradicts, either stalls a reachable item or spends a session of his
on a choice that does not exist. The check is cheap and is now demonstrated —
read the frontmatter of every item a fork's premise names before treating the
fork as live.

## 2026-08-09: the same gap opens at the first build attempt, not only at minting

09.2 (`todo/the-output-is-a-step-and-its-ticks-are-edges.md`) reproduced the
head finding from the other end of an item's life. The work run did not mint
it — it *took* it, spent the run establishing that the item cannot be built
until an ADR rules on whether the tool contract admits a node that emits
nothing, wrote that conclusion into the body as a dated section, and left
`status: open`, `gated_on: nothing` on the argument that the gate was the
reviewer's edit to make. `--next` on that commit answered with 09.2 again, so
the next work run would have spent itself re-deriving a conclusion already in
the file it was handed.

Two things this adds. First, the asymmetry is not a minting habit — filling
`status` and `gated_on` from the shape of the item you found rather than from
what you just concluded happens whenever a session's thinking lands in the
body, and a work run's thinking always does. Second, this occurrence had a
*correct* reading of the prompt behind it: the review prompt says the reviewer
sets `status`, and the worker deferred to that rather than overwriting a field
it had been told was not its own. So the recoverable failure now has a cause
that is not carelessness, and the check belongs to the reviewer — an item whose
newest section concludes "this cannot be built until X" while its frontmatter
says `gated_on: nothing` is the pair to read every time, because the session
that wrote the first half is the one forbidden to write the second.
