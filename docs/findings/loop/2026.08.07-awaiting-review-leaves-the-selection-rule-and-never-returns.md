# An item at awaiting-review leaves the selection rule and never returns

The status field was designed against the failure where a worker writes its
own `done`, and it holds: `done` is always someone else's edit and the item's
diff shows whose. What it does not do is make the second edit happen. The
review is queued by whoever types the next entry, and "continue the loop" is
the entry a person naturally types — it names the loop rather than a step, and
the loop's own selection rule answers it with the next unbuilt thing. The
prompt and the tool agree with each other perfectly and both are looking past
the item that is waiting.

The prediction that would have distinguished this from ordinary latency: if
the pairing were merely slow, an item at `awaiting-review` would grow *more*
likely to be picked up as the loop caught up. The opposite is true. `--next`
takes the minimum step among open items, so once the loop is working 01.x
nothing it can answer will ever be numbered 00.3 again — the item's own place
in the order, which is what makes the queue need no ordering of its own, is
also what puts it permanently behind the cursor.

Two items dropped, not one, and they dropped on consecutive runs. That rules
out a run-specific mistake: neither work run did anything wrong by the rules
it was given. Each wrote `awaiting-review` because a worker may go no further,
said so plainly in its final message, and stopped. The instruction they were
following has no step after "stop", and the queue is not part of the repo, so
there was nowhere for the requirement to live except in a person's memory of
having read the last final message.
