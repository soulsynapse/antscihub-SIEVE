# git add -A commits the tree the run inherited, not the work it did

The two halves of this are one fact seen twice. A run reads the repo once, at
the start, and everything it concludes is about that snapshot; then it commits
the tree as it stands at the end. When those differ, the run argues from the
old text and ships the new one, and both halves are silent — the argument
looks sound because it cites a real sentence that was real when it was read,
and the commit looks clean because `git add -A` never says what it picked up.

What makes it a loop finding rather than a slip is the shape of the mistake.
The worker's closing sentence is the most careful part of its whole run: it
noticed the harness told it to push, went and checked what the repo said, and
declined on the repo's authority. That is the behaviour the apparatus wants.
It was wrong anyway, because the sentence it checked had been overwritten by
an edit the same run was in the act of committing. Diligence about the rules
does not protect a run whose picture of the rules is a snapshot, and no amount
of care inside the run closes that gap — only re-reading at the point of
decision, or not committing what it did not write.

The prediction that separates this from ordinary carelessness: if it were
carelessness, the worker would have been vague about the push. It was not — it
named the rule, quoted its substance, and gave it as the reason. A run that
reasons *harder* here fails identically, which is why the answer has to be
mechanical.

## 2026-08-10, review of `adc0756`: staging by path does not close it either

The rule this finding's open question settled on — a run names what it wrote, so
a file it did not write cannot be swept in — is about `git add`, and the third
occurrence did not use `git add` at all. `adc0756`'s run staged nothing by any
means the transcript shows and committed with `git commit -F <file>`, no
pathspec. That commits the index as it stands, and the index is a shared object:
Kendrick staged a rename into it mid-run, and the citation hunk in
`core/tool_base.py` with it. Staging by path constrains what the *run* adds and
says nothing about what is already there, so the rule as written is satisfied by
a commit that carries someone else's work.

What survives as a rule is one word longer: commit by explicit pathspec, not
just stage by one. `git commit -F msg.txt -- <paths>` takes the named paths from
the worktree and leaves everything else staged, which is also the only form that
leaves the author's index intact rather than emptying it under a message about
something else.

The half that makes it a loop finding rather than a slip is the same as the
first occurrence, and sharper: this run *noticed*. It read `git status`
mid-session, said in as many words that "the author is editing the tree
concurrently", and reported the swept rename in its final message with an
explanation of why it did not revert it. That diligence caught one of the two
hunks it had committed. The second is one line in a file the run legitimately
edited for its own reasons, so it is invisible to exactly the check that caught
the first — a run reading `git show --stat` sees `tool_base.py` and recognises
its own change there. Only the per-hunk diff distinguishes them, and nothing
asks for it.

There is no gate underneath this: no test in the tree checks that an
`adr/…` path cited in a source comment resolves, so between `adc0756` and
`4434cb4` the repo held a comment pointing at a file it did not contain, and
`uv run pytest tests` was green on both sides.

Concretely, the edit was Kendrick's, and it answers the open question in
[[2026.08.07-the-repo-forbids-the-push-that-the-harness-requires]] — the
blanket prohibition is gone and a session with permission may push. The
loop got the right answer to that question by accident, in a commit that does
not mention it, three paragraphs after asserting the opposite.
