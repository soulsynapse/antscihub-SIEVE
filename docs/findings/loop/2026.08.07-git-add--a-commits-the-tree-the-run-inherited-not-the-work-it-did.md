# git add -A commits the tree the run inherited, not the work it did

The two halves of this are one fact seen twice. A run reads the repo once, at
the start, and everything it concludes is about that snapshot; then it commits
the tree as it stands at the end. When those differ, the run argues from the
old text and ships the new one, and both halves are silent — the argument
looks sound because it cites a real sentence that was real when it was read,
and the commit looks clean because `git add -A` never says what it picked up.

What makes it a loop finding rather than a slip is the shape of the mistake.
The worker's closing sentence is the most careful part of its whole run: it
noticed the harness told it to push, went and checked what the repo said, and
declined on the repo's authority. That is the behaviour the apparatus wants.
It was wrong anyway, because the sentence it checked had been overwritten by
an edit the same run was in the act of committing. Diligence about the rules
does not protect a run whose picture of the rules is a snapshot, and no amount
of care inside the run closes that gap — only re-reading at the point of
decision, or not committing what it did not write.

The prediction that separates this from ordinary carelessness: if it were
carelessness, the worker would have been vague about the push. It was not — it
named the rule, quoted its substance, and gave it as the reason. A run that
reasons *harder* here fails identically, which is why the answer has to be
mechanical.

Concretely, the edit was Kendrick's, and it answers the open question in
[[2026.08.07-the-repo-forbids-the-push-that-the-harness-requires]] — the
blanket prohibition is gone and a session with permission may push. The
loop got the right answer to that question by accident, in a commit that does
not mention it, three paragraphs after asserting the opposite.
