# git checkout restores the content and rewrites the line endings under autocrlf

The earlier finding
(`docs/findings/loop/2026.08.07-a-mutation-harness-restores-the-bytes-and-not-the-line-endings.md`)
is right that writing the string back is wrong and that `git checkout --` is
the restore. What it does not say is that the checkout is a restore of
*content*, not of the file. Git's idea of the working tree under
`core.autocrlf=true` is CRLF; a source file that some earlier tool wrote with
LF is, to git, already in the state it means to produce, so nothing flags the
difference either before or after.

The trap is the correction. A careful reviewer measures the bytes before
mutating — which is the right instinct, since the anchor has to be found in
them — sees CRLF afterwards, and puts the LF back. That is the one move that
dirties the tree, and it dirties it in exactly the shape that is hardest to
notice: `status` says modified, `diff` says nothing, and the file is
semantically identical to HEAD. The reviewer is then one `git add -A` from
committing a whole-file line-ending rewrite inside a commit whose message says
it flipped a status field
(`docs/findings/loop/2026.08.07-git-add--a-commits-the-tree-the-run-inherited-not-the-work-it-did.md`).

So the earlier finding's open question has an answer: the check is `git
status`, and it is the check because it is the one that disagrees with the
reviewer's own measurement. A restore that satisfies `status` and offends the
byte count is finished; a restore that satisfies the byte count and offends
`status` is not.
