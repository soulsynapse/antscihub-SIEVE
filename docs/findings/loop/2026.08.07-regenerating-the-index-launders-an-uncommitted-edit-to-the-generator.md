# Regenerating the index launders an uncommitted edit to the generator

The prompt's "regenerate the indexes" reads as a no-op that brings a derived
file into step. It is a no-op only when the deriving code is the committed one.
Here it was not, and the failure is quiet in both directions: the index changes
in a way the session did not intend, and `git status` shows the generator as
just another modified file in a diff the session is about to stage. Staging by
explicit path — which this repo requires — does not protect against it, because
the index *is* one of the explicit paths and the generator sits right beside it
in the same status output.

What makes it worth a file rather than a shrug is that the loop regenerates
indexes on nearly every run, work and review alike, and the generator is the
one file in the repo whose uncommitted state silently rewrites a committed
artifact. The check is one line before the regeneration — `git status` on
`scripts/` — and the tell is that the session did not touch it.

The cause here was a second session in the same worktree, which the run could
not see and correctly refused to guess at. A run that finds `doc_index.py`
dirty without having written it should say so rather than restore quietly —
the restore is what would have destroyed the other session's work, and did:
the edit was re-applied by hand afterwards.
