# Reverting the implementation is no proof when the item created the module

This is the same defect as
[one red per contract certifies the contract, not its lines](2026.08.06-one-red-per-contract-certifies-the-contract-not-its-lines.md),
arrived at from the opposite direction. There the sample was five edges standing
for 23; here it is one import error standing for seven assertions, and the ratio
is worse because the single failure is not even a member of the set it claims to
cover — a `ModuleNotFoundError` is not any test failing, it is every test not
running.

What makes it easy to miss is that the worker's account is accurate. 03.7 said
"all seven were shown failing first," and they were. The claim is true and
certifies nothing, which is exactly the shape a review that only checks
claims-against-diff will pass.

The prediction that would have refuted the concern: a mutant of the landed
implementation that no test caught. Six mutants and every test moved for at least
one, so this file's assertions are real — the finding is about the *proof*, not
about 03.7's tests, which hold.

## Second instance, same shape, and the remedy held (2026-08-08)

06.6 created `src/sieve/pipeline/series_collector.py` and its six tests in one
commit, and its account of red was the same single collection-time
`ModuleNotFoundError` — accurate, and certifying none of the six. The review did
not re-run it. Three mutants of the landed module instead, each anchored on a
sentence the module docstring makes: `self._series = self._stacked()` moved
outside the `measure` context (the span closing before the array exists),
`refill` no longer clearing `_start`/`_rows` (a second drag's graph carrying the
first's frames), and the frame-gap comparison short-circuited to false. Each
killed exactly one test and a different one — the three claims separate, which
is what the import error could not show.

Two things this instance adds. The mutant set was drafted from the *docstring*
rather than from the diff, which is what made the one-mutant-one-test mapping
checkable: a module that states three claims should have three tests that move
independently, and a claim with no mutant that isolates it is either untested or
not really a separate claim. And the cost was about three minutes of a review
that had already re-run the criterion — cheap enough that the open question
below (whether the burden should move to the worker, red against an importable
stub) still has no forcing argument on either side.

## Third instance, and the mapping is the reusable part (2026-08-08)

07.2 created `src/sieve/session/session.py` and its eight tests in one commit,
and its account of red was the same pair — `file or directory not found` for the
missing test module, then one collection-time `ModuleNotFoundError` for the
missing implementation. Accurate; certifying none of the eight.

Seven mutants of the landed module, drafted from its docstring and its method
docstrings as in the 06.6 instance: `open` seeding `_past` with the loaded
project, `commit` not clearing `_future`, `commit` not pushing the present,
`undo`'s bottom-of-stack guard forced true, `undo` not pushing onto `_future`,
`redo` not moving the present, and `save` writing the redo top instead of the
present. All seven killed by
`uv run pytest -q tests/unit/test_session.py`.

What the run of the sweep once per test adds — eight further sweeps, `-k` on one
test name each — is the mapping, and it is worth the extra couple of minutes
because it is the thing that answers *is any test in this file vacuous*, which
the aggregate KILLED column does not. All eight tests moved for at least one
mutant and all seven mutants died to a distinct subset of tests, so nothing in
the file is vacuous and no two mutants are testing the same thing.

The reading worth carrying is of the near-miss rather than the result.
`a_reopened_project_round_trips` — one of the two tests the criterion selects —
is killed by exactly one of the seven, and it is the mutant that seeds history
at `open`, which the test asserts against directly. Its actual subject, that the
document comes back off disk as the one the session was holding, was reached by
none of the seven, because at the moment that test saves, the redo stack is
empty and even the deliberately misdirected `save` writes the right value. An
eighth mutant, `save ==> pass`, kills it. So a mutant that fails to separate is
usually a fact about *when* the fixture reaches the mutated line, not about the
test — and the sweep is only proof for the claims some mutant actually reaches.
Reading the survivors, and noticing which claim no mutant touched, is where the
review earns the sweep.

## Fourth instance, and a mutant shape the aggregate hides (2026-08-08)

07.5 created `src/sieve/gui/param_form.py` and `core.tool_base.resolved_schema`
with their tests in one commit (`b19599f`), and its account of red was the pair
this file already records — `file or directory not found` for the two missing
test modules, then `ModuleNotFoundError` with the module moved aside. Accurate,
certifying none of the six tests. What is new is that the *worker* ran the
sweep, and reported it as "mutation sweeps over `param_form.py` kill every
branch I wrote — both connects, the enum's stored-value lookup, the label map,
all four bound keywords and the unbounded default." The review's sweep agrees
with the aggregate and disagrees with one of the named claims, which is the
part worth carrying.

Six mutants, drafted from the module docstring as in the 06.6 instance:
`_NUDGE ==> 1e-6` (v2's bug, the one the commit message claims to have departed
from), `_UNBOUNDED ==> 100`, the integer/real type branch forced false, the
refusal replaced by a silent fallback, the spin box's connect moved ahead of its
`setValue`, and `combo.activated ==> combo.currentIndexChanged`. Five killed.
The last survives the whole test file, and it survives for a structural reason
rather than a missing fixture: `_enum` sets the current index *before*
connecting, so the construction claim is carried by the ordering, and the
signal's identity — user-chose-this versus value-passed-through — has no
consequence until something exercises a closed combo under arrow keys, which
`todo/the-generated-controls-commit-on-intent-not-on-pass-through.md` is for.

The generalisation, and the reason this is not a note about one combo: a mutant
that *deletes* a wiring proves the wiring exists, and a worker counting "both
connects" as killed has proved exactly that. Only a mutant that *swaps* one
wiring for its plausible alternative proves the choice was a choice. Where a
docstring argues for a specific API over a named neighbour — `activated` not
`currentIndexChanged`, `INTER_AREA` not `INTER_LINEAR` in the 03.7 instance —
the swap is the mutant that matches the sentence, and deletion is the one that
flatters it.

The `_NUDGE` result is worth recording separately because it reads as
unfalsifiable and is not. `0.0 < minimum()` is true of `1e-6` as a number, so
the assertion looks like it would pass under v2's value; it fails because
`QDoubleSpinBox.setDecimals(3)` rounds the range it is given and `1e-6` becomes
`0.000`. The test is held by Qt's rounding rather than by the comparison it is
written as, which is a dependency a later author could remove by widening the
decimals without touching the test.

## Fifth instance, and where a worker's own mutant lands (2026-08-08)

07.7 created `src/sieve/gui/graph_panel.py` and its five tests in one commit
(`3843283`), with the same account of red this file has now recorded five times
— `file or directory not found`, then `ModuleNotFoundError`. As in the 07.5
instance the worker mutated as well, and reported one: deleting `x_of`'s
no-axis guard, which it had added after green. Both facts are true and the
module still shipped four live survivors, all in `value_range`
(`todo/the-gui-skeletons-argued-branches-have-no-case.md` holds them).

The reading is about which mutant a worker reaches for unprompted. It mutated
the line it was least sure of — a guard written after the tests, whose case it
had just added — and the four it did not mutate are the ones its own module
docstring argues hardest for: the zero floor, the headroom, the degenerate span,
the empty axis. That is the opposite selection from the one the 06.6 instance
found worked. Drafting from the docstring is not merely a good habit for a
reviewer; it is the correction for a bias in the worker, whose sense of what
needs proving tracks its own uncertainty rather than its own claims. A worker
that argues a decision in prose has already decided it is right, which is
exactly when it will not think to test it.

So a review meeting a worker-run sweep should not read it as coverage of the
diff. It covers the worker's doubts. The claims the commit message states most
confidently are the ones to sweep first.

## Sixth instance, and the sweep earned itself (2026-08-08)

07.10 created `src/sieve/gui/expander.py` and its two tests in one commit
(`2c11da9`), with the same account of red — `file or directory not found`, then
`ModuleNotFoundError` — accurate and certifying neither test. Seven mutants
drafted from the module docstring; five survived, and three of them are one
defect that the docstring's opening sentence is the whole subject of. It is
written up separately, because the shape is about a test's observable rather
than about proof of red:
[a widget's state accessor reads the toggle and not the thing toggled](2026.08.08-a-widgets-state-accessor-reads-the-toggle-and-not-the-thing-toggled.md).

Worth recording here only for the ratio. Five instances of this file ended with
"the file's assertions are real, the finding is about the proof"; this is the
first where the sweep convicted the tests as well, and it took the same few
minutes as the ones that acquitted. That is the argument against the open
question below settling toward moving the burden to the worker: the value is in
a second party drafting mutants from the docstring, not in when it happens.

## Seventh instance, and it does not need a new module (2026-08-08)

07.12 (`4bd9e5d`) created no module. `gui/app.py`, `gui/canvas.py` and
`gui/tuning.py` all predate it, and the item's case was added to an existing
test file. This is the condition under which the consequence above says
revert-and-run works — "the tests predate the change" is the wrong half of the
distinction; what actually matters is whether the *first line the new case
touches* exists in the reverted tree.

It did not. The worker stashed `src/sieve/gui/*.py` and reported
`AttributeError: 'MainWindow' object has no attribute 'viewport'`; the review
reverted the same directory to the parent commit and got the identical line.
Accurate both times, and certifying nothing past it — the case's substance is
four assertions about pixels and geometry that never ran, exactly as a
`ModuleNotFoundError` never runs a file. A new *accessor* on an existing class
collapses a revert the same way a new module does, and there is no reason to
expect it to be the last shape that does: a revert proves red at the earliest
line that stops existing, which is rarely the line the case is about.

The mutant that separates is the one that leaves the accessor in place and
changes only the claim. `if values is None or not self._viewport.set_values(
index, values): ==> if values is None:` — the viewport keeps its accessor, keeps
painting, and paints the source instead of the render — fails on
`assert (160, 120) == (5, 4)`, which is the geometry assertion rather than the
attribute lookup. That is the case's actual subject reached, and it took one
edit.

So the reviewer's rule is not "mutate when the item created the module" but
"mutate whenever the revert's red is an `AttributeError`, an `ImportError`, or
any other name error" — those are the outputs that are identical for a file of
real assertions and a file of `assert True`, and the class of items that
produces them is larger than this file's title suggests.

## Eighth instance: a command that does not exist yet (2026-08-09)

08.4 (`753c241`) created `src/sieve/cli/materialize_cmd.py` and eight cases in
one commit. Its account of red was `src/` stashed and all eight failing — true,
and the failure is `Error: No such command 'materialize'` with exit 2 from
every one of them, which is the same output a file of eight `assert True`
invocations would produce once the command is missing. A Typer registration is
the same shape as the missing module and the missing accessor before it: the
revert's red lands at the earliest line that stops existing, and for a CLI item
that line is the dispatch, three frames above anything the case asserts.

Five mutants of the landed command, drafted from its module docstring as in the
06.6 instance, all killed and each by a distinct subset:
`read_range(plan) ==> plan.span`, `replicate=target ==> replicate=None`,
`luma=plan.luma ==> luma=False`, `with_crop(record).save ==> save` (write
without registering), and the two-root refusal short-circuited to pick the
first. The window mutant is the one the item's argument turns on and it is
carried by exactly one case.

What is new here is where a mutant landed against the *test's own* prediction.
`test_the_command_derives_the_format_and_offers_no_flag_for_it` says in its
docstring that no chroma graph exists on the shelf, so "the derived value cannot
be contrasted against a colour one", and asserts the absence of a `--format`
flag as the thing it can prove instead. The `luma=False` mutant kills it anyway:
the record carries `format`, so the derivation is observable at the document
even where no graph can disagree about it. A case that argues in prose that it
cannot discriminate something is worth one mutant before that is believed — the
sentence is a claim about the fixture, and the record written beside it may
already separate what the pixels cannot.
