# The case counts in the re-derivation items are right and the class counts are not

PLAN.md's re-derivation clause states v2's case count in the item "so a table
with fewer rows than v2 has cases is visibly wrong rather than quietly short".
The class count rides along in the same sentence and nothing reads it — no
table is organised by class, and a v2 class that v3 splits or merges changes
the number without changing a single claim.

That makes the discrepancy a clerical one and not a contradiction, which is the
distinction the loop's deferral rule turns on. Had the *case* count been wrong,
the table's completeness would be uncheckable and the item would have had to
stop; a wrong class count leaves the one arithmetic PLAN.md asks for intact. The
predicted alternative was the opposite result — a case count off by a few, from
an item drafted against a v2 file that had moved — and it did not appear in any
of the seven files.

Two items downstream carry the same defect. Recording it here is what stops
each of them spending a session rediscovering it, and what stops one of them
deferring over it.
