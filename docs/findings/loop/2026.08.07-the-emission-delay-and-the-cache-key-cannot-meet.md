# A lagging node and a keyed node are disjoint sets, so one mutant survives

The delay 03.6 adds is a per-node lag: at loop step `j` a node answers for
`j - lag`, where `lag` accumulates its own declared lookahead and its
upstream's. Two indices therefore exist where v2 had one, and the store call is
the place that has to pick the right one — an entry filed at the reading index
would be served back to a run that reached that frame at a different step,
which is a wrong answer from cache and the failure `cache_key.py`'s asymmetry
rule spends comparisons on.

The prediction that would have made it testable: a node that both lags and
carries a key. There is none, and not by accident. The two conditions are
mutually exclusive through a policy neither module states as a pair —
`cache_policy` refuses a key to a windowed tool, `Dag.node_keys` refuses one to
anything whose upstream has none, and only a windowed tool can introduce a lag.
So the correct spelling and the mutant compute the same number on every graph
schema v1 can express, and a case written against the difference would be
asserting something that cannot vary.

What the file asserts instead is the disjointness. That is the load-bearing
claim: it is what licenses the loop to hand `answers_for` to the store without a
second thought, and it is exactly what stops holding if the windowed frontier is
ever admitted to the cache.
