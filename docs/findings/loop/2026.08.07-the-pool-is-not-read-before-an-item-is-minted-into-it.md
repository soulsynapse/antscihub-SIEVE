# The pool is not read before an item is minted into it

The defect is not that a run noticed a red `ruff format --check` and wrote it
down — that is exactly right, and the second run's diagnosis was better than
the first's. It is that the run had every piece of evidence that the item
already existed and none of it was in a place a run looks.

That is the generalisable shape. `doc_index.py` makes the index a build
artifact, and a build artifact is something you run and commit rather than
something you read. Every other consistency property of the pool is checked by
the gate, so the one property the gate cannot check — that two items are not
the same item — is also the one nothing prompts a human or an agent to look
for. Automating a check makes its output invisible; the properties left over
are the ones that then rot.

What would refute the framing: a run that reads the pool table by habit and
mints a duplicate anyway, which would mean the failure is in recognising a
paraphrase rather than in never looking. Nothing in the two logs suggests
that — neither run opened the pool table at all.

## Amended after 04.3, 2026-08-07

A third run minted the same defect a third time, as
`ruff-format-is-not-in-the-gate.md`, and this one is not from a repeated
attempt at one item — it is a different item, a day later, four commits on. So
the rate is not "an item retried twice sees its own leftovers"; it is that any
run noticing this defect mints it, because noticing it and having read the pool
are independent events. The duplicate again landed adjacent to the original in
the pool table, this time on the line directly below, and again went in
unread.

That settles the open question in the direction of the habit rather than the
absorption: the review has now absorbed this twice, the absorption is cheap
each time, but it does not decay — three occurrences at a rate of roughly one
per two work runs that touch the formatter, with no mechanism that would ever
make the fourth less likely. The cost is not the merge, it is that a defect
with three items and no owner reads as three separate problems to anyone
scanning the pool.

What is worth carrying into the work prompt is narrower than "read the pool":
read it *before minting*, which is a single table and a few seconds, and only
in the moment a run is about to add to it. A run that never mints never needs
to look.

The new information is in the duplicate's *content*, not its existence. It
counted five unformatted files where the original counted two, because Phase 05
added three more, which turns the original's argument from "a formatter moved
under two files" into "the count rises with the tree". That is worth folding in
and was: the merged item now carries the five, and the duplicate's `mypy`
observation with it. The absorption stayed cheap for the fourth time running,
which is the whole reason it keeps not being fixed — but the merge is now
rewriting the item's central claim rather than appending a sentence to it, and
that is the point at which a duplicate stops being free.

The prompt edit is the outstanding action, and it is not a reviewer's to make:
the work prompt lives in `../agent-orchestrator/prompts/`, outside this repo,
and distillation into it is Kendrick's pass. Four occurrences is what this
finding can contribute toward it.

## Amended after the rule reached CLAUDE.md, 2026-08-07

The outstanding action landed, by a route this file did not consider. The third
amendment argued the sentence belonged in the work prompt and the fourth
measured its absence there; `grep -i pool ../agent-orchestrator/prompts/sieve-v3-work.md`
still matches nothing but its own "pool item with a `priority`" line. Instead
the rule is in CLAUDE.md's minting paragraph — read the pool table in
`docs/todo/.index.md` before minting into it, a duplicate that paraphrases
rather than collides goes red nowhere — and in the review prompt's step 5. At
the time of writing that CLAUDE.md edit is in the working tree and uncommitted,
made outside any loop run, so a later reader should check whether it survived
into HEAD before treating the rule as live.

The route matters for what this finding predicts next. The work prompt already
defers to "CLAUDE.md's merge-first rule" by name, so a worker that reads
CLAUDE.md now gets the habit and one that skims only its prompt does not — which
means the next occurrence measures whether workers read CLAUDE.md, not whether
the rule exists. That is a sharper test than the four occurrences above, all of
which were measured against a tree where the rule was written nowhere. The
refutation this file has always asked for — a run that reads the pool table and
mints a duplicate anyway — is now the one that can actually happen.
