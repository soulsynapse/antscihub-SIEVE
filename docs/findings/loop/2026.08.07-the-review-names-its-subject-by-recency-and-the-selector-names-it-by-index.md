# The review names its subject by recency and the selector names it by index

The prompt and the selector were written against the same picture — a work run
finishes, the review runs next, the transcript on top of the log stack is that
work run's. Nothing enforces it. `--next` orders by the index, so the item it
serves is the oldest unfinished one, and the run that finished most recently is
whatever happened to finish most recently. The two coincide by convention.

The convention broke here in the way that is hardest to notice: both halves
answered confidently. `read_run_log` returned a complete, articulate final
message about `render_window`'s cold first frame and a per-sample budget gate,
and every sentence of it was true. It was simply about a different item. A
review that had read it as its subject would have found no contradiction, no
missing evidence, and nothing to report — it would have re-ruled a ruling.

The prediction that separates this from ordinary lag: if the pairing were only
slow, the transcript would be the right run's and merely old. It was not old,
it was newer than the subject by an hour, because the subject's session never
entered the queue. Recency cannot point backwards to the item, and the item is
what the ruling is about.

## 2026-08-09: it recurred, and this time recency itself was wrong

Same truth, second occurrence, new mechanism — amended rather than superseded.
The review of `bd416d8` opened `read_run_log` with no label and was handed the
`phase 9 walk-back corrections` run, which made `bd416d8` at 01:28. But
`5c1ed7e` was committed at 01:35 by a *later* run, `sieve-v3-review — render on
settle`, whose log sits in `~/.agent-orchestrator/logs` between the two: the
queue's finished list did not carry it, and `read_run_log` given its label
answered that no run by that name has a log. So the no-label call did not
return the most recent run at all — it returned the most recent run the queue
would admit to, one commit behind git.

That breaks the last thing recency still had going for it. The 2026-08-07 case
was recency pointing confidently at the wrong item; here recency was not even
recency, and the only artifact that ordered the two runs correctly was
`git log`. A review that trusts the no-label call and then reads `git log` to
find "the commit(s) it made" meets a HEAD its transcript never mentions, and
the natural repair — assume the transcript is terse — is again the wrong one.

What made this review recoverable was not the log. It was that no item stood at
`awaiting-review`: the walk-back run touched three items and moved no status,
and the item the earlier run had ruled was already `done` with its criterion
still green when re-run. The item is what said which runs had already been
adjudicated, exactly as this finding's open question predicts, and the queue
and the log stack each said something false on the way there.

## 2026-08-09, later: a third mechanism, and this one has a name

It recurred again the same night, and the mechanism is now identified rather
than inferred: the orchestrator answers `read_run_log` and `list_queue` per
*project*, and takes the project from the calling session's working directory,
so this loop's rows are split between the worktree root and `docs/todo`. The
review of `6c0eddb` was handed the 02:07:28 worker — which made no commit —
while `6c0eddb` itself was made by a run in the other partition that this
session cannot name, list, or open. Recency was not stale and not mis-ordered;
it was answered over a subset. Measured and argued in
[2026.08.09-the-queue-is-partitioned-by-the-directory-a-row-was-queued-from.md](2026.08.09-the-queue-is-partitioned-by-the-directory-a-row-was-queued-from.md),
which is where the fix belongs; what it adds here is only that this finding's
open question — identify the subject from the item — is now the third
independent thing that would have prevented the failure, and again the only
thing that did.
