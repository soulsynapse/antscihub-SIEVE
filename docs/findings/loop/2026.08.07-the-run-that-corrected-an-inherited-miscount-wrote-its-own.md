# The run that corrected an inherited miscount wrote its own

The two numbers failed differently and that is the finding. The table's three
verdict counts were exact because each is one grep over a column that exists in
the file; the two prose totals were wrong because they are arithmetic a reader
has to redo, and the run that wrote them had just spent a session proving that
nobody redoes it.

So the corrective is not "check the count" — 03.3 demonstrably was checking
counts, that is what its finding is — but "put the count where the gate is".
`tests/docs/test_doc_index.py` already fails on a stale index; a table total
stated in the same file as the table is the same kind of claim and is currently
the only kind the loop states in prose.

Neither number was load-bearing. That is why it survived a run whose whole
subject was counting, and it is the argument for the check rather than against
it: a wrong number nothing reads is exactly the one no reader catches.
