# A case that calls the guard directly cannot see the caller that pre-empts it

The review prompt already lists "a guard with a test and no production caller"
among the vacuity shapes. This is the variant that survives that check: the
caller exists, it is named in the item, and it is even the reason the guard was
written — and it still never reaches it, because it performs the same
validation one statement earlier over the same node set. Reading `plan.py:185`
confirms `node_keys` is called; only reading the fifteen lines above it shows
that the `params` dict comprehension has already raised by then.

The tell is available without running anything: the wrapper's argument is about
what a *reader* sees, and no case in the diff is written from the reader's side.
Every assertion is on `node_keys` called directly. A single case at the level the
argument is about — build the plan, catch, assert the node id is in the message
— would have been red for the whole feature rather than green for its interior,
and it is the case the item's own prose describes ("this fires mid-traversal in
the interactive loop"). Where a change is justified by what someone downstream
will read, the case belongs at the surface that reader touches, and a case at
the raise proves only that the raise raises.

The prediction that would have distinguished a working change: with the wrap in
place, a `--edit` that sets a bad parameter prints a message containing the node
id. It prints `BlurParams` and `radius`, the same as before the commit —
`preview_cmd._render` catches `ValidationError` and hands its text straight to
the user, and that `ValidationError` came from `plan.py`, not from the walk.

## Amendment 2026-08-08: the prediction was run, and it flipped

`3a04cd7` wrapped `ExecutionPlan.build`'s own validation in the same
`InvalidParamsError`, closing `todo/the-named-params-refusal-is-pre-empted-by-
its-only-caller.md`. The review of that commit ran the falsifiable prediction
this file wrote down — a `--edit` that sets a bad parameter prints the node id —
rather than inferring it from the diff. `sieve preview --edit tail:factor=999`
now exits 1 with `node tail has invalid parameters: 1 validation error for
DownsampleParams / factor …`, where before it printed the model and the field
alone. The guard has its reader; status moves to `closed`.

The prediction earned its keep twice over. It is the only assertion in this
file that could distinguish "the wrap now runs" from "the wrap now runs and the
message survives the CLI's own handler" — and the second half was not free,
because the refusal reaches the user through a *different* `except` arm than it
did before the wrap (`GraphError`, not `ValidationError`). Nothing in the diff
says so; the integration case that covers the surface stayed green because its
assertions name the exit code and the field, neither of which moved. Writing the
prediction at the reader's surface is what made a one-command check sufficient.
