# A case with two raises blocks proves red only for the first

Nothing was wrong with the diff: both folds really had been indexing `fed[0]`,
and both really do raise once unpacked. The defect is in what the proof
covered. The worker changed two call sites in one commit, wrote one case
asserting both, reverted nothing selectively, and quoted a single
`DID NOT RAISE` as the case's red. That quote is evidence about
`Dag._elements` and about nothing else, because the case ends there — had
`_element_names` been left indexing, or had the second assertion named a
function that could not reach the branch at all, the same quote would have been
produced and read the same way.

This is not the two-refusals-share-a-code shape
([2026.08.07-two-refusals-that-return-the-same-code-shield-each-other-from-the-only-case.md](2026.08.07-two-refusals-that-return-the-same-code-shield-each-other-from-the-only-case.md)),
where the case cannot discriminate between the guards. Here the case does
discriminate — running it against a tree with only the second hunk reverted
fails on the second line, which is exactly what makes the second half real.
What fails is the *method* used to check: one revert of the whole diff answers
only for whichever subject the case reaches first, and the number of reverts a
multi-subject case needs is the number of subjects.

The generalisation for the vacuity list is not about assertions per case in the
abstract — a case with five asserts over one call is fine, since the call is the
subject. It is: **when one case calls production code more than once, the
proof-of-red has to be run once per call.**

## Amendment 2026-08-08: it recurred four minutes later, and the per-call run paid

`8fba2b7` — the next work run after the one this file was written against, and
the one the review that wrote this file did not overlap with — landed
`test_a_non_positive_output_rate_is_refused_on_the_warmup_side` with the same
shape: two `pytest.raises` blocks, two calls to `input_warmup_frames`, and a
worker quote of a single red that can only be the first. The recurrence is not
evidence the worker ignored anything; this file lives in `findings/loop/`, which
the review prompt tells a *reviewer* to read and tells a worker nothing.

Running the second call on its own is what this file asked for, and it earned
its cost differently than expected. Both halves were genuinely red, so the case
survived — but the probe returned `ValueError` where the diff's own comment
predicted a frame count, which is how the false-premise defect in
`2026.08.08-the-proof-of-red-corrects-the-item-and-leaves-the-comment-it-was-
written-from.md` was found at all. The per-call run is not only a vacuity check:
it is the only place a comment about *why* the second call is there gets tested
against what the second call does.

## Amendment 2026-08-08: a third occurrence, and the second half was real again

`0297f49` added two `pytest.raises` blocks to
`test_a_node_id_the_filesystem_cannot_hold_is_refused_at_load` — a direct
`Node(node_id="abc\n", …)` and a `Project.from_yaml` whose quoted scalar carries
the same newline — and quoted one `DID NOT RAISE`, which pytest can only have
produced at the first. The review reverted `NODE_ID_PATTERN` to its `$` spelling
and ran the second call on its own: the document loads with
`node_id == 'abc\n'`, so that half is genuinely red too and the case survives.

Three for three now, across three workers and two days, none of whom had read
this file — it is in `findings/loop/`, which the review prompt hands to a
reviewer and the work prompt hands to nobody. The pattern is stable enough that
the cheap side of the open question below is worth costing again: the recurrence
rate is a property of where this lives, not of the workers, and a per-call rule
a worker never reads is enforced only at review time, one revert at a time.

A second-order trap this occurrence added: checking the `from_yaml` half by hand
is easy to get wrong in the shell, because both a real newline and a `\n` escape
inside a double-quoted YAML scalar reach the parser and only the escape survives
as a newline — a bare one folds to a space and is refused for *that*, which
looks like the same green. The probe has to print the parsed value before it
trusts the refusal.

## Amendment 2026-08-08: four blocks, and a mutation sweep does not stand in for the reverts

`38271aa` is the fourth, and the largest: `test_a_tool_id_or_version_ending_in_a_
newline_is_refused` holds *four* `pytest.raises` blocks — a direct `Node` and a
`Project.from_yaml` for each of `tool_id` and `version` — against a single quoted
`DID NOT RAISE`, which can only be the first.

The new thing this occurrence tests is whether a mutation sweep discharges the
obligation. The worker also swept each constant back to its `$` spelling and
reported **KILLED** for both, which is genuinely more than one revert: it proves
`TOOL_ID_PATTERN` and `SEMVER_PATTERN` each have at least one block that depends
on them. It is still not per-call. A `SEMVER_PATTERN` kill is satisfied by block
two alone, so blocks three and four — the `from_yaml` route for both fields, and
the only blocks that test the item's actual premise about a hand-edited document
— are covered by neither the sweep nor the red. **A sweep is per-subject; the
rule is per-call, and a case with two calls per subject leaves half of itself
unproved under both.**

The review ran the two document blocks on its own against `$`-spelled constants:
`yaml.safe_load` yields `'downsample\n'` and `'1.0.0\n'` and the model accepts
both, so both halves are genuinely red and the case survives. Four for four.

The second-order trap the previous amendment recorded fired on this review's own
probe, which is the first evidence it generalises past the run that found it: a
hand-written repro of the `from_yaml` half went through two shells, one of which
ate a backslash, and the parsed value arrived as `'downsample '` — refused by the
`$` spelling too, and indistinguishable from a green at the exit code. Printing
the parsed value before trusting the refusal, as that amendment instructs, is
what caught it. The instruction is now load-bearing rather than cautionary.

That bears on this file's open question. A rule of one call site per case would
have split this into two cases and made each revert trivially per-subject — but
it would also have removed the artifact that made the false comment visible,
since the comment exists precisely to justify a second call sharing a case. The
question stays open, now with a cost on the cheap side of it.
