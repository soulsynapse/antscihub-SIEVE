# A correction inherits the finding's citation and drops its scope clause

A review convicts a comment of naming a consequence its branch does not have.
The run that fixes it reaches for the finding that measured the branch, and
writes that finding's verdict into the comment with the citation attached. The
verdict, though, was written to be exact: `image_of`'s guard is
output-equivalent to the division it refuses on every constant frame *that
carries no positive infinity*, and the finding's own open question is whether
anything on the graph can produce the exception. What landed in the comment was
"the guard is not visible in the pixels", full stop, with the finding cited
after it.

The citation is what makes this worse than an ordinary overclaim. An unsourced
absolute invites a reader to check it; a sourced one does not, and the source
here says something narrower than the sentence it is supporting. The failure the
comment now carries is the opposite of the one it replaced — the old clause
argued a consequence the branch does not have, the new one argues the branch has
no consequence — and both would be read by someone deciding whether the branch
can go.

What the criterion could see was the two strings: the false clause absent, the
true half present. It cannot see what took the false clause's place, which is
the whole of the correction. A replacement is not bounded by a substring test
and a review is the only thing that reads it, which is the general form: **a
`done_when` over prose can require a deletion and cannot require a
replacement's accuracy.** Rotations that hand prose to a worker should expect
the review, not the criterion, to be what holds it.

What would flip this: a comment convention that quotes the finding's scope
clause verbatim when it cites one, so dropping the clause is visible in the
diff rather than only in the finding.

## The second replacement was accurate, and the review is still what held it (2026-08-08)

The queued requalification landed at `4a5256e`. Re-derived here rather than read
off the transcript: on `[[5, 5, inf]]` the guard draws `0 0 0` and the division
draws `0 0 255`, and on a constant frame the division's every cell is `0`, so
the comment's scope clause and its named exception both hold. Nothing in the
criterion moved — the item's `done_when` is untouched and still red at `exit=5`
— which is the finding's own verdict observed a second time from the other side:
the accurate replacement and the inaccurate one are indistinguishable to
everything except a reader. The convention the section above asks for is
followed at this one site and is written down nowhere, and whether it becomes
one is a decision, not a defect.
