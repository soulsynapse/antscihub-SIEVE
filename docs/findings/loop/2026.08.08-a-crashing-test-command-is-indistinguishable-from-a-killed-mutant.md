# A crashing test command is indistinguishable from a killed mutant

`mutation_sweep.py`'s docstring opens on four ways a hand-built sweep lies, and
every one of them is a *false SURVIVED* — the direction that convicts correct
work. This is the fifth and it points the other way: a false KILLED, which
certifies work that was never done. That asymmetry is why it matters more than
its one observation suggests. A false survivor sends a worker to write a test
that already exists and the wasted effort is visible; a false kill closes an
item, and nothing downstream ever asks again.

The prediction that would have refuted the reading: if a crashed run were
distinguishable from a failed one, the sweep's output would carry the difference
somewhere. It does not — `run_sweep` keeps only `returncode != 0`, discards the
captured output entirely, and `main` prints the boolean.

What makes the GUI suite the place this bites is that it is the only oracle in
the tree with a native event loop in it. The four earlier findings
([[2026.08.07-a-same-size-mutant-is-masked-by-the-bytecode-cache-and-reports-a-false-survivor]]
and its neighbours) are all about the subject file; this one is about the
command, and no amount of care with anchors and bytes reaches it.

## The baseline closes the deterministic half (2026-08-08)

`a078f11` acted on the first consequence: `run_sweep` runs the command once on
the original bytes and refuses, showing the command's own output, unless that
run is green. Verified by mutation — `if baseline.returncode != 0: ==> if
False:` is killed by
`tests/scripts/test_mutation_sweep.py::test_a_red_baseline_is_refused_rather_than_swept`.

The finding stays `open`, because the shape it was measured on is the shape the
baseline cannot see. A broken import, a mistyped path after `--`, or a suite
that is simply red fails the baseline too, and those are now refusals. The
access violation was one run in nine — an intermittent crash is by construction
free to land on a mutant run instead, where it still reads as a non-zero exit
and still prints KILLED. The baseline lowers the odds by one sample; it does not
convert the class into a refusal the way it does for a deterministic red.

What would close it is a KILLED that is read off something other than "the
command failed" — the mutant's own test failing rather than the process exiting
non-zero. That is a larger change than this item asked for, and the reason to
write it down here is that the second consequence above still stands: a worker
pasting `N killed, 0 survived` over a Qt oracle should still have seen the same
command green either side of it, and now has the baseline as half of that.

## A mutant that will not compile is a false KILLED the baseline cannot reach (2026-08-08, review of 274278d)

A deterministic instance of the class, hit live and reproducible in one command,
so the intermittency the section above rests on is not what the hole needs.
Anchoring on an indented statement and writing the replacement with matching
indentation —
`--mutant "            del self._entries[index] ==>            pass"` — loses
one leading space from the replacement, because `parse_mutant` partitions on
`" ==> "` and the separator's own padding is stripped from both sides. The
result is `IndentationError` on import, the whole oracle collapses, and the
sweep prints KILLED. The correctly-indented form of the same mutant,
`--mutant "del self._entries[index] ==> pass"`, prints SURVIVED — the true
answer, and the one the review acted on.

Two things follow. The narrow one is a usage rule with no code behind it: anchor
on the bare statement and let the file's own indentation stand, because an
anchor that carries leading whitespace is one space away from convicting the
tests of a coverage they do not have. The broad one is that the baseline check
structurally cannot cover this. The baseline runs the *original* bytes; every
way a mutant makes the subject unparseable — a bad indent, a dangling
`else:`, a replacement that closes a bracket the anchor opened — is invisible to
it and lands as KILLED. That is the same false-kill direction as the access
violation but with none of its luck in it: it fires every time, on any subject,
under any oracle, and the worker's paste reads clean.

The fix implied is the same one the section above names — read KILLED off the
mutant's own test failing rather than off a non-zero exit — but this instance
also admits a cheap partial the crash does not: compile the mutated bytes before
running the oracle and refuse the mutant, the way a non-unique anchor is
refused, rather than scoring it. A `SyntaxError` from `compile()` is a mutant
that was never applied, not one that was killed. Folded into
`todo/a-sweep-reads-killed-off-its-oracles-own-crash.md` rather than minted:
whether the harness grows a compile gate or the whole KILLED signal is
re-founded is one decision, and that item is where it sits.

## The deterministic member is a refusal now (2026-08-10)

The decision came out as the cheap partial rather than the re-founding:
`refuse_unparseable` compiles the mutated bytes before they are written and
raises `SweepError`, so a mutant that will not parse is refused the way a
non-unique anchor is and the sweep prints no verdict for it. Both verdicts of the
one mutant are run by
`test_mutation_sweep.py::test_a_mutant_that_leaves_the_subject_unparseable_is_refused`
against an oracle that `exec`s the subject: the indented form SURVIVED, and the
form one space short exited non-zero and printed KILLED before the gate — the two
answers a space apart, now one refusal and one verdict. Killed by
`refuse_unparseable(subject, mutant, mutated) ==> pass` and by
`compile(mutated, str(subject), "exec") ==> None`.

The finding stays `open` on what it is named for. The access violation is
intermittent and free to land on a mutant run, where it is still a non-zero exit
and still prints KILLED; only the deterministic member is converted. What would
close it is unchanged — KILLED read off the mutant's own test failing rather than
off the process exiting non-zero.
