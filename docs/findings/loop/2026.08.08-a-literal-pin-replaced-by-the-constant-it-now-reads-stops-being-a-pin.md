# A literal pin replaced by the constant it now reads stops being a pin

`2026.08.07-a-run-that-convicted-v2-of-a-tautological-bound-shipped-one-in-the-same-commit.md`
names the check that would have caught this — "for each assertion in a new test
file, what value the right-hand side would take if the left-hand side's inputs
were wrong" — and names it for *new* files. The assertion here is in a file two
phases old, and the diff that broke it is one identifier wide. Nothing about it
looks like writing a test.

The mechanism is that the refactor and the vacuity are the same edit. The
declaration moved from a literal to a named constant, which is the right move
and is what every other tool on the shelf does; the assertion that used to
stand outside the declaration and check it against a hand-written number was
updated to keep compiling, and updating it correctly *is* what removed its
subject. There is no version of "update the test to match the rename" that
preserves the check — it has to be replaced by a different kind of check, one
that reads data rather than the constant, and that is a decision rather than a
mechanical follow-through.

What makes it hard to see from inside the run: the worker's own summary called
it "now pins the constant", and in the ordinary sense of the word it does — the
line names the constant and would fail if somebody wrote a *third* value into
`SPEC`. What it can no longer fail on is the constant being wrong, which is the
only thing anybody wanted from it, and the two readings are one sentence apart.

Red-before-green does not reach this because the habit is scoped to cases the
run adds. An edited assertion is green before and green after, and a run that
reverts the implementation to prove red proves it for the new case only. The
cheapest generalisation is the earlier finding's question asked of the diff
rather than of the file: every assertion whose text the commit changed, not
every assertion in a file the commit created.
