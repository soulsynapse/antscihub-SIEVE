# A number an item orders re-measured is taken by a probe the tree does not hold

The shape is not a wrong number. All three measurements may well be right, and
the third is consistent with the argument beside it — a guard that keys strictly
fewer frames withheld only lead-in frames, and the figure is counted over the
span, so it did not move. The defect is that "may well be right" is the whole of
what the review can say. Every other claim 06.5 made was checkable: the
criterion re-ran, the two tests failed against a reverted `executor.py`, the
mutants were the revert, the named twin in `test_executor.py` was a root and was
genuinely innocent. The reuse figure is where the chain of verification stops,
and it is the number Phase 6's gate and `PLAN.md`'s revival table rest on.

What makes it recur rather than being one run's shortcut: the item itself orders
the re-run in prose ("if the recomputed count does not fall, the admission did
not reach the path the preview actually takes"), and prose is not a thing a
worker runs. So each session reads the order, builds a probe, gets a number,
records it, and deletes the probe — leaving the next session, and the next
review, exactly where this one was. A criterion cannot cover it either, because
the claim is about a figure and not about a pass, which is precisely why the
producer has to be committed instead.

A negative result would have looked like this: the reuse counter turning up in
`tests/bench/`, `src/sieve/bench/`, or a `scripts/` probe, with the finding's row
citing it. Nothing does, and `src/sieve/bench/metrics.py` names five timed keys
and no count.

## Discharged for the reuse row, half-discharged for the second (2026-08-08, review)

`the-reuse-figure-has-no-committed-probe.md` landed at `e6acf46` and this file's
`open_questions` — whether the same holds of the other rows — now has an answer
for the one other row of this shape, and the two halves came out differently.

The reuse row is fully discharged, and by more than the item asked for. It is not
merely produced by the committed pass; it is asserted as an equality on the shape
the admission rule forces, so the figure is in the test source and a change to
`cache_key.cache_policy` is red rather than re-measured. The review confirmed
that directly: mutating the admission rule to refuse a bounded warmup again kills
`test_reuse_on_a_post_edit_render`. That is the strongest form of a committed
producer — the number cannot go stale silently, because staleness is a failure.

The stack share is only half discharged, and the residue is worth naming because
it is the same defect one notch weaker. `Reading.stack_shares` is computed on
every pass, which is what the item asked for, but nothing asserts or prints the
figure — the test judges only pairing and positivity, both of which the nesting
guarantees. So the number in the finding is still re-taken by instrumenting: to
check it, this review had to bracket the values by mutating the assertion into a
range and reading KILLED/SURVIVED off `mutation_sweep.py`. A committed producer
whose product no reader can read leaves the finding's row exactly as checkable as
a deleted probe did, one command cheaper.

That is not the worker's error — the item explicitly ruled a gate out of scope,
and a ceiling on the share is a number nobody has argued for. It is the part of
the question the item deferred, and it is a decision (does an unceilinged reading
assert its own spread, or is a reading that only a mutation can read enough?)
rather than work waiting to be picked up. The residue is recorded here rather
than minted, and
[2026.08.08-a-re-measurement-explains-a-gap-that-one-more-pass-of-its-own-probe-covers.md](2026.08.08-a-re-measurement-explains-a-gap-that-one-more-pass-of-its-own-probe-covers.md)
is what the unreadable reading cost in the same commit.

## 2026-08-10 (amendment): it recurs on 10.3, and the load-bearing half is pinned

`findings/2026.08.10-the-block-field-costs-a-millisecond-and-a-drag-pays-none-of-it.md`
carries two cost rows — 2.11 ms field against 0.92 ms greyscale at B = 16,384,
and 1.91 against 0.72 at B = 6 — from a probe the tree does not hold. Its
`files:` list names one source module and no producer, and this review could not
re-run either row. Same shape, third instance, and this time the item did not
even order the measurement in prose: the item asked for an attribution to
`scrub_to_repaint`, and the numbers are what the run produced to argue the
attribution was wrong.

The distinction worth recording is that the *conclusion* is pinned and the
*numbers* are not. What the finding is for — that a drag builds no field, so the
cost lands on the render and not on the scrub — is asserted in
`tests/bench/test_gui_loop_budget.py` as `drag_field is None`, and the review
killed nothing to believe it. So the un-reproducible rows here support a claim
that would go red on its own if it stopped being true, which is strictly better
than the reuse row's position in the body above, where the figure *was* the
claim. The rule this suggests: an uncommitted probe is tolerable exactly when the
sentence it supports has a committed oracle of its own, and is the defect above
when it does not.
