# A per-subject revert is green when the old expression and the new agree on every fixture

The prior review's rule — when one case calls production code more than once,
run the proof-of-red once per call
([2026.08.07-a-case-with-two-raises-blocks-proves-red-only-for-the-first.md](2026.08.07-a-case-with-two-raises-blocks-proves-red-only-for-the-first.md))
— is what found this, and it is not what this is. There the case could
discriminate and the *method* answered for only the first subject. Here the
method was run correctly, per subject, and one subject came back green.

ee6ffc5 has three subjects: `FrameSpan` gains a `lookahead` field and counts
`target` back by it, the executor sets that field from `node_lookahead_frames`,
and `detect.run` replaces `row = len(window) - 1 - params.lookahead_frames().frames`
with `row = window.target_row`. Reverting `src/` wholesale is red, and so is
reverting either of the first two — the executor's index check catches the
frame the tool answered for. Reverting `detect.py` alone is green across its
whole file, because the two expressions compute the same row for every
configuration that exists: `detect` declares its lookahead as both a bound and
a refinement, so `params.lookahead_frames()` and the `node_lookahead_frames`
the span carries are the same number, and the only tool that would separate
them — one declaring the bound alone — is not among the fixtures.

The shape to look for is not "too few cases". It is a refactor that replaces a
derivation with a lookup where the two agree on the whole fixture set, so the
green is the fixture set's answer rather than the code's. It reads exactly like
a covered change: the suite is thorough, the case names the property, the
worker can quote a red from the same session. The red the worker quoted here
was real and was about something else — updating `detect`'s `span_for` helper,
which had been building a window that reached ahead without saying so, moved
the emitted frame and turned the case red. That red belongs to the helper.

What separates the two expressions is a configuration, not an assertion, so the
repair is a fixture and not a stronger check: the branch a change is *made for*
has to be among the fixtures, or the change is unfalsifiable no matter how the
cases are written. A reviewer meeting a green per-subject revert should ask
which configuration would make the old and new expressions disagree, and then
whether that configuration exists in the tree.

## The same shape at whole-module scale (2026-08-08, from 07.4's review)

07.4 wrote `src/sieve/gui/walk.py` rather than reuse `pipeline/dag.py`'s
`linear_order`, and said why in the module docstring and the commit message: a
window has to draw a document that branches, that is disconnected, or that will
not run, and `linear_order` refuses all three. The item's only fixture is a
three-node chain. Under `uv run pytest -q tests/gui`, `if node.node_id not in
fed:` → `if True:`, `for child in children[node.node_id]:` → `for child in ():`,
and `return tuple(ordered)` → `return tuple(pipeline.nodes)` all survive: the
suite cannot tell the walk from the document's own node order, because on a
chain they are the same tuple.

Nothing here was reverted and no expression was replaced, so the per-subject
revert this file was written about would never have run. The transferable
sentence is the one above it — the configuration that separates the two
answers has to exist in the tree — and it applies to a *new* module as
sharply as to a refactor: the justification a worker gives for writing code
instead of reusing code names the fixture that code needs, and a review can
read the fixture requirement straight off the justification without waiting
for a mutation sweep to suggest one. `todo/the-gui-skeletons-argued-branches-have-no-case.md`
carries the three fixtures.

## A fixture chosen for readability is the thing that disarms the claim (2026-08-08, from 07.6's review)

07.6 ported v2's timeline and wrote `src/sieve/gui/timeline/geometry.py` fresh.
Its `frame_at` docstring argues at length for dividing by `width` rather than
`width - 1`, naming the failure the wrong divisor causes: it "reaches the last
frame a pixel early and never reaches it at all when the band is wider than the
asset is long, which is the ordinary case for a short source in a maximised
window". Under `uv run pytest -q tests/gui`, `int(x / self.width *
self.frame_count) ==> int(x / (self.width - 1) * self.frame_count)` survives, and
so does `MIN_BAND_PIXELS = 2.0 ==> 0.0`.

Both survive for one reason, and it is written into the fixture in so many
words: `test_timeline.py` sets `STRIP_WIDTH = 1000` over `SOURCE_FRAMES = 1000`,
commented "as wide as the source is long, so every frame owns exactly one column
and a click can name any of them". One column per frame is what makes the
arithmetic in every assertion readable, and it is also the single configuration
in which the two divisors agree everywhere a case looks and in which no span is
ever narrower than the floor.

What this adds to the two instances above is the *source* of the missing
configuration. In the `detect` instance the separating configuration did not
exist in the tree; in the `walk.py` instance the fixture was the only document
anyone had. Here the author chose the fixture deliberately, for a good reason,
and the reason is exactly the degeneracy. A round number that makes the
assertions legible — one column per frame, one pixel per unit, a stride of one —
is a warning rather than a convenience: a reviewer should read the fixture's own
justification comment and ask which of the module's claims that justification
collapses. `todo/the-gui-skeletons-argued-branches-have-no-case.md` carries the
two fixtures.

## The fixture's convenient value is the claim's own boundary (2026-08-08, from 07.7's review)

07.7 wrote `src/sieve/gui/graph_panel.py`, whose module docstring leads with
"Zero is the floor of the value axis" and argues it from the absence of tick
labels. Its fixture is `series([0.0, 1.0, 2.0, 3.0])` — a run of small integers
from zero, chosen so the axis arithmetic in the assertions reads by eye. Under
`uv run pytest -q tests/gui`, `low = min(float(finite.min()), 0.0) ==> low =
float(finite.min())` survives, because a series whose minimum is zero cannot
tell a clamped floor from an auto-scaled one. `_HEADROOM = 1.06 ==> 1.0`
survives beside it, and for a related reason: the only assertion on the top of
the axis is that the last point sits above the first.

The three instances above are all round-number fixtures — one column per frame,
one pixel per unit, a three-node chain. This one is narrower and worth naming on
its own: the fixture's *starting value* is the constant the claim is written
about. A floor at zero, a threshold at one, an epsilon, an origin — whenever a
module argues for pinning a quantity at some constant, a fixture that happens to
contain that constant makes the pin and its absence agree. The check is
mechanical and does not need a sweep to suggest it: read the constants a
docstring argues for, then read the fixture for those same numbers, and every
coincidence is a claim with no case.

The test comment is what makes it read as covered. Above the surviving line,
`test_the_panel_draws_the_series_it_is_handed` says "Zero is the floor of the
value axis, so it lands on the bottom edge: with no tick labels a raised floor
would draw a value of nothing as something" — the decision, stated as the
assertion's rationale, in a test that is green either way. A comment naming the
decision is not evidence the case discriminates it, and a reviewer scanning for
uncovered claims will skip exactly the lines that name their claim best.
`todo/the-gui-skeletons-argued-branches-have-no-case.md` carries the fixtures.

## The boundary is the *neighbouring rule's* answer, not a constant (2026-08-10, from 09's band-surface review)

The section above is about a fixture containing the constant a docstring argues
for. This is the same shape where the coincident value is not a constant at all:
it is what a *different* rule in the same function would have returned.

`kind_editors.BandEditor._dragged_to` has two claims in four lines — the drag
commits the value under the cursor, and an edge stops at the other rather than
crossing it. `test_band_surface.test_a_dragged_band_surface_handle_enters_as_a_set_param`
drags the low edge to 0.75 of a fixed 0..1 axis while the high edge sits at
0.75, so the value the first claim commits and the value the second claim clamps
to are the same number. Replacing the branch with `return (high, high)` — the
clamp swallowing the drag entirely — leaves all nine cases in the file green.

Two things generalize. The coincidence was not chosen for legibility: 0.75 and
0.75 are a plausible band and a plausible drag target, and nothing about the
pair reads as round. So the previous section's check — read the constants the
docstring argues for, then look for them in the fixture — does not find this
one. What does find it is reading a function's claims *against each other*: when
one function answers a gesture two ways, the fixture has to put the two answers
at different numbers, or the case pins whichever the reviewer did not have in
mind. Second, the mutant is killed here, but by
`tests/bench/test_band_surface_budget.py`'s distinct-band anti-vacuity
assertion — a window-driving benchmark five layers away from the arithmetic.
Coverage that lives only in the slowest gate in the tree is coverage the next
person to touch the editor will not see fail.
`todo/the-gestures-replicate-address-is-carried-by-lines-nothing-reads.md`
carries the fixture, beside the address case it already asks for on the same
gesture.
