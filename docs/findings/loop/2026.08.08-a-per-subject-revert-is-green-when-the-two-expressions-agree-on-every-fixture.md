# A per-subject revert is green when the old expression and the new agree on every fixture

The prior review's rule — when one case calls production code more than once,
run the proof-of-red once per call
([2026.08.07-a-case-with-two-raises-blocks-proves-red-only-for-the-first.md](2026.08.07-a-case-with-two-raises-blocks-proves-red-only-for-the-first.md))
— is what found this, and it is not what this is. There the case could
discriminate and the *method* answered for only the first subject. Here the
method was run correctly, per subject, and one subject came back green.

ee6ffc5 has three subjects: `FrameSpan` gains a `lookahead` field and counts
`target` back by it, the executor sets that field from `node_lookahead_frames`,
and `detect.run` replaces `row = len(window) - 1 - params.lookahead_frames().frames`
with `row = window.target_row`. Reverting `src/` wholesale is red, and so is
reverting either of the first two — the executor's index check catches the
frame the tool answered for. Reverting `detect.py` alone is green across its
whole file, because the two expressions compute the same row for every
configuration that exists: `detect` declares its lookahead as both a bound and
a refinement, so `params.lookahead_frames()` and the `node_lookahead_frames`
the span carries are the same number, and the only tool that would separate
them — one declaring the bound alone — is not among the fixtures.

The shape to look for is not "too few cases". It is a refactor that replaces a
derivation with a lookup where the two agree on the whole fixture set, so the
green is the fixture set's answer rather than the code's. It reads exactly like
a covered change: the suite is thorough, the case names the property, the
worker can quote a red from the same session. The red the worker quoted here
was real and was about something else — updating `detect`'s `span_for` helper,
which had been building a window that reached ahead without saying so, moved
the emitted frame and turned the case red. That red belongs to the helper.

What separates the two expressions is a configuration, not an assertion, so the
repair is a fixture and not a stronger check: the branch a change is *made for*
has to be among the fixtures, or the change is unfalsifiable no matter how the
cases are written. A reviewer meeting a green per-subject revert should ask
which configuration would make the old and new expressions disagree, and then
whether that configuration exists in the tree.

## The same shape at whole-module scale (2026-08-08, from 07.4's review)

07.4 wrote `src/sieve/gui/walk.py` rather than reuse `pipeline/dag.py`'s
`linear_order`, and said why in the module docstring and the commit message: a
window has to draw a document that branches, that is disconnected, or that will
not run, and `linear_order` refuses all three. The item's only fixture is a
three-node chain. Under `uv run pytest -q tests/gui`, `if node.node_id not in
fed:` → `if True:`, `for child in children[node.node_id]:` → `for child in ():`,
and `return tuple(ordered)` → `return tuple(pipeline.nodes)` all survive: the
suite cannot tell the walk from the document's own node order, because on a
chain they are the same tuple.

Nothing here was reverted and no expression was replaced, so the per-subject
revert this file was written about would never have run. The transferable
sentence is the one above it — the configuration that separates the two
answers has to exist in the tree — and it applies to a *new* module as
sharply as to a refactor: the justification a worker gives for writing code
instead of reusing code names the fixture that code needs, and a review can
read the fixture requirement straight off the justification without waiting
for a mutation sweep to suggest one. `todo/the-gui-skeletons-argued-branches-have-no-case.md`
carries the three fixtures.
