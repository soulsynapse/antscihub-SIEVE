# A restored sweep subject came back mutated after the sweep had exited

The failure is loud in both directions, which is why it is `open` rather than
urgent. A sweep started on an already-mutated subject either cannot find its
anchor (the mutated text is not the anchor) or, if the mutant it carries is one
of its own, refuses on a red baseline showing the failing test. Both refuse; no
run of the twelve reported a verdict computed against a dirty tree. What it
costs is a stalled run and a tree a worker could stage without noticing.

The two occurrences bracket a series of otherwise identical invocations, so
nothing about the command separates them: the same two mutants over the same
file, once with `-q tests/gui` and once with the same oracle narrowed by `-k`,
both ran clean before and after the runs that did not.

A restore that is verified against bytes the same process read cannot detect
this class at all. The check that would is a comparison against the subject as
git has it, or a refusal to start when the subject is dirty and the run did not
mean it to be — but a sweep is legitimately run over uncommitted work under
test (`2026.08.07-git-checkout-restores-a-sweep-onto-the-commit-and-deletes-the-work-under-test.md`),
so the second is not free either.

## 2026-08-09: a third occurrence, on another subject, and this time it was not loud

The class is not `geometry.py`'s. A four-mutant sweep over
`src/sieve/gui/chain_stack.py` printed `4 killed, 0 survived` and exited 0 — so
its own read-back passed — and the next command read
`PORT_LEADING = -20.0`, the third mutant's bytes, still on disk. Two immediate
re-runs of the identical command, with the subject's md5 taken either side,
restored byte-exact; nothing about the invocation separates the occurrence from
its own repeats, which is what the two above already said.

What is new is the cost. The section above rests on both prior occurrences being
caught by a *following sweep*, which refuses on an anchor it cannot find or a red
baseline. Here the following command was the item's own `done_when`, which has no
such refusal: it went red on an assertion about the work just written, in a run
whose whole job was to turn that assertion green. The obvious reading of a red
criterion on freshly written code is that the code is wrong, and the false
verdict cost a diagnosis — a font-metrics hypothesis, two probe prints and four
runs — before the mutant on disk was the thing being looked at rather than the
placement rule under test. So the failure is loud only for as long as the next
command happens to be a sweep, and the loop's own habit is to close a sweep by
re-running the criterion.

The cheap defence needs no decision about the read-back: read the subject after a
sweep before reading anything else as a verdict. `md5sum` either side of the
command, or `git diff` over the subject, distinguishes the two readings in one
line, and the sweep's exit status does not.
