# A runtime check was refused as a lint the tree does not have

The worker's reasoning was not lazy — it is the good version of the argument. It
identified the real failure mode of the obvious class-level test ("a tuple of the
three enumerated by hand is per-constant testing in a loop: the fourth constant
is absent from the tuple for exactly as long as it is absent from anyone's
mind"), and then asked what a check that did *not* have that failure mode would
have to do. That step is where it went wrong: it answered "read the module's
source for `re.compile` and judge the literal" and stopped, because that is a
lint and the tree has none.

`re.compile` returns an object that remembers the string it was compiled from.
Enumerating the class therefore needs no parsing and no allow-list — import the
package, walk its modules, and every compiled pattern in the tree is in hand with
its own source string attached. The check the worker ruled impossible is nine
lines and needs nothing installed.

What makes this a loop finding rather than a code finding is the asymmetry in
what the loop verifies. The case the worker *writes* owes a proof of red; the
case it *declines to write* owes nothing, and the declining argument lands in a
`findings/` amendment where it reads as settled to everyone after. A false
premise costs more there than in a comment: the amendment is the reasoning a
later session inherits for why the tree has no guard, and it will be read by
someone who has no reason to re-derive it. The generalisation is the mirror of
the proof-of-red rule — **a claim that no check is possible is a claim about the
tree, and it is cheap to run.**

The prediction that would have distinguished a working argument: with the
worker's premise true, no test could name the five patterns without an author
naming them first. The probe above names nine bindings, including two the
worker's own `src/` grep did not surface as separate names, and the author named
none of them.
