# A split item copies its paragraphs and the original closes still holding them

A fold and a split are the same edit run backwards, and the loop has a rule for
one and not the other. Folding says the survivor takes the paragraph and the
emptied item is closed with a dated section naming where it went — the point
being that after the edit exactly one file argues the claim. Splitting has no
such sentence anywhere, so a worker doing the right thing structurally still
leaves two.

What makes it worse than an ordinary duplicate is the status asymmetry. The
copy that stays behind is in the file the review is about to close. A duplicate
between two open items is redundant; a duplicate between a `done` item and an
`open` one is a claim about the tree that is false in one of its two homes, and
nothing goes red for it — `doc_index.py` counts items and validates
frontmatter, and neither notices that two bodies argue the same unbuilt case.

What would refute the framing: if the parent's criterion had covered the split
paragraphs, keeping them would be right and the new item would be the
duplicate. It does not — `-k arity_the_shelf_does_not_declare` selects two
cases, and the `ENUM` half wants a refusal `core/tool_base.py` does not make.
