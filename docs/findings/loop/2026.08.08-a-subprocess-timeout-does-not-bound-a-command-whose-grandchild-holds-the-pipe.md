# A subprocess timeout does not bound a command whose grandchild holds the pipe

The test that proves the hang is a kill uses `sys.executable -c` — a direct
child with no descendants — and it is green and honest. The oracle the loop
actually passes after `--` is `uv run pytest`, which is a grandchild shape, and
the probe above is the difference: the same timeout, the same exception, forty
times the wall clock.

The prediction that would have refuted this: if `run()` bounded the call rather
than the child, the probe would have raised at ~3 s regardless of what the child
spawned. It raised at the grandchild's own sleep, twice, on both the synthetic
and the live shape.

## The bound is there, by both halves at once (2026-08-10)

`run_sweep` no longer calls `subprocess.run`. `_run_bounded` redirects the
streams to files and waits on the process handle, so `communicate()` has no pipe
to block on, and on `TimeoutExpired` it kills the tree — `taskkill /T /F` on
Windows, `killpg` on a session started for the purpose — before re-raising.

Measured against the live shape rather than the direct-child one: a mutant whose
command spawns a grandchild that outlives its parent, under a 1 s per-mutant
timeout, took **20.24 s** on the unchanged tree and **under 10 s** after
(`tests/scripts/test_mutation_sweep.py::test_a_hung_grandchild_does_not_outlive_the_mutant_timeout`,
whose second assertion is the grandchild's own disk marker never appearing —
redirection alone returns on time and leaves the work running, which is why the
consequence above named the tree kill as the one that ends it). Both halves are
load-bearing: `stdout=out, stderr=err ==> stdout=subprocess.PIPE, ...` and
`_terminate_tree(process) ==> process.kill()` are each KILLED by that case.

The third measurement above — the derivation surviving because every case passed
`mutant_timeout` explicitly — is closed too: `max(MUTANT_TIMEOUT_FLOOR_SECONDS,
2.0 * elapsed + 1.0) ==> 300.0` is now KILLED.

The third consequence is not closed. Nothing sums the parts, so
`ORACLE_BUDGET_SECONDS`'s comment still claims structurally impossible for what
the numbers make likely; the bound holding makes the worst case computable —
budget plus N timeouts of at least the floor — rather than computed.

## One of those two kills does not reproduce (2026-08-10)

The section above is right that the bound is there and wrong about which half
carries it. Re-run independently from a clean tree at `57658c4`, over the same
two cases, `stdout=out, stderr=err ==> stdout=subprocess.PIPE,
stderr=subprocess.PIPE` **SURVIVED** — 2 killed, 1 survived. `_run_bounded`
never calls `communicate()`; it calls `Popen.wait(timeout=...)`, which waits on
the process handle, so it returns on time whatever the streams are, and the
mechanism this file measured is not on the path the fix takes. Redirection is
still load-bearing for a reason stated nowhere and covered by nothing — nothing
drains the pipes, so a PIPE oracle blocks at the buffer and its timeout is a
false KILLED. The sentence above claiming both halves are killed by that case
stands as what was believed;
[[2026.08.10-a-two-part-fix-is-reported-as-two-kills-and-the-half-that-carries-it-is-the-other-one]]
holds the re-run and the consequence. `_terminate_tree(process) ==>
process.kill()` and the derivation's `==> 300.0` both reproduce as KILLED.

This is the third member of a family
([[2026.08.07-a-same-size-mutant-is-masked-by-the-bytecode-cache-and-reports-a-false-survivor]],
[[2026.08.08-a-crashing-test-command-is-indistinguishable-from-a-killed-mutant]])
where the sweep's mechanism is written correctly against a model of the command
that the loop's real command does not satisfy. The bytecode one was about the
subject, the crash one about the command's exit code, and this one about the
command's children.
