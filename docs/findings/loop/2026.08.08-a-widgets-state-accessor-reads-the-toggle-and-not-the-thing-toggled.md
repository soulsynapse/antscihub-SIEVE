# A widget's state accessor reads the toggle and not the thing toggled

The test reads as a complete behavioural case. It builds the widget, asserts it
is not expanded, clicks the arrow, asserts it is, clicks again, asserts it is
not. Three assertions, a real user gesture between them, and no fixture that
could be too uniform to disagree with itself — none of the shapes the review
prompt lists.

What it never touches is the widget. `is_expanded()` is
`return self.arrow.isChecked()`, and `QToolButton.setCheckable(True)` is what
makes that alternate. Delete the `toggled` connection and the sequence still
passes; ship the body visible from construction and it still passes. The
module's opening sentence — the explanation "stays shut until it is asked for",
which is the whole of what makes this VISION's wizard reimagined rather than
VISION's wizard — is carried by nothing.

The prediction that would have refuted this: a mutant that makes the guidance
appear on the step unasked and turns some assertion red. `setVisible(False) ==>
setVisible(True)` is exactly that mutant and it survives.

The generalisation is about where a test's observable sits relative to the
behaviour. An accessor written for the test's convenience tends to read the
*input* to the behaviour rather than its *effect* — the button's state rather
than the panel's, the flag rather than what the flag gates — because the input
is the value the implementer had in hand. That is upstream of the code under
test, so the assertion passes through it without touching anything the module
wrote. It is the same defect as a getter that returns the constructor argument,
dressed as an interaction test, and the click in the middle is what makes it
look otherwise.

Distinct from
[reverting the implementation is no proof when the item created the module](2026.08.07-reverting-the-implementation-is-no-proof-when-the-item-created-the-module.md),
which is about what a `ModuleNotFoundError` certifies. Here the sweep is the
remedy that file prescribes, and this is what it found.

## 2026-08-09: the open question gets a partial answer, and the shape is weaker than stated

`c7b1f8b` added `VideoCanvas.showing_source` / `badge_text()` for the source
badge, and the three cases that landed with it assert on those two and nothing
else. The `open_questions` above named `control.py` and `app.py` as the
candidates; this is a third site, and the reason to record it is that it fails
the finding's own test one degree short.

`showing_source` is *not* the expander's defect. It reads the module's own
field, which is genuinely the state, and every mutant that would break the state
machine dies — the clear in `set_values`, the `mark_source()` call in
`app._paint_viewport`, a mark forced back down after it. The accessor is
upstream of nothing. What is unheld is the layer past the accessor: under
`uv run pytest -q tests/gui`, replacing `paintEvent`'s `if badge:` with
`if False:` survives, so the widget can decline to draw the word and every case
about the badge stays green. The verdict sentence at the top of this file would
not convict it, and the body's generalisation — "the flag rather than what the
flag gates" — is the clause that does.

The distinction is worth keeping rather than collapsing: an accessor reading the
input to the behaviour is a wrong assertion, and an accessor reading correct
state that nothing then draws is a missing one. Both leave the module's headline
sentence unfalsifiable and both are found by the same sweep, so the review
question stays as written — ask what the accessor reads, and then ask what reads
the accessor. On this widget the second question is the one that bites.
Carried as work in
`todo/the-source-badge-is-painted-by-nothing.md`.
