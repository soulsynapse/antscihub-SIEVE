# The proof of red corrects the item and leaves the comment it was written from

The order the run worked in is the whole mechanism. It read the item, whose
own body (written the day before, by a `specify` run) says a zero rate "would
make `at_input_of` divide by zero, and a negative one would run the whole graph
with a window pointing the wrong way". It wrote `StalledParams` and the case
from that premise, restating it in both the model's docstring and an inline
comment. Then it deleted the guard to prove red, discovered that `at_input_of`
refuses the rate one line later, and wrote *that* into the item under a heading
called "What the proof of red measured" — accurately. The comment two files
away, arguing that a negative rate escapes as frames, is what the run believed
an hour earlier and never went back to.

Nothing catches this. The case is red per call, both calls, so the vacuity
checks pass; the criterion passes; `ruff` has no opinion on a false sentence.
The only reader who would notice is one who opens `types.py` while reading the
comment, which is exactly the reader the comment was written to save the trip.

The cost is not the sentence. It is that the comment is the stated reason the
second `pytest.raises` block exists — a reader deciding whether the block earns
its line is told the two directions differ, when in fact both directions are
refused identically by the same neighbouring guard and the case's whole subject,
for zero and for negative alike, is that the message names the node. Delete the
premise and the second block still earns its place, but for the other reason,
and no artifact in the tree says which.

## 2026-08-08: the same shape reaches a neighbour item, and the final message is where the correction dies

Second occurrence, in the review of `f6508d7`. The run read four neighbour items
before implementing, then wrapped `ExecutionPlan.build` in `except ValueError`
— which, because `GraphError` subclasses `ValueError`, falsified the first
sentence of the first bullet of
`todo/the-second-failing-command-moves-the-shared-refusals.md` ("`run_cmd`
catches … nothing at all around `ExecutionPlan.build`"). The run *knew*: it said
so in its final message, and then said "that item's file move remains, so I left
it alone." The item file kept the pre-commit tree. The same run folded correctly
into the two artifacts it was still holding at the end — the item it took the
decision from, and the finding whose measurement it changed.

So the shape below generalises past comments in the same diff: **a run corrects
the artifacts it is holding when it finishes, and a neighbour it read at the
start keeps whatever the tree said then.** The failure mode is specific and
worse than staleness — the run is not unaware, it has decided that "not my item"
means "not my edit", and routes the correction into a final message that no
future reader of the item will ever see. A neighbour read for guidance is a
neighbour to amend when the commit makes its text false; the merge-first rule in
`CLAUDE.md` already says a fold is cheaper than a mint, and this is the case
where it is cheaper than a sentence in a transcript too.

Distillation candidate for the *worker* prompt rather than the review one: if a
run names, in its final message, an item whose claim its commit changed, that
item needed a dated correction in the same commit.

## 2026-08-08: the correction lands in a new finding, and the false comment is the one the finding quotes

Third occurrence, in `fa1a86d`. The run was writing a case for
`canvas.image_of`'s constant-frame guard, probed it, and established that the
guard and the unguarded division are pixel-identical on every constant frame
without an infinity in it. It wrote that up accurately in
`findings/2026.08.08-the-constant-frame-guard-is-output-equivalent-to-the-division-it-refuses.md`,
which says in as many words that the comment above the branch "argues two things
… Only the first is true of the code as written". The comment itself is
untouched by the commit and still reads "dividing by the spread would be a
division by zero, **and either extreme of the ramp would be a brightness the
frame did not earn**" — and the guard writes `np.zeros_like`, which *is* the low
extreme of the ramp, the same one `nan_to_num` gives the mutant. The clause
argues against the branch's own output.

The new variable is where the correction went. The two occurrences above route
it into an item file or a final message; this one routes it into a *new finding
file*, which is the most discoverable artifact a reviewer has and the least
discoverable one a reader of `canvas.py` has. A finding that quotes a false
sentence in order to explain it is not a correction of that sentence, and it
reads more like one than the item file does, because it is about exactly the
line. The check the shape now wants is narrower than "read the diff's prose":
**when a run's probe falsifies prose the diff does not touch, the finding it
writes is evidence the prose is still there.** Grep the finding for what it
quotes.

The falsified prose here is in the module under test rather than in the test —
outside the item's stated scope, which is why the review folded the correction
into `todo/the-gui-skeletons-argued-branches-have-no-case.md` rather than making
it. Scope is the reason the run was right not to edit it and is not a reason the
tree gets to keep it.

The general shape, for the vacuity and review lists: **a run's last artifact is
the one its late discoveries reach.** Comments and docstrings written before the
probe keep the pre-probe belief, and the item file that contradicts them reads
as a record rather than as a correction. A review that has run the proof of red
itself already holds the fact — checking the diff's prose against it costs
nothing extra and is the only place it gets checked.
