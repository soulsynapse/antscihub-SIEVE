# A -k disjunction is green for the disjunct that names nothing

Two rules in this repo point the same way and only one of them is safe. The
todo template says to name the test the work will add, "with `-k` or a node id,
even though it does not exist yet", because "red because nothing matches is red
for the right reason". The review prompt says widening `done_when` is the
reviewer's power and to use it when a fold outgrows the criterion. Put together
they read as: append the new case name to the existing `-k` and the criterion
now covers it.

It does not. `-k` selects among the names pytest collected; a term matching
nothing removes nothing and asserts nothing. So a disjunction is exactly as
strong as its weakest satisfied term, and appending to it can only ever be a
no-op or a narrowing that never fires. The failure is invisible in the usual
direction — the widened command still passes, which is what a reviewer expects
to see for the half that already landed, so nothing signals that the other half
was not covered.

This is a different defect from
[2026.08.07-a-k-selector-and-the-prose-name-beside-it-are-two-criteria.md](2026.08.07-a-k-selector-and-the-prose-name-beside-it-are-two-criteria.md),
which is about a selector and a prose name disagreeing and shows up as an exit
5 a worker cannot ignore. This one never shows up at all.

What makes it worth writing down rather than filing as a quirk of pytest is
where it bites: the review is the only session that edits `done_when`, and the
edit it is most often asked to make — widen for a fold, widen for a half that
is not started — is exactly the edit the mechanism cannot carry. A reviewer who
believes the widening landed has certified the untouched half in the same
breath as the finished one.

## Amended 2026-08-10: the shape recurred at minting time, one day after this closed

This file closed on 2026-08-09 with `commit: b63f43f`, and on 2026-08-10
`the-field-that-names-footage-leaves-the-schema` was minted (`d529f8b`) with a
`done_when` whose first leg was `-k "A or B or C"` over three names, one of which
(the anchoring case) landed with 11.3 a few hours later. From that moment the
leg exited 0 and said nothing about the two clauses that carry the removal, and a
worker read the exit as its baseline. This is the mint case, not the widen case
the body is written about, and the body's own carve-out is what let it through:
a disjunction over names that *all* fail to match is sound, so the rule "red
because nothing matches is red for the right reason" is true when the item is
written and stops being true the first time any one clause lands. An item whose
clauses land one at a time — which is every multi-clause item — passes through
that state by construction.

So the open question above resolves toward one leg per clause rather than a
disjunction, and the answer is the same for minting as for widening: this
review's edit to that item made the first leg three `&&` invocations of one name
each, and each now exits 5 for its own absence. Node ids would also do it (exit
4 on absence) at the cost of pinning the module and class a case must live in
before it is written.

The recurrence is the placement truth of
[2026.08.07-a-platform-trap-diagnosed-into-findings-recurs-until-it-reaches-claude-md.md](2026.08.07-a-platform-trap-diagnosed-into-findings-recurs-until-it-reaches-claude-md.md)
in a second domain. A finding in `findings/loop/` is read by reviews; the session
that *writes* a criterion is a specify or work run, and the channel it does read
is `docs/todo/_TEMPLATE.md`, whose criterion paragraph says "name the test the
work will add, with `-k` or a node id" and does not say that joining names with
`or` makes the leg green on the first one to land. Until that sentence is in the
template the shape has no reason to stop arriving, and a review can only tighten
one criterion at a time, after the fact. The template is a durable instruction
and the edit is Kendrick's.
