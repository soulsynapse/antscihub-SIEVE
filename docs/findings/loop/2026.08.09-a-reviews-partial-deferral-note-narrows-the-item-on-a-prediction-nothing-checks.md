# A review's partial-deferral note narrows the item on a prediction nothing checks

The review that wrote the note was doing the right thing by the loop: 09.2 had
just become `deferred_for: decision`, and
[a deferral propagates and only the review sees it coming](2026.08.07-a-deferral-propagates-and-only-the-review-sees-it-coming.md)
is the finding that says the downstream items must be told. What it could not do
is check itself. It restated PLAN's own argument — one input per node, so no
edge has a card to occlude — and that argument had been carried, unexamined, in
two places since the phase was sequenced. Restating a thing twice written is the
strongest available feeling of having verified it.

The asymmetry is what makes this worth a file. A review that hands a work run
*more* scope than the item asks for is caught by the next review, which reads
the diff against the item and calls the surplus a finding. A review that hands
it *less* leaves no diff to read. The missing clause is not in the commit, not
in `done_when` — a `-k` selector is satisfied by whichever cases were written —
and not in the item, because the note is the item's most recent word on what it
covers. Every artifact the loop inspects agrees with the narrowing, because the
narrowing is what produced them.

This is the same root as
[a subject-deferral's gate lifts and nothing in the repo notices](2026.08.09-a-subject-deferrals-gate-lifts-and-nothing-in-the-repo-notices.md)'s
amendment — reasoning written about a subject nobody can see is a prediction —
read at the moment the gate goes *up* rather than down. There the prediction
becomes checkable when the subject lands. Here it was checkable immediately, off
`Pipeline._check` and `walk.py`, by anyone who read the gate as a claim about
the tree rather than as a claim about clauses. The two spellings cost the same
sentence to write and are not the same artifact: "schema v1 gives a node one
input, so the occlusion clause waits" hides a step that "no graph in the tree
puts a card between an edge's ends" would have exposed to a grep.

The prediction that would refute this: if the note's error had been detectable
by the loop's own machinery, the work run's account would cite something going
red. It cites nothing — the run read `Pipeline._check`, saw the refusal was on
`downstream`, and wrote a graph the tree already admitted. The item's criterion
never had an opinion, before or after.
