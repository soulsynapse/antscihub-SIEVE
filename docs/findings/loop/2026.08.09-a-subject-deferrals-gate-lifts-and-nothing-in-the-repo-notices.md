# A subject-deferral's gate lifts and nothing in the repo notices

The failure this sits beside is
[a deferral propagating down the phase](2026.08.07-a-deferral-propagates-and-only-the-review-sees-it-coming.md),
and it is the same asymmetry read in the other direction. That one is about a
gate closing over items downstream of a deferral, which costs a work run per hop
and is loud. This one is about a gate opening, which costs nothing visible at
all: the items sit in the deferred table, the queue draws from the open ones, and
the loop drains a phase without them. Nothing goes red, no run stalls, and the
only symptom is a plan that finishes early while four high-priority items are
still spelled `deferred`.

What makes it a reviewer's job rather than a rule's is that `gated_on` is prose
by design — it holds "which decision, which subject", a sentence rather than a
reference, and that is what lets a deferral name something no item covers. The
cost of the prose is that its truth value is not derivable. A worker on the
gating item cannot discharge it either: a worker does not set `status`, and the
run under review read two of these four items for their rulings and correctly
left their frontmatter alone.

The prediction that would have refuted this: if gate-lifting were self-clearing,
at least one of the four would have been minted with a criterion or a status the
gating item's landing changes, or `doc_index` would name the gating item as a
path it could resolve. Neither is true of any of them — every gate is a sentence
naming a subject in English, and one names its item by filename inside that
sentence, which is as close as the schema gets.

## 2026-08-09 amendment: clearing the gate is not the whole of the duty

The next work run took one of the four items this finding reopened —
`crop-serving-and-checkpoint-read-back-become-source-tools` — and stopped
without touching the tree, because the item's central argument was written
against the gating subject while it was still hypothetical, and the real one
does not have that shape. The item asserted that `dag.node_keys` folds
`source_key` into every root, so a run over a written crop already folds what a
source tool over that file folds; `44b6456` split the root key and a source root
now folds `picked_key`, a different flavour with a different digest
([findings/2026.08.09-a-source-tool-root-keys-in-a-different-flavour-than-the-footage-it-replaces.md](../2026.08.09-a-source-tool-root-keys-in-a-different-flavour-than-the-footage-it-replaces.md)).
The item is now deferred again, on a decision, one work run later.

The trigger is the same one this file already names — the subject lands, and a
reviewer is the only session holding both facts — but the duty is larger than
`status`. An item gated on a subject was written by somebody who could not see
the subject, so its *reasoning* about that subject is a prediction, and the
landing is when the prediction becomes checkable. This review's own predecessor
flipped four items to open on exactly the grep this finding prescribes and read
none of their bodies against the commit, which is why the cost surfaced as a
burned work run rather than as a line in a review.

What that adds to the grep: for each item the gate lifts, read the paragraphs
that name the subject and check them against what actually landed, not just the
frontmatter pair. It is cheap at the moment of lifting — the reviewer has the
gating commit open — and it is a work run at any later moment.

The prediction that would refute this: if the items' bodies were subject-neutral,
none of the four would name a symbol of the gating commit's. All four do — a
grep for `source_key`, `node_keys`, `ToolSpec.source`, `source_roots`,
`picked_key`, `resolve_source`, `crop_bound` and `pick` hits every one of them —
and this item named `source_key` and `dag.node_keys` in the paragraph its whole
argument rests on, both of which moved in that commit.

## 2026-08-09 amendment: the open question was taken up, and answered narrower than it was asked

The open question above — whether `gated_on` should name the item as a link the
index can resolve, "so a gate pointing at a done item is a fact a test could go
red on rather than a sentence a reviewer has to notice" — was minted as
`todo/the-index-surfaces-a-deferral-whose-named-gate-is-done.md` and landed at
`4035899`. It is not the schema change the question anticipated and it does not
go red. `doc_index.render` scans each deferral's `gated_on` for any existing
item's filename as a substring and renders the pairs whose named item reads
`done` as a table beside "Waiting on a person"; `gated_on` stays free prose and
`validate` is untouched, so a gate that names a landed item and one that names
an unwritten one still validate identically.

The narrowing is the part worth carrying. The item's argument for informing
rather than failing is that a lifted gate is answered by "re-argue, don't
build" as often as by "open" — which is this file's own second instance, the
`crop-serving-and-checkpoint-read-back` item that came back deferred one work
run later. A check that went red would have demanded a status flip, and the
amendment above is the evidence that the flip is the wrong reflex. So the half
of the duty this file's amendment named as larger than `status` — read the
item's body against what actually landed — is exactly the half the machinery
does not take, by design rather than as a gap.

What it does take off the reviewer is the grep, and only for gates written as
filenames. All three deferrals live at `4035899` state prose triggers, so the
table renders empty against that tree and its first live subject is a deferral
minted after `docs/todo/_TEMPLATE.md` started asking for the filename. The
duty this file prescribes therefore does not lapse: for a deferral whose gate
is a sentence about a person's ruling, the grep is still the only probe, and it
still belongs to the reviewer of the gating item.
