# An invariant that only the rejected alternative breaks has no red to show

The item put two shapes on the table and said the choice was as much the item as
the change: a region-derived component in the file name, or a uniquifying suffix
before `part.replace(final)`. The worker chose the first and gave the reason —
`CropRecord.identity` says the second write of one cut replaces the first, and a
suffix counted off the folder makes it accumulate instead, so the suffix shape
would have closed this collision by opening its mirror. That argument is the most
load-bearing sentence in the commit, and it is the one thing in the commit no
test touches, because the worker wrote the case for it, watched it pass on the
unchanged tree, and removed it.

The removal was reasoned, not careless — the run's own message names it and gives
the rule it was following. That is what makes this a loop finding rather than a
diff note: the rule as the prompt states it ("check the transcript for
red-before-green evidence; if it's missing, revert the implementation and run the
test yourself") is a test *for* vacuity, and the worker applied it as a test
*of* whether a case is allowed to exist. Reverting the implementation is the
right probe when the question is "can this case fail at all". It is the wrong
probe when the case's subject is a property the implementation under review did
not move.

The near mirror is
[a consistency guard as a criterion is green on both sides of the work](2026.08.08-a-consistency-guard-as-a-criterion-is-green-on-both-sides-of-the-work.md).
There a green-both-sides *criterion* was the defect, because a criterion has to
witness the item's outcome. A green-both-sides *case* is a different animal: it
is a regression test, and every characterisation test in this repo is green the
day it lands. The two collapse into each other if the only question asked is
"did it go red today", which is exactly the collapse that happened here.

What the discriminator should be: a case is worth keeping when some
implementation a reader could plausibly write makes it fail. The pre-fix tree is
one such implementation and the easiest to reach, which is why the prompt names
it — but an alternative the item itself put on the table is another, and it is
the one whose refutation is the reason the code has the shape it does. A case
that fails against no implementation anyone would write is the vacuity the audit
was about; a case that fails against the design the item rejected is the record
of why it was rejected, and the docstring is a weaker place to keep it than a
test, by this repo's own rule about claims over prose.

What would flip this: an item whose rejected alternative is not stated. Then
there is no second implementation to name, the only available red is the revert,
and the worker's reading is the correct one.
