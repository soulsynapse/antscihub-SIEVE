# An item's alongside question is answered only in the run log

The item asked for one thing and wondered about a second: make every front end
resolve its source roots, and — worth deciding alongside — whether `node_keys`
should keep silently dropping a source node it was given no identity for. The
first is what `done_when` can witness, because a criterion is written from the
change the item wants. The second cannot be, and the asymmetry is not an
oversight in the drafting: had the answer been "yes, change it", the change
would have arrived in the diff and been visible; the answer was "no, keep it",
and a decision to change nothing produces no artifact at all.

So the ruling was argued at length in the run's final message, where it is as
good as unwritten. The item then reads `status: done` with a paragraph asking a
question, and a later reader cannot tell whether it was weighed and kept, or
read and skipped. This is the same failure the repo's own rule about docstrings
describing a shape the code has left behind is written against, pointed at the
backlog instead of at a comment.

Why it lands on the review rather than the worker: the worker did the reasoning
and stated it, which is all the loop asks of it, and no rule in its prompt says
a ruling has to be committed. The review is the step that sets `done` — the
moment the question stops being open — and it is the last participant holding
both the run log and the tree. After it, the log is one of hundreds and nothing
points at it.

The instance is worth keeping for its own sake. The ruling rested on
`cli/materialize_cmd.py` being a legitimate caller that hands no identities, and
that is true; but it relies on `picked` accepting *absence per node*, whereas
the cliff the item named is the *default value* of the `picked` parameter on
`ExecutionPlan.build` and `Dag.node_keys`. Making the argument required and
letting `materialize_cmd` pass `{}` would keep the deliberate case and remove
the forgotten one. Nothing in the tree is wrong today — every front end
resolves — which is why this is recorded here rather than minted as an item; a
fifth front end is what would make it cost something, and this file is what that
run should find.

## Amended 2026-08-09: a second instance, from an unsatisfiable premise rather than an open question

Same failure, different cause.
`docs/todo/the-luma-cap-is-slower-than-sequential-on-a-small-allocation.md`
stated an invariant as beyond question — a 2-CPU allocation must not be handed
more workers than a 32-CPU one gets per core — that no resolver returning at
least one worker can satisfy. The worker showed it unsatisfiable, substituted a
fixed cores-per-worker floor, and argued both in its final message. The
criterion witnesses the floor and is silent on the substitution, so the item
would have closed `done` with its own "what is not in question" paragraph
contradicted and nothing in the tree recording that. The same run also ruled the
colour path in, against the item's "the colour path is not part of this", on the
strength of a later sentence in the same item.

So the shape is wider than an *alongside* question: it is any ruling the
criterion cannot witness, and the item's premise being wrong is one of those. A
worker that contradicts, substitutes for, or declares unsatisfiable a sentence
of its item has made a decision the criterion does not carry, and the review is
the last participant holding both the log and the tree. This review wrote both
rulings into the item as a dated closing section before setting `done`, which is
the same act this file's consequence records — twice now, which is the argument
for the open question above being answered yes.

## Amended 2026-08-10: the limit case is a run with no item at all

A hand-written entry — "look through for things that are unblocked by the
latest adrs" — ran between two loop pairs, read the fourteen ADRs of 2026-08-09
against the open pool, and committed nothing, because there was nothing an
item's diff could carry: its whole output is rulings about other items. The
orchestrator recorded `exited with 0 — queued nothing`, which is what a run
that did its job and a run that did nothing look like from outside, and 226 runs
share the label.

The rulings were checkable, and this review re-checked them: `23`-`36` map to
the slugs the run named, the four Phase 10 items are `open` with `gated_on:
nothing`, ADR 27 is cited by no item, and the index's 67 open rows match its
count. One was a repo defect rather than an observation about the pool — ADR 33
names a `todo/` file in the present tense as the remedy for the epsilon re-walk,
and both halves of that remedy are `done` — and it had nowhere to land; this
review folds it into `todo/the-admission-argument-is-retold-in-four-modules.md`,
being the last session holding both the log and the tree. One claim did not
hold: the run called the first `open` row "the loop's next pick", and
`doc_index.py --next` answers a review of
`todo/the-intent-kind-list-has-no-referent.md`, because an `awaiting-review`
item pre-empts the open table.

What the limit case adds: the duty is not "write the ruling into the item" but
"a ruling reaches the tree or it did not happen", and a run with no item has no
place of its own to put one. The loop absorbs that only because a review
follows; a survey queued as the last row before a session is cleared leaves its
whole yield in a log nothing points at.

## Amended 2026-08-10: the item contradicted itself, and only the log noticed

`todo/the-canvas-shows-the-result-over-the-input.md` says in one paragraph that
"a source step shows its result alone" and in another that a root's input is
`result.source`, which is a composite rather than a lone picture. The work run
saw the tension, ruled it consistent — at a footage root the two frames are the
same, so the composite is a visual no-op — implemented the second paragraph,
and wrote both the ruling and the case it does not cover ("a checkpoint-read
root is the case where they would visibly diverge, and nothing exercises it")
into its final message and nowhere else.

The shape here is one step past the finding above. There the item asked a
question alongside its work; here the item's own two sentences disagreed, so
there was no question to answer, only a reading to pick — and a reading picked
silently is indistinguishable from a worker that read one paragraph and not the
other. The ruling was right and the tree still cannot show it: nothing in the
diff, and nothing in the item, records that a graph with more than one source
root has one `result.source` and therefore one answer for every root's input.
This review moves both into the item. The cost of not doing so is paid by the
next worker on the same item, who meets the same two paragraphs with no record
that anyone has been here.
