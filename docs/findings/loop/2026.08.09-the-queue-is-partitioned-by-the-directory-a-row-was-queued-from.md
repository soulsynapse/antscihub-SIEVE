# The queue is partitioned by the directory a row was queued from

The orchestrator runs one session at a time — twenty log files today, no two
overlapping — but it answers `list_queue` and `read_run_log` per project, and
it takes the project from the calling session's working directory. A worktree
opened at its root and a worktree opened at `docs/todo` are two projects. The
loop has been launched from both.

Nothing about this reads as a fault from inside a run. Every partitioned answer
is well-formed: a real running row, a real ordered history, real finished
entries with real exit codes. It is short, and shortness has no signature. The
01:24:53 run did the correct thing — read the queue, find nothing pending,
queue the successor — and the correct thing widened the loop, because the
pending row it would have deferred to was filed under a different name for the
same directory.

The prediction that separates this from ordinary duplication: a careless run
would show no `list_queue` call before its `queue_prompt`. This one shows the
call and its answer, and the answer is falsifiable against the log directory's
timestamps — the row it did not see started 235 seconds later. That is not lag
in the queue, it is absence from the view.

The cost is bounded but not zero, and it is paid twice. Once as a wasted run:
a worker whose selector answers `review` cannot do anything, and 02:07:28 is
that run in full. Once as a review with no subject: the transcript this session
was handed belongs to the worker that did nothing, while the commit that
`git log` calls HEAD was made by a run this session cannot name, list, or open.
Both are recoverable by reading the item — which is what
`2026.08.07-the-review-names-its-subject-by-recency…` already concluded, now
for a third reason.
