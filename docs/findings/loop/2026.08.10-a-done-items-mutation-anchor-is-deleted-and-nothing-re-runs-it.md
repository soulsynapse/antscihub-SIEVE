# A done item's mutation anchor is deleted and nothing re-runs it

The neighbouring failure is
[the copy-verbatim anchor](2026.08.07-the-copy-verbatim-anchor-stopped-being-verbatim-two-commits-after-it-landed.md),
and the difference is worth keeping straight. That one is a *property* a review
checked by hand once and then nobody kept — the tree never claimed to enforce
it. This one is a `done_when`, the loop's own executable object, the thing that
exists precisely so a claim does not depend on a reader going and looking. It
still rotted, because the loop only ever runs a criterion twice: once by the
worker it was written for, once by that item's review. After `done`, the command
is a string in frontmatter that nothing executes.

What makes `mutation_sweep` criteria the exposed class rather than `pytest -k`
ones is what they quote. A `-k` selector names a *test*, and a test that is
renamed or deleted is a change somebody made on purpose to the file the criterion
points at. A mutant anchor quotes a line of *production* source, which is edited
by every refactor that happens to touch it — and the person doing that refactor
has no reason to read `docs/todo/` for quotations of the line they are moving.
The worker here did nothing wrong: it retired a posture the item it was given
told it to retire, and the line it deleted was a line, not a criterion.

The failure is quiet in the specific way that matters. `mutation_sweep` exits 1
on a missing anchor rather than reporting a survivor, so the criterion is not
green-and-vacuous — which would be worse, certifying work nobody did. It is red
and uncollected, which means the only cost is that the six claims went unguarded
for however long it took someone to look. Here that was hours, because the
commit that broke it was the commit under review.

## Amendment 2026-08-10 (the sweep item's review): the exemption above is two sizes too generous

This file exempts `-k` criteria and it exempts findings by never mentioning them.
Reviewing f122dff turned up one of each, in one commit.

The `-k` half. That commit renamed
`test_an_oracle_whose_output_outgrows_the_pipe_buffer_is_scored_by_its_exit` to
`…_still_finishes` — a deliberate rename of a test, which is exactly the case
this file argued was safe, because "a test that is renamed or deleted is a change
somebody made on purpose to the file the criterion points at." True of the file;
false of everything else quoting the name. Three `measurements` probes and the
`verdict` of
[[2026.08.10-a-case-whose-oracle-is-talkative-at-the-baseline-is-refused-before-any-mutant-is-scored]]
name the old selector, and re-running one now is `27 deselected in 0.02s`, **exit
0** — worse than the anchor case this file was minted for, which at least exits 1.
A dead `-k` is green and vacuous. No `done_when` quoted it, so the exposure was
confined to findings this time; that is luck, not structure.

The mutation half, which is not rot at all. Both mutants that commit records as
`2 killed, 0 survived`, in the item's dated section and in the amendment to
`2026.08.08-a-crashing-test-command-is-indistinguishable-from-a-killed-mutant.md`,
are refused when re-run verbatim today:

    mutation_sweep: the mutant leaves mutation_sweep.py unparseable, so it was
    never applied and no exit code from it is a verdict:
    'refuse_unparseable(subject, mutant, mutated)' — IndentationError: unindent
    does not match any outer indentation level (line 288)

They reproduce `2 killed, 0 survived` with one space added to each replacement,
because ` ==> ` eats the replacement's first indent space. So the recorded string
was already unrunnable on the day it was written, and what caught it was the gate
that commit had just landed — before f122dff the same strings would have printed
two silent false KILLEDs and the record would have looked right. The general
statement: a recorded mutant is a claim only if somebody types it back in, and
the loop's habit of quoting mutants into prose as evidence produces strings
nothing ever re-runs, whether they rotted later or never ran at first. A run
recording a sweep should paste the command it actually ran, not a transcription
of it.

The prediction that would refute this: if a rotted anchor were self-announcing,
some part of the tree would read `done_when` for items other than the one being
worked. `scripts/doc_index.py` parses the field and refuses its absence; nothing
runs it. `tests/docs/test_doc_index.py` asserts the index is fresh and the debt
set only shrinks; nothing runs a command out of frontmatter. The string is
inert the moment its item closes.
