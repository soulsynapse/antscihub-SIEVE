# A suite read through tail keeps the summary and discards the only number the red was for

`| tail -N` is the right shape for a green run: the counts are the whole of
what a green suite says, and the rest is noise a session should not carry. That
is exactly why it is reached for by default, and why it keeps being reached for
on the one run where it is wrong.

The asymmetry is that redness is not knowable in advance. A session that
believes it is confirming a green tree pipes to `tail`; if the tree comes back
red, the assertion body — for a budget gate, the measured milliseconds against
the budget — has already gone to the terminal and been dropped. The remedy a
session then reaches for is to run it again, and the second run of a
load-sensitive gate is green, so the margin is not merely missing but
unrecoverable without spending another full-suite run on a coin flip. Both
sessions here did precisely that, in the same order.

What makes this a loop finding rather than one more line in the flake's own
file is that the flake's file already contained the warning. Its 11.3 amendment
says, in as many words, "a run that expects to see this red reads the failure
body, not the last five lines" — and the review that read that amendment made
the same cut on its own red run an hour later. A caution addressed to a future
session's judgement did not survive contact with the default shape of the
command, which is the general form: where a habit and a written caution
disagree, the habit wins, and the fix has to change the command rather than
warn about it.

The cheap correction is that a whole-suite run is captured to a file
unconditionally — `uv run pytest -q > <file>` — and the summary read out of the
file. It costs nothing on a green run and is the only thing that works on a red
one. It also composes with the standing bound on re-running a test command: the
capture is what makes the *first* run informative, so the second is not spent
buying back what the first already had.

What would flip this: a red run of a budget gate whose margin was captured and
turned out to say nothing useful — that would make the missing datum cheap and
this finding a nuisance rather than a loss.

## Amendment 2026-08-10 (the sweep item's review): `$?` after the pipe is the tail's

Everything above is information a run had and dropped. The same idiom loses a
second thing, and that loss is worse than dropping, because it substitutes a
wrong value for a right one and nothing about the substitution looks wrong.

`cmd | tail -3; echo "EXIT=$?"` reports `tail`'s status, and `tail` succeeds on
any input it is handed. The review of `f122dff` ran

    uv run pytest tests/scripts/test_mutation_sweep.py -q
    -k an_oracle_whose_output_outgrows_the_pipe_buffer_is_scored_by_its_exit
    2>/dev/null | tail -3; echo "EXIT=$?"

recorded `27 deselected in 0.02s`, **exit 0**, and reasoned from it in
[[2026.08.10-a-done-items-mutation-anchor-is-deleted-and-nothing-re-runs-it]]
that a dead `-k` selector is green and vacuous — the worst class this loop knows,
a criterion certifying work nobody did. Re-run here unpiped, the same selector is
`29 deselected in 0.02s`, **exit 5**. It is red, and red under any `&&` chain or
CI step that reads it. That amendment is corrected on its own file; the number
here is why it was wrong.

The general form is that a pipeline's `$?` is its last element's, so every
`cmd | tail; echo $?` in this loop is an unmeasured exit code wearing the shape
of a measured one. `${PIPESTATUS[0]}`, or the file capture this file already
argues for, is what the idiom is missing. Note that the two losses have the same
asymmetry behind them: on a green run the piped `$?` is 0 and correct, so the
idiom is wrong only on the runs it is being trusted for.
