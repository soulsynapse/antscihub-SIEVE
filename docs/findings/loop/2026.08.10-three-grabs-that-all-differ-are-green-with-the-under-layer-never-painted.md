# Three grabs that all differ are green with the under layer never painted

The case under review asserts the composite by grabbing the canvas three
times — at the default opacity, at 1.0, and at 0.0 — and asserting the three
images are pairwise unequal. Its own docstring says why it grabs rather than
reads fields: "a canvas holding both images and drawing one of them would
satisfy every assertion made about its fields." That diagnosis is exactly
right and the remedy stops one step short. Delete the `drawImage` of the lower
layer and the three grabs are still pairwise unequal, because the sweep is
over the *upper* layer's alpha and the thing revealed underneath it — a real
input, or the empty letterbox — never enters an assertion.

The general shape: an inequality sweep certifies that the swept parameter
reaches the surface. It says nothing about what the parameter reveals. Any
claim of the form "A is drawn over B" needs one grab pinned to a picture, and
the pinning grab is the endpoint where the other layer is supposed to be
alone — because that is the only point where the claim and its negation
disagree.

The proof-of-red is where this got through.
`2026.08.09-a-proof-of-red-is-red-for-the-harness-and-reads-as-red-for-the-defect.md`
names reds that are the harness's rather than the defect's; this is the same
failure one layer up. The run's red was `'VideoCanvas' object has no attribute
'under'` against the stashed implementation — an `AttributeError` raised before
any assertion in either case ran. Every case is red against a tree missing the
attribute it names, so that red establishes only that the case imports the new
surface. The mutant above is the red the case needed and never saw: the smallest
tree on which the attribute exists, the fields are right, and the claim is
false.

## 2026-08-10 (amendment): the pinning grab is format-sensitive, and the mutant is now killed

The remedy above compares grabs of two *different* widgets — the live viewport
and a bare `VideoCanvas` handed the input as its only frame — and that is where
`QImage.__eq__` bites. A shown widget grabs `Format_ARGB32_Premultiplied` and an
unshown one grabs `Format_RGB32`; the two compare unequal whatever the pixels
say, so the first form of the pinned assertion failed on formats and would have
read as the composite being wrong. Both are opaque over the canvas background,
so `convertToFormat(Format_RGB32)` on each side is lossless and is what the case
carries. Any later pinned-picture claim in Phase 10 pays this same toll.

With the pinned case added, the mutant of the measurement above is killed:

    $ uv run python scripts/mutation_sweep.py --file src/sieve/gui/canvas.py --mutant "painter.drawImage(box, self._under) ==> pass  # " -- uv run pytest tests/gui/test_canvas_composite.py -q -k 'result_over_input or off_one_render'
    KILLED    painter.drawImage(box, self._under)
    mutation_sweep: 1 killed, 0 survived

and the same sweep restricted to the two cases that existed before still prints
`SURVIVED`, so the kill is attributable to the pinned grab and to nothing else.
