## The composite claim

File choice dominates route choice. In the right container (proxy for
exploring, lossy-intra cut for tuning) every decode route is interactive and
remaining differences are single-digit milliseconds; NVDEC, hybrid routing
and kf-snap exist only to make the *original* tolerable before its derived
files exist or when a release needs exact source pixels. Evidence: the full
sources × approaches × modes batteries (explorer-logs 18:38, 18:45), where
per-source spread dwarfs per-approach spread on every derived file.

The contention matrix extends the claim to a loaded machine: file choice
dominates route choice *and load*. On the right file, background sweep, flow
and encode barely move foreground latency; on the uncut original no route is
rescued from them (results/07-*203200Z, all 25 cells).

## Known weaknesses of this synthesis

- Single machine; the probe-and-cache mechanism is the portability answer,
  and its verdicts are near-tie-noisy (it kept hw on the proxy where
  sustained use favours sw by ~3 ms — explorer-logs 18:45).
- ~~Viewer-scrubbing-while-pipeline-runs has not been demonstrated live~~ —
  measured at process level (results/07-*203200Z): under sweep + 4 DIS flow
  workers + a live proxy encode, random access stays interactive on every
  derived file (proxy 9.8→31 ms p50, cut 11.9→24.8, utvideo 5.2→15.5 and
  never inverting despite having no hardware route), while the original
  degrades for real — NVDEC 150→294 ms p50 (p95 507), software 314→938.
  NVDEC immunity is partial: a ~2x hit under full load, holding a ~3x lead
  over software. What remains undemonstrated is only the felt, in-GUI
  version. (The 150 ms hw idle figure is random access over a 2,000-frame
  span — longer GOP rolls than exp02's short jumps; both stand.)
- ~~"Lossless loses" is measured only against FFV1~~ — closed: x264 `-qp 0`
  loses harder than FFV1 (random ~37 ms, 147 MB, no NVDEC help), while Ut
  Video posts the fastest random access of any file measured (~6.4 ms, 186 MB,
  software-only forever) — results/05-*192609Z, explorer-logs 20:08, and the
  amended lossy-intra finding. "Lossless loses" survives only as "loses the
  size/speed trade"; the latency race it wins.
- The Ut Video numbers are warm-cache: 186 MB fits in RAM, so cold-storage
  random access and cache-pressure at real span lengths are unmeasured.
- DIS flow's field quality on real events is unvalidated; every pipeline
  number downstream of flow inherits that caveat.
- CineForm was rejected on two measurements (198 MB > FFV1's 124 MB for the
  same 300 frames; ~107 ms drags — explorer-logs 18:38) — via ffmpeg's cfhd
  decoder, which may not represent GoPro's own implementation.

## How to recreate

Harness experiments: `uv run --group experiments python
experiments/decode-experiments/0X-*.py` (each finding file on the docs shelf
carries its exact command). Batteries: open the explorer, pick a source,
press "test all"; the log lands in `explorer-logs/` with machine and knob
provenance. The cut clips regenerate from 05-the-cut.py; the other derived files were
made by hand and their commands would otherwise live nowhere but a session
transcript:

    ffmpeg -i video-tests/GX010047c2_02_17_26.MP4 -vf scale=1328:-2 \
      -c:v libx264 -crf 23 -preset veryfast -g 1 -fps_mode passthrough -an \
      video-tests/derived/proxy-1328-intra.mp4

    ffmpeg -ss 60 -i video-tests/GX010047c2_02_17_26.MP4 -frames:v 300 \
      -vf crop=1024:1024:2144:982 -an -c:v cfhd -quality film3 \
      video-tests/derived/cut-cineform.mov

Delete `explorer-logs/probe-cache.json` to re-probe routing on new hardware.
